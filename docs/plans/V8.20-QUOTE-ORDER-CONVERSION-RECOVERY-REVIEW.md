# SH-08 — Quote → Order conversion recovery review

8 November 2026, Australia/Sydney. **Review and proposed fix only.** The owner
requested fictional-record verification and a documented proposal before code
changes, preserving intentional multiple orders per quote. No application code,
rules, endpoint, SQL, production record, commit, push or deployment changed.

Reviewed checkout: `49629eee12ec527d1f681c229768f9fe42eca761`, clean and up to
date before review. Its runtime source is `97cbf5d`. The preceding SH-06 release
record remains the authority for production; this review did not refresh live
deployment or business-record state.

## Recommendation

Treat **one intended order** as the retry identity, not the quote itself.
Ordinary re-entry should open existing orders or resume the saved conversion.
**Create additional order** should be an explicit, reviewed action with its own
request and order ID. Commit the order, its lines, SO counter, conversion receipt
and quote pointer in one Firestore transaction. Preserve every previous order.

Do not add unique `client_quote_id`, infer duplicates from matching amounts or
customer, collapse split orders, reset numbers, or automatically delete/merge
historical records. Merely awaiting the current backlink or disabling one button
does not solve independent tabs, browser interruption or lost acknowledgments.

## Findings, in repair order

### 1. P2 — re-entry has no durable conversion identity

`ShipmentForm` initialization reads the quote and items but ignores
`converted_order_id`. `QuoteDetail` uses that scalar only to replace its Convert
link with View PI. Consequently:

- Actual Router Back after success reopens the new-order form; another Create
  makes another order and replaces the quote pointer.
- A direct `?from_quote=` URL ignores a valid pre-existing link.
- Two separately mounted editors loaded before the first completion each create
  an order, even after the first has succeeded.
- Leaving during Create correctly avoids late navigation after SH-05B, but
  returning to the conversion form still creates another order.

The real SDK test also runs two independent clients concurrently. Both commit
distinct orders, each with one line, exact `1.222` pricing and consecutive
fictional SOs (`SO260101`, `SO260102`; seeded counter 100 → 102). The counter
transaction is consistent. It does **not** know that two calls might represent
one intended conversion. This is not an SO-number collision.

### 2. P2 — quote linkage can fail or finish out of order

After the order transaction, `handleCreate` calls `updateDoc` on the quote,
without awaiting it, and swallows rejection. The tests reproduce:

- A rejected backlink leaves a saved order and no visible warning; repeating
  conversion creates another unlinked order.
- Navigation completes while the backlink is pending; another conversion is
  available before it acknowledges.
- A late first backlink overwrites the newer successful order pointer.
- Deleting the source quote after initialization does not prevent the order
  commit; its later backlink fails.

Actual SDK/rules cases independently verify that a permission change after
creation rejects only the backlink, source deletion does not stop the current
creation transaction, and separate backlink writes leave both orders while
the last completed write owns the scalar pointer.

### 3. P2 — saved orders lack structured quote provenance

The normal actual-form case writes `source: 'manual'` and
`client_quote_id: null`, despite the human note saying Converted from Quote.
The schema already permits `in_app_quote` and `client_quote_id`, but this form
does not populate them. The normal SDK case confirms these persisted values.

Searching orders by `client_quote_id` therefore cannot recover every historical
conversion. Notes, amounts, customer IDs and filenames are insufficient to
deduplicate or assign ownership, especially after copying or manual editing.
Changing the source classification must retain current totals and editable
mapping, not introduce imported-PI fallbacks.

### 4. P2 — Duplicate quote copies the previous conversion link

The actual `QuoteDetail` Duplicate action spreads all header fields except
`id`, then resets status/dates. A converted quote's new draft therefore inherits
`converted_order_id` and shows View PI for the original order. The original is
preserved, but the copy has misleading ownership and no normal Convert button.

Proposed correction: explicitly omit conversion pointers, versions and operation
state when copying a quote. Copying commercial content and attachments must stay
as it works today. Existing historical copies require reviewed association;
do not clear their links in bulk.

### 5. P2 — ambiguous completion and broken legacy links need review states

A deliberately injected page-boundary fault commits the modeled transaction,
then rejects its acknowledgment. The form displays Create failure and a retry
creates another modeled order. Separately, two actual SDK calls create separate
orders when the fixture discards the first successful result. This establishes
the missing application-level request identity. It does **not** claim that a
particular production Firestore outage or SDK-internal retry has duplicated data.

A direct conversion entry with a dangling legacy pointer never reads its target
and silently replaces it after Create. Separately, source inspection shows
`shipping.deleteOrder` deletes the order/lines without repairing quote pointers.
The latter is a code-path finding, not a live deletion performed by this review.
Unknown completion or missing/mismatched legacy targets must offer Review/Retry
and retain evidence, rather than silently treating the quote as unconverted.

### Passing controls that must remain unchanged

- Same-editor native repeated clicks and duplicate submit events enter one
  transaction while it is pending.
- A definite rejection before commit changes no order/counter; Retry creates
  one order with one SO allocation.
- Failed source initialization exposes no Create form or write.
- First-tier selection, quantity 1,000, unit price `1.222` and total 1,222 remain.
- Two **deliberately intended** fictional orders, each for 500 pieces with
  separate customer POs, retain both orders and totals of 611 each. The first
  order is unchanged by the second. Today's UI does not express that intent;
  the proposal must make the distinction explicit without removing this use.
- Customers cannot read source quotes or create orders; denied creation consumes
  no SO. Existing staff need both Shipping and Quotes for this conversion path:
  SO counter rules belong to Quotes. Shipping-only SO allocation is currently
  denied. Do not broaden capabilities during recovery work.

## Proposed behavior

| Situation | Proposed response |
|---|---|
| No recorded conversion | Review the existing prefilled draft; Create prepares one durable request, then commits it. |
| Prepared request exists | Show its reviewed summary and Resume. A second tab must reuse it or show a conflict if its draft differs. |
| Request committed, response lost | Read the receipt and open that exact saved order; do not allocate another SO. |
| Re-entry/Back after success | Show linked orders with Open order as the main action. |
| A genuine additional order is needed | Explicit Create additional order, review customer/quantities/prices/PO and a short reason; prepare a new intent. Previous orders stay intact. |
| Source or prepared draft changed | Review required; preserve both the user's edits and frozen request. Never reuse an operation ID for different facts. |
| Legacy link is missing, mismatched or uncertain | Keep the existing reference visible, explain the issue and require association review. No automatic replacement or guessed historical order. |
| Order was later deleted | Preserve the conversion receipt as a missing-target record. No implicit reconversion; an explicit additional order may follow reviewed resolution. |
| Quote is duplicated | New draft has commercial data but no inherited conversion ownership or receipt. |

Additional-order preparation must compare the current conversion revision.
Two tabs confirming against the same old revision must not silently create two
new intents: return the active request or require refreshed review. Distinct
reviewed additional intents are legitimate and each receive their own order.

## Proposed implementation boundary — not implemented

### A. Private saved intent and atomic commit

Use a narrow Node conversion endpoint with the existing Firebase Admin bootstrap,
current-profile authentication and internal Shipping **and** Quotes capability
checks. Reuse the invoice-recovery approach to identity, receipts, conflicts and
safe responses, but not its SQL allocator: this conversion is entirely Firestore.
Do not reuse invoice IDs/collections or call invoice allocation as a side effect.

Proposed additive private path:
`client_quotes/{quoteId}/order_conversions/{operationId}`. A server-owned quote
pointer identifies a single active prepared request; a version protects explicit
additional-order decisions. A request stores:

- Server-selected operation/order IDs fixed before the allocation transaction.
- Initial/additional intent, initiating internal UID/time and reason where needed.
- Reviewed, normalized order/line payload and a canonical typed fingerprint;
  source quote/header/items snapshot or equivalent complete source preconditions.
- Prepared/committed/cancelled/review-required status and the final order/SO receipt.

Prepare must transactionally return the existing compatible active request,
return existing committed history for ordinary entry, or claim a new explicitly
reviewed intent. It must not trust a client-chosen customer/quote association,
new UUID as permission for another order, or a stale additional-order revision.
Lost prepare responses recover through the quote's persisted active pointer.

Commit must read all required quote/request/order/counter/source facts before
writes, check frozen payload/ownership/source preconditions, then atomically:

1. Create the stable-ID order with normalized lines and structured quote ID.
2. Allocate the SO through the same Hong Kong year/seed/format rules as today,
   only where the current workflow allocates one.
3. Mark the request committed with order/SO receipt.
4. Update the quote's compatibility `converted_order_id` to this latest committed
   order, increment its conversion version and clear the active pointer.

If committed, subsequent calls return the stored receipt without rewriting
commercial data or allocating. If nothing committed, retry the same prepared
request. An existing stable-ID order without a matching receipt is Review
required, not success inferred from existence. Keep every earlier receipt as
history; the scalar remains a latest-order shortcut, not the full relationship.

Do not use `updatedAt` alone as a quote revision: existing item edits do not all
update their parent. Source checks must include the actual item set/content.
Do not recompute over reviewed user edits on retry. Preserve all existing pricing,
precision, custom/Corp Gift/Range mapping, discount/deposit/totals, UC recognition,
optional catalogue fallback, manual empty-quote entry and file references.

The current `shipping.js` mixes browser/React imports with normalizers and SO
allocation. Extract only the pure shared contracts needed by the server, with
parity tests, rather than importing that browser module into a Lambda or writing
a second pricing/numbering implementation. The existing Woo stable-ID helper
illustrates identity, but lacks SO allocation/quote receipts and cannot simply
replace the current function. Leave manual, Direct Invoice, Woo, Shipping
Duplicate, SI/UC recovery and stock workflows outside this bounded conversion fix.

### B. UI ownership and customer boundary

ShipmentForm retains startup state, draft editing, source mapping and navigation.
QuoteDetail and the conversion form share a small read-only order-history/status
panel with explicit Resume/Open/additional controls. Busy, errors and receipt
states must survive navigation; a request failure is not proof no order exists.

Private requests contain reviewed commercial/internal context and stay under
the customer-denied quote path. Customer requests must be denied at the endpoint
before private reads. Operations must never be nested under the existing broad
customer-readable order wildcard without a specific exclusion. Keep private
snapshots, actor IDs, fingerprints/reasons and receipts out of public order
payloads, customer APIs and exports. The existing `client_quote_id` order field
is an opaque foreign key, not permission to read an internal quote.

### C. Rules and legacy-client limits

Before implementation, specify and test server-owned quote pointer/version
fields and operation writes. Ordinary quote edits/items keep their permissions;
clients cannot replace conversion ownership or forge operation receipts. Protect
new converted orders' provenance from later client changes. Deletion of a
tracked quote/order requires explicit guarded handling that retains receipt
history; do not let ordinary Delete silently erase recovery evidence.

**Important limit:** old conversion tabs submit an indistinguishable manual
order with `client_quote_id: null`. Restricting the new fields alone cannot
prevent that old path from creating an unlinked order. The bounded fix can
protect its own requests and block old scalar-backlink updates, but cannot
promise complete old-client prevention. Require a controlled tab refresh at
cutover and test stale tabs explicitly. If mandatory backend prevention across
all legacy manual Creates is required, first propose the broader SH-07 creation
protocol; do not silently disable manual order creation to claim SH-08 closure.

## Migration and rollout proposal — apply nothing at review stage

1. Review the exact additive fields, rules, endpoint and lifecycle contract before
   implementation. No SQL, Storage migration or business-record upload is needed
   for this proposal. Bound request size/line count before transaction creation;
   never split the atomic conversion into partial order batches.
2. Test only fictional data initially. Preserve the current schema/defaults for
   old orders and normal quote editing. New prepared requests are created only
   by an authorized, explicit conversion action, not page viewing.
3. A later read-only historical audit may list valid/missing/mismatched pointers,
   source IDs and ambiguous copied links. That audit has not been run here. Do
   not backfill ownership from notes, prices or a pointer alone: Duplicate has
   demonstrated that a pointer can be inherited. Record a reviewed association
   before importing a legacy link into verified history; create no order/SO for
   this association action. Historical orders and attachments stay unchanged.
4. Publish reviewed rules/backend compatibly, then the gated app candidate;
   fail closed if recovery is unavailable. Confirm explicit additional orders
   still work. Document the stale-tab limitation and refresh procedure. Retain
   receipt/rule protections during app rollback; never roll back by deleting
   operations, orders or counters.
5. Deployment requires owner authorization, both exact-SHA GitHub jobs through
   `npm run release:ci -- --wait`, fresh candidate/production admin and approved
   customer sign-ins, real feature/readback proof and unchanged unrelated records.
   No deployment approval is implied by this review request.

## Lessons and next decision

The SO transaction already solves counter/order atomicity. Conversion recovery
needs a saved business intent and an atomic source relationship around it.
A scalar pointer is neither full order history nor proof of original ownership.
Same-editor guards do not coordinate tabs, and copied header metadata needs an
explicit lifecycle whitelist. Preserve deliberate multiple orders while making
accidental repeats resumable.

**Next proposed implementation:** the bounded SH-08 conversion protocol, status/
history UI and quote-copy ownership correction described above, with fictional
tests and migration review. General SH-07 Create recovery, concurrent saved-order
editing and durable financial outbox work remain separate. Implementation and
deployment await a subsequent owner instruction.
