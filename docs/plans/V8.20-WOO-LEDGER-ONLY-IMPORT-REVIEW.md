# WooCommerce ledger-only import review

15 November 2026 AEDT · Read-only review against `22e4ca336d8c7fa37b563435bca3465dc4748d6d`.

The exact internal WooCommerce order ID finds OC invoice rows through `app_sales_invoice.order_id = 'woo-' + id`, independent of the Firestore order header or lines. A matching invoice can identify a UC through its `uc_id` foreign key. An exact SI recorded in `uc_registry.jes_si` is a second way to find related UC history. A UC row on its own has no structured Woo internal ID. Its `order_no` carries the Woo display number, which can differ from the internal ID. ## Evidence and limits

- A production SELECT inside a read-only transaction found one invoice row for the exact ID of the previously audited detached sale. It found one UC through the foreign key. Exact SI and exact display-number checks also each returned one UC candidate, and the display-number result was closed. That case still had surviving Firestore lines in the historical audit. The ledger-only condition was reproduced with fictional records. [Detached invoice source review](V8.20-SHIPPING-DETACHED-RECORDS-AUDIT.md#woocommerce-invoice-source-review)
- The production snapshot contained 12 invoice rows with canonical Woo IDs. All 12 had `channel = 'woocommerce'` and a populated `external_order_no`. The ID suffix and display number agreed in this snapshot. The Woo source returns these fields separately. The allocator also saves `order_id` and `uc_id` at issuance before the follow-up adds the channel and external number. The canonical lookup therefore must include exact order-ID matches whose channel or external number is blank. [Allocator INSERT](../../erp-sync/app_sales_invoice.sql#L268) · [Invoice follow-up](../../netlify/functions/lib/invoiceRecoverySql.js#L157)
- The production UC Registry had 224 Online Shop rows with a plain numeric order reference and 115 with one leading `#`. None of the numeric references in either form had surrounding spaces. These are reference formats, and the source label plus an exact number can signal a possible match for review. The reference alone cannot establish that a UC belongs to a given internal Woo ID.
- The existing invoice list API can filter by SI but has no exact Woo order-ID operation. The UC search matches partial text across several columns. Import preflight needs a narrower read than either list. The ledger already has a non-unique index on `external_order_no`. The live schema has no dedicated index for `app_sales_invoice.order_id` or `uc_registry.order_no`. An on-demand check by one order is the first slice. Measure the deployed-sized queries before adding any index. [Current UC API](../../netlify/edge-functions/uc.js#L94) · [Current invoice API](../../netlify/edge-functions/uc.js#L137) · [PostgREST equality filters and index guidance](https://docs.postgrest.org/en/stable/references/api/tables_views.html)

## Fictional verification

Six tests ran in in-memory PostgreSQL 17 using the checked-in invoice schema and durable allocation migration, with a minimal fictional UC Registry. Seeded allocations used the real allocator and replayed the same operation to verify the same receipt was returned. Every lookup compared invoice, UC, receipt, audit and sequence snapshots before and after.

| Case | Result |
| --- | --- |
| New sale | No exact evidence. Similar numbers, free-text matches and another channel's identical number were ignored. |
| Ledger-only sale | The internal ID found the invoice and its UC without a display number or any Shipping record. Supplying a different, correct display number independently matched that invoice and UC. |
| UC-only sale | Both plain and hash-prefixed references matched against the independently known display number. The internal ID alone could not resolve these rows. Using it as a display number could instead select an unrelated candidate. |
| Split and reissued invoices | The exact Woo ID returned three distinct invoice numbers with one shared UC, including the voided original. The first, split and reissue receipts retained their identities. Fixture invoices in this case had no follow-up channel or external number. |
| Historical display-number match | Exact Woo channel and display number surfaced one invoice with a blank order link and another pointing to a different order ID. Both require review of the original source to establish ownership. |
| Read-only boundary | PostgreSQL rejected a write inside the lookup transaction. The stored rows and sequences were unchanged. |

The fixture and output are in the Git-ignored `qa/out/woo-ledger-review/` directory. These tests verify the lookup rules. The application guard and role-specific responses still need implementation tests.

## Smallest proposed fix

1. Keep the existing Firestore checks. An existing header returns **Imported**. A missing header with surviving lines returns **Needs review**. If both are absent, run the financial check before staging any order or line writes. Keep the current stable-ID transaction and retry behavior.
2. Add one narrow read operation to the existing Woo server endpoint, available to admin and staff who have both Woo and Shipping access. Accept only a validated internal order ID and derive the canonical Firestore ID server-side. Use exact equality against the invoice ledger. Any matching invoice, including a void or multiple invoice rows, returns **Needs review**.
3. When the canonical lookup is empty, take the display number from the Woo order resolved by that internal ID on the server. Check exact `channel = 'woocommerce'` plus `external_order_no`, and exact Online Shop UC `order_no` matches for the display number and its single-`#` form. These are review signals, including when an invoice points to another order. Return a minimal outcome and a short reason to the Woo page. Keep invoice and UC details behind their current permissions. Do not broaden `/api/uc` or add database grants. [Woo endpoint gate](../../netlify/edge-functions/woo-sync.js#L173) · [UC gate](../../netlify/edge-functions/uc.js#L45)
4. Continue with creation only after all required reads complete without a match. If Woo identity or the ledger could not be checked, show a retryable verification error before writing. Keep the transaction's check for a concurrently created header. The financial lookup is a preflight across systems, so it does not make Supabase and Firestore a single transaction.
5. Verify the real Import action with fictional Firestore and ledger fixtures. Cover new import, retry, two tabs, ledger-only and UC-only history, split and reissue history, conflicting references, unreadable sources and role denial. Assert that review leaves the header absent and all financial rows, numbers and receipts intact. Include a customer-access check for the new endpoint.

The read-only review left production data and the application untouched. Recovering historical records and obtaining original invoice files remain separate from the import guard.

## Implementation and regression coverage

The Woo import checks the saved order and lines first. For a new order, the browser sends the internal Woo ID to `verify_order_import`. The server verifies the ledger and returns `clear` or a review reason. The Woo page shows **Needs review** for invoice and UC matches and offers a retry after a verification error. Review results are checked again on a new import attempt. The operation sends no invoice or UC details to the browser and requires no database migration or Firebase rules change.
