## Findings from fictional orders

| Area | Observed result | Implication for closure |
| --- | --- | --- |
| Reserved and consumed stock | One order held 10 metal units and had already consumed seven crystals. Explicit Release returned the metal reservation to zero with 100 on hand and two movements. Crystals stayed at 93 on hand, zero reserved, with two movements. | A closure check needs each stock class independently. Release unused reservations through the existing action. Keep physical consumption on the ledger. |
| Interrupted reservation | Reservation saved four crystal units against the first stock item, then failed on a missing second item. The order had `stock_activity` but no reserved flag or saved lines. Calling the existing Release function directly left the four units reserved and posted no release movement. | Check outstanding movements by order and item as well as the order flags. Block ambiguous or interrupted stock for Supply review. A cleared flag or a successful return from Release cannot serve as proof of a zero balance. |
| Packing, Freight and invoices | An emulator-only closure field on the existing order kept the order ID and lines. The actual Packing print, staff invoice print and owning customer's invoice print rendered identical content. The Packing print retained `3 sets`, its legacy tier remark, `4 boxes`, consignee, UC, SO and customer PO. Freight kept the same selected quote, scenario, cargo and USD 145.25 price. Three invoices, UC rows, SQL receipts, audit rows, Firestore mirrors and allocation-history records were preserved. The customer remained unable to read a private allocation receipt. | Preserve the order root and lines and expose existing document routes under Closed. Keep packing and finance history readable under the same permissions. |
| Metadata alone | The Production Orders screen still showed the order as Confirmed. With the fixture closure field set, the ordinary stock function reserved two packaging units, the Freight function cleared the selected quote and a Shipping client created a Packing scenario. After the current invoice follow-up was reviewed, the invoice repository also accepted a new pending reissue request. The test stopped at that request and issued no fourth invoice. | Apply closure to the operational lists and enforce it at the write boundaries. A field or UI badge alone leaves stale tabs and privileged handlers able to start work. |
| Invoice follow-ups | A linked current invoice still received an automatic worker claim with the fixture closure field present. For an older allocation, the worker discarded its job because the order pointed to the latest invoice, while the historical receipt stayed pending. With a current claim already issued, the existing SQL review prevented its delayed write. Firestore recorded `manual_review`, removed the job and ignored the stale completion. Repeating review returned the original audit result and financial counts were identical. | Check every allocation and queue job for the order. A blank queue does not prove all follow-ups are resolved. Use the existing SQL review fence and confirm its Firestore readback before closing. |

The order status describes physical progress. `Cancelled` in Sales Invoices is an invoice disposition, so reusing that field would conflate closure with a decision about billing. The Production Orders list also uses its filtered app orders to deduplicate JES by SO. Filtering closed app rows before calculating that set would make their JES copies reappear in Active. Requirements uses confirmed/packing/ready status and can keep selected order IDs in memory. The dashboard also uses those stages for Production. These are source-review findings and should be covered in implementation tests.

## Proposed workflow

1. **Start with Review closure.** A staff user with Shipping access opens the existing order and sees its current stage, stock status per class, linked Packing/Freight records and outstanding invoice actions. Require a reason. Keep the order active while the checklist has unresolved items. Record the final actor, reason and timestamp in a private audit record. Customer-readable order fields should carry at most the lifecycle marker needed for existing reads. Keep closure reasons, finance details and internal actor identities outside customer-readable documents and child paths.
2. **Resolve stock explicitly.** For each material class, allow the existing authorised Release action for reserved stock, then read back the movement and balance for that order. Treat active operations, unmatched movements and legacy issue inconsistencies as blockers requiring Supply review. Leave consumed stock in place. A confirmed physical return can use the existing audited reversal workflow before closure. Resolve tracked partial activity before closing, without relying on the stock-history flag alone.
3. **Resolve invoice work under existing permissions.** A pending or unlinked allocation must be recovered or reviewed through the existing financial workflow. For each linked invoice, finish applicable follow-ups or have an authorised reviewer record the reason through the existing SQL review fence. Preserve completed stages and all receipts, including split and reissue history. Surface older pending receipts even if there is no queue job. Reconcile a lost SQL acknowledgement from the same receipt before completing closure. An uninvoiced order needs a deliberate finance disposition when billing is still due. Closing the Shipping order does not decide the invoice, credit-note or payment outcome.
4. **Close the saved revision.** Use a server-owned, retry-safe transition. Recheck the order ID and revision, the stock state and the invoice review outcome at confirmation. The action should write one closure record and keep the original stage and identity. Coordinate it with new stock, commercial, Packing, Freight and invoice writes so a stale tab either wins first and forces a fresh review, or receives a closed-order response without a partial write. Do not treat Firestore and SQL as a single transaction. For pending cross-system work, persist and verify the existing finance review before final closure. A failed check leaves the order active and the verified review available for retry.
5. **Show Active and Closed in Production → Orders.** Keep closed records searchable by customer, SO, UC and SI, with the prior stage and a Closed label. Keep Packing and Freight history read-only, retain print and download links, and preserve Finance and customer invoice history under their current permissions. Remove closed orders from active Requirements and Dashboard production demand, including previously selected IDs. Preserve JES deduplication against all app SOs. For the first slice, use the existing finance workflows for legitimate corrections and leave reopening for a separate decision.

## Implementation

Production → Orders now has Active and Closed views. Review closure shows the
saved stage, material status, linked Packing/Freight counts and all invoice
allocation states. The server compares the reviewed order and linked record
versions at confirmation. A successful close keeps the original order, lines,
stage and documents and saves one private audit record. Closed orders remain
searchable and their document views remain available to their existing roles.
The Active view continues to deduplicate JES against all app orders.

Reservations are released explicitly from the stock panels. Closure checks the
movement totals per order and item, verifies saved reservation/consumption rows,
and blocks unfinished or inconsistent stock work. A per-class operation marker
keeps interrupted stock work visible until the same action finishes. A retry
must use the original input. A new review after resolving stock or invoice work
is required before closure. Invoices with pending or unlinked requests need
Finance attention. Linked historical and current receipts can use the existing
SQL manual-review fence. Existing completed stages and invoice identities are
retained. This release adds Firestore rules and writes additive closure fields
only as orders close. It uses the existing stock movement index and invoice SQL
procedures. No index, SQL migration or historical backfill is required.

The release fixture exercises the authenticated closure and invoice handlers,
real stock and freight functions, closed-list and JES behavior, Firestore rules,
and in-memory PostgreSQL. It checks idempotent confirmation, the private audit
and document permissions, release and partial reserve, a changed Packing record,
late invoice work, the actual Packing workbook and rendered staff/customer
invoice views. Native browser PDF generation is outside that fixture.
