## Problem and resulting contract

Previously Sales Invoices built a shorter Re-sync payload than normal invoice
saving. A fictional approved line total 1,222 / Accounting Total 1,200 could
become accounting 1,222 with its adjustment/reason/date/PO/notes cleared in the
financial copy. The warning then disappeared because comparison covered only
total/currency/UC/customer. Read and upsert errors were also swallowed by the
best-effort client, so an unavailable ledger could look empty.

Normal saving and recovery now share one complete field projection in
`shipping.js`. The existing `invoiceRegistryFields` signature, computed/PI
fallback and ordinary-save payload semantics are preserved. The separate
`savedInvoiceRegistryFields` uses the saved actual `total_amount`, approved
accounting amount and legacy `orderUc` fallback. It does not recalculate lines,
copy a subtotal/PI estimate as an actual total, round stored values or allocate
numbers. A blank accounting field falls back to the known actual total only
when there is no conflicting approved adjustment.

`invoiceReconciliation.js` owns comparison, review guards and strict fresh source
reads. It uses `useOrders`' original `_raw` snapshot, with trusted document ID
applied after the spread, for preview. Before writing, recovery reads a new raw
server snapshot with `getDocFromServer`; a cached/offline source cannot authorize
a financial write. List display, exports and global normalization remain intact.

The owned copy includes invoice/order/UC identity, customer, currency, actual and
accounting totals, derived adjustment/reason, allocation date and invoice date
separately, customer PO, notes, channel and external order number. Comparison
uses the edge's existing string limits/null conventions and cents for financial
equality. Payload/source values retain their existing precision. Server-owned
status, UC IDs, allocation/audit metadata, deposits and cash receipts are excluded.

## Safe recovery and visible outcomes

- Unknown actual total, invalid identifiers/dates, missing required source fields,
  adjustment without a reason, and a financial entry linked to another order are
  **Review required**. No automatic write is allowed. An explicit numeric zero
  remains valid; null/blank/whitespace never invent a zero amount.
- If the source Accounting Total is absent but either source or financial copy
  records an approved nonzero adjustment, recovery requires confirmation on the
  order. It does not silently discard that correction. Legacy SI references only
  in `erp_so_no` stay outside this writer; no invoice is inferred or reissued.
- Read errors show an alert and Retry. They cannot become `[]` and license writes.
  Recovery snapshots its requested eligible targets, guards repeated clicks, reads
  current source and financial ownership before each write, reports partial
  failures and confirms full field readback before reporting recovered records.
- A readback failure states that some records may have synced and offers a new
  financial check. If the write actually succeeded, that check removes the need
  to write again. Retrying a partial batch skips already aligned records.
- Abandoning the page stops subsequent work after awaits. A write already in
  flight can finish, but its old UI cannot update another page. This is not a
  transaction/lock across Firestore and the financial backend, or a durable outbox.

## API compatibility and completeness

Existing `upsertInvoice` and `listAppInvoices` best-effort behavior remains
unchanged for ordinary saves and UC Registry. Explicit recovery uses
`upsertInvoiceStrict` and `listAppInvoicesForReconciliation`.

The latter reads specific SI numbers in batches of at most 100, rather than
assuming absence from the first 1,000 rows means absence from the ledger.
`/api/uc`'s existing `list_invoices` operation adds an optional validated `si_nos`
filter and returns `complete:true` only for a complete targeted result. It uses
PostgREST's `Prefer: count=exact` and Content-Range count to reject truncated or
unverifiable results ([primary API documentation](https://docs.postgrest.org/en/stable/references/api/pagination_count.html)).
The client also rejects duplicate/unrequested rows. Existing list limits, `since`
filter and response shape remain compatible when `si_nos` is absent. The select
adds the already existing channel/external-order columns used by the projection.

Strict recovery rejects HTTP/parsing/completeness and missing-write-acknowledgment
failures. The existing edge upsert/default/adjustment-validation branch is
unchanged. No database schema, RPC, auth/module/rules, allocation or permission
change is included. Supabase changelog guidance was checked; no Supabase CLI or
database migration is used by this correction.

- 34 actual Chrome cases pass at 375px/1280px. Recovery/busy/error/review cards and
  long text fit without clipping. Source-bound evidence includes actual HTTP
  payloads, partial retry and no duplicate writes after readback recovery. All
  financial writes and responses are fictional; unexpected I/O fails closed.
- Full build and 914 prebuild cases pass, including 171 Shipping cases. Whole
  source no-undef lint and all 11 public Firebase configuration tests pass.
  Existing bundle-size/Browserslist notices remain outside this scope.

Two integration gaps found during implementation now have permanent coverage:
whitespace Accounting Total could otherwise become zero through edge coercion;
and normalized list fields could disagree forever with correctly recovered raw
notes/accounting. Recovery now uses consistent raw source facts without changing
global display normalization or ordinary-save semantics.

Permanent checks: `qa/invoice-reconciliation.test.mjs` in prebuild and the
product-search job; `qa/invoice-reconciliation-source-emulator.mjs` in the
customer-merge-emulator job. Evidence is local under `qa/out/invoice-reconciliation/`.
No real customer emails, financial upserts, invoice numbers, source-order writes,
stock changes or automatic historical backfill are test actions. Fresh QA sign-in
