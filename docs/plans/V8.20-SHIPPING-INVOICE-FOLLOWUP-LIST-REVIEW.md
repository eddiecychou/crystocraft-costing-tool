## Proposed first slice

1. **Add an Invoice follow-ups view under Production → Orders.** It lists linked invoices with unsettled financial or Woo stages, including older split and reissued invoices on active or closed orders. Show the exact SI, UC, SO or order reference, customer, current or historical label, pending stage and a short next step. Use **Open order** to take staff to the selected receipt. If the receipt has changed by the time the order opens, show its fresh status and keep the link from selecting another invoice.
2. **Read from saved invoice receipts.** Use a bounded server-side projection of `orders/{orderId}/invoice_allocations/{operationId}`. Check the document path, stored operation and order identity, parent header and stage states. Reuse the per-order classifier for linked receipts. Consult the retry job for a verified lease when needed. Advance the full document-path cursor even when a page contains only settled records. Distinguish loading, partial results, read failure and a completed search with no pending items. Offer continuation and refresh. [Firestore query cursors](https://firebase.google.com/docs/firestore/query-data/query-cursors)
3. **Keep order actions in the existing order panel.** The view gives staff **Ready to resume**, **In progress**, or **Finance review needed** and the references needed for handoff. Submit Resume or a completed Finance review from the order panel, using its existing saved request and reference checks. When a parent is missing or ownership conflicts, show a review status without an order action and avoid presenting an unverified SI or UC as authoritative. Treat the order and operation IDs together as the row identity so a reissue or duplicate invoice number cannot silently replace another row.
4. **Keep access aligned with Shipping.** Verify the active profile in the server read handler and return a limited, private, no-store response. Admin and Shipping staff can view it. Existing permission checks continue to govern actions for admins and staff with both Shipping and UC. Keep the view outside invoice-only staff summaries, their CSV and customer routes. Keep private reasons, actor IDs, attachments and financial snapshots out of the list response.

The first slice needs no recovery queue writes, historical backfill or invoice-original approval. Before rollout, check the exact read query and committed index configuration in a candidate environment. The emulator validates cursor behavior and rules but does not establish production index requirements. Measure reads and latency with representative volumes before deciding whether a separate index or stored projection is warranted. [Firestore emulator index limitations](https://firebase.google.com/docs/emulator-suite/connect_firestore#how_the_cloud_firestore_emulator_differs_from_production)

## Implementation

Production → Orders now has a separate **Invoice follow-ups** view with refresh, continuation and retry. The private GET endpoint checks the current Shipping profile, then reads 50 saved receipts at a time with one lookahead. It uses the full document path for continuation and batch-reads only the relevant order identities and retry leases. An empty page with a cursor still offers **Check more receipts**. An ownership conflict or a missing order shows a Finance review status without an invoice link.

Each verified row links to its own order and operation ID. Loading the order requests the exact receipt even if it falls beyond the per-order checklist limit. The order highlights and focuses the verified row, or explains when that receipt has settled, gone missing or could not be verified. Opening the link does not submit an invoice action. Resume and Finance review still use the order panel’s existing identity and permission checks.

Tests cover separate split and reissue links, an empty page followed by a retried page, linked receipts beyond the checklist limit, closed orders, leases, detached and conflicting records, access restrictions and a receipt settling after the list opens. The list performs no invoice, ledger or recovery-queue writes and needs no record migration.
