## Confirmed bugs and recovery gaps

### SH-01 — P1: PI data can be attached to another selected file

**Trigger and observed result:** start fictional PDF A, then B. Completing B
before A leaves the selected filename B but replaces the SO/UC/lines with A.
Completing A while B is still pending clears the shared busy state and enables
Create too soon. A third case completes A, then selects B whose extraction fails:
A's data remains usable while the selected upload is B. In all three cases a
fictional Create captures `source_file.name = Fictional-B.pdf` together with
`uc_no = UC5001/26`, `erp_so_no = SO260001`, `item_code = PI-ITEM-A`.

**Owner:** `ShipmentForm.jsx:417–441`, selected file/result/busy state.
Single and sequential successful imports associate their own file and data.
The relevant startup/completion/error sections match pre-extraction `a38465b5`.

**Proposed repair:** give an import one identity; commit its file and parsed
result together. A superseded completion must neither apply data nor clear the
current busy state. A replacement failure needs an explicit restore-previous
source or manual-entry decision. A latest-request token alone does not repair
the failed-replacement association. Preserve documented parsed-field precedence,
including an already selected customer, unless separately approved.

### SH-02 — P1: a stale ERP check can supply another PI's lines

Parse A, then B; resolve ERP B, then ERP A. B's current file/header remain, but
ERP A replaces the comparison. Clicking the ordinary recommended ERP-adoption
action copies `ERP-SO260001` lines while the form still has B's `SO260002` and
`UC5002/26`.

**Owner:** `ShipmentForm.jsx:446–463`. Bind comparison and adoption to the current
committed import/SO identity. Clear/reject stale comparisons; the adoption action
must recheck identity. The check function matches pre-extraction `a38465b5`.
Implement with SH-01, retaining ERP absence as a nonblocking outcome.

### SH-03 — P1: customer invoice exports ignore accounting total without a deposit

Fictional approved invoice: 1,000 units × USD 1.222 = USD 1,222;
Accounting Total USD 1,200; adjustment −22 with a reason. The actual existing-order
form preserves those values through a fictional save/reopen. With deposit absent
or zero, admin print/Excel show Amount Payable 1,200 and words for 1,200, but
customer print/Excel show only 1,222 and words for 1,222. With deposit 200, the
customer control correctly shows payable 1,200/outstanding 1,000. An unadjusted
control agrees in both views.

**Owner:** `src/customer/CustomerInvoicePrint.jsx:98–114` and its totals/words
markup. Accounting payable is currently rendered inside the positive-deposit
branch. `invoicePaymentTotals` already derives the correct amount independently.
Pre-deposit `ae19a034` already uses line total without accounting payable in
customer output; this defect predates Deposit Paid and the recent panel cleanup.

**Proposed repair:** choose the approved invoice payable total independently of
deposit visibility. Keep deposit/outstanding rows hidden for absent/zero deposit,
while still disclosing the approved accounting payable when different. Align
admin/customer print, Excel and amount-in-words contracts. Keep proforma and
legacy ERP behavior unchanged. The test proves actual print markup and generated
XLSX values; it is not a newly saved native Chrome PDF/layout inspection.

### SH-04 — P1: financial Re-sync can erase the approved adjustment in its copy

The actual `SalesInvoices` page compares only total/currency/UC/customer.
An accounting-total/date/reason/PO/notes-only difference raises no drift warning.
If a currency mismatch triggers Re-sync on the same adjusted invoice, its actual
request omits accounting total, adjustment reason, invoice date, PO and remarks.
The actual unchanged `/api/uc` upsert handler defaults those omissions to line
total/empty values. Fictional readback becomes accounting total 1,222,
adjustment 0, empty reason, null invoice date and blank PO/remarks. The warning
clears even though the financial copy has lost these values. The Firestore order
still retains its approved accounting total 1,200.

**Owners:** `SalesInvoices.jsx:185–224`, `ucRegistry.upsertInvoice`, and
`netlify/edge-functions/uc.js:163–205`. This is a payload/recovery-contract gap,
distinct from the known browser-close/durable-outbox limitation.
The drift/Re-sync block is byte-identical to pre-cleanup `a38465b5`.

**Proposed repair:** use the authoritative registry mapping for every writer,
define exactly which source fields reconciliation owns, compare those fields,
and preserve explicit null/zero/approved adjustments. Surface failed recovery
instead of treating a swallowed best-effort result as success. Test no-drift,
metadata-only drift, missing row, adjusted row, failure/retry and idempotent repeat.
No historical financial records should be rewritten automatically under this fix.

### SH-05 — P1 recovery contract: direct invoice allocation can lose its result

After direct-order creation commits, SI/UC allocation and the order-reference
patch run separately. Both failures set a warning on the New editor, then
unconditional navigation remounts the saved editor and discards it.

Two distinct fictional cases matter:

- Allocation rejection leaves one accessible saved order with Raise Invoice,
  but no visible landing-page explanation. No duplicate order was created.
- Allocation acknowledges an SI/UC, then the Firestore reference patch rejects.
  The saved order has no SI. Ordinary Raise Invoice invokes allocation a second
  time for the same order ID, rather than recovering the acknowledged result.

**Owner:** `ShipmentForm.jsx:553–582`, registry client/edge allocation contract.
The block matches pre-cleanup `a38465b5`. Checked-in allocator SQL issues a new
number without lookup/reuse by order ID; the deployed function was not inspected.
The diagnostic proves a repeated client allocation request, **not observed live
duplicate invoice issuance**.

**Proposed repair:** distinguish allocation rejection from reference-persistence
failure, retain an acknowledged result and show recovery on the saved order.
Before retrying allocation, establish a recover-by-intent contract. Inspect the
current deployed definition read-only before selecting any SQL migration. An
invoice-per-order uniqueness rule must not be assumed if split/reissued invoices
are legitimate; use a defined operation identity and explicit new-invoice action.

### SH-06 — P2: quote initialization has no pending/error ownership

Rejected quote-header and quote-item reads each produce an unhandled rejection,
no visible read error/Retry, and an optimistic “Prefilled from the quote” message.
While quote items are pending, the form permits edits; later completion replaces
the manually selected customer, UC, notes and line without warning. Ordinary
prefill/missing-quote warning and quote Q→R abandoned-response controls pass.

**Owner:** `ShipmentForm.jsx:198–225`; effect matches pre-extraction `a38465b5`.
Add explicit initial pending/success/error/retry states. Prefer completing the
initial quote snapshot before enabling edits/Create; if early editing is required,
define dirty-field/confirmation rules first. Preserve existing normal defaults,
Range validation and the ability to review/edit a successfully initialized quote.

### SH-07 — P2: creation completion can navigate after its editor is abandoned

For manual, direct and quote creation, hold a transaction/allocation pending,
navigate to another route, then complete it. The old handler forces navigation
to its newly created order. Existing-order Save already guards this outcome;
Create does not. This can interrupt later work, although the original committed
order is valid.

**Owner:** `ShipmentForm.jsx:484–592`, especially navigation at 582. Add an
initiating-editor completion guard, without pretending an in-flight database
write was cancelled. Add a synchronous in-flight guard for Create as well:
ordinary repeated button clicks are already disabled, but explicit duplicate
submit events currently enter twice. The latter is a robustness gap, not proof
of native double-click duplication or an SO-number collision. Startup and
post-create navigation match pre-cleanup `a38465b5`.

### SH-08 — P2 policy/recovery gap: quote conversion re-entry can create another order

`QuoteDetail.jsx:500–509` relies on `converted_order_id` to replace Convert with
View PI. The conversion form does not check an existing conversion. After a
successful conversion, actual Router Back reopens the earlier conversion form;
Create makes a second distinct fictional order and overwrites the backlink.
A rejected best-effort backlink also leaves the quote offering conversion again.
Normal transaction rejection/retry is a passing control and creates only one
order; do not confuse that with this re-entry gap.

**Owners:** quote prefill, post-create backlink at `ShipmentForm.jsx:578–579`,
`QuoteDetail`, and transactional creation. Establish intended conversion/recovery
identity and check/reuse it atomically where possible. Define intentional
reconversion/split fulfillment separately before imposing quote uniqueness.
The current backlink/navigation block predates cleanup. There is no authorization
to merge/delete any existing orders under this review.

## Known design debt and unverified coverage

- **Concurrent editors:** the acknowledged header/line batch does not compare a
  revision or prevent last-writer loss. A cached line query may miss another
  user's unseen line. Preserve offline behavior; design conflict semantics and
  test two clients before proposing revision preconditions.
- **Durable financial synchronization:** frontend follow-up can stop after browser
  closure. Re-sync currently needs SH-04 correction before being described as a
  complete recovery path. A durable outbox/reconciliation worker is a separate
  design, with bounded retries, observable state and identity, not a UI extraction.
- **Initial direct-invoice financial projection:** the post-create allocator sends
  identity/customer/currency/UC, not monetary fields, and the create handler has no
  subsequent financial upsert. Confirm initial-ledger completeness in fictional
  integration tests when defining SH-05; no live missing-total diagnosis is claimed.
- **Upload/validation order:** Create uploads its selected file before validating
  the order. An invalid draft can therefore leave an unreferenced uploaded object.
  This is source-inspected, not a real Storage write in this review. Validate before
  upload and define retry/file reuse in a later creation slice; do not delete
  existing objects without record/reference evidence and a retention decision.
- **Packing/Freight:** ownership and explicit write entry points were inspected;
  their complete failure/overlap/save outcomes were not exercised in this review.
  Packing scenario switches await cartons without a selection token; rejected
  initial tab reads also lack a complete catch/Retry path. These are source-review
  risks requiring fictional reproduction, not newly certified cross-scenario
  corruption. Do not claim the prior tab-render parity tests cover these outcomes.
- **Other boundaries:** no current production-record audit, AI extraction accuracy,
  live allocator schema verification, concurrent-counter delivery, real Storage
  upload durability, PBIS accounting validation, stock re-audit, or new native PDF
  layout certification. Those claims need their own evidence.
- **Diagnostic retention:** new runners and raw evidence are local ignored files,
  not permanent regressions in CI. Promote the confirmed cases into tracked tests
  only with the separately authorized repairs. Durable reproduction steps/results
  are recorded above so the report is useful on the other Mac too.
