## Ownership and cause

- **Order.** The form displays Delete order for an existing order without a quote-conversion receipt. The handler reads the line collection and batches those line deletes with the order delete. Firestore checks Shipping permission and blocks a non-linked current invoice allocation. It permits a linked allocation and has no stock, Packing or Freight check. The line read happens before the batch, so a later edit is not part of that read set. [Form](../../src/pages/ShipmentForm.jsx#L950) · [Delete handler](../../src/shipping.js#L225) · [Order rules](../../firestore.rules#L1201)
- **Stock.** Ledger movements have their own transactions and order IDs. Reserve reads a missing order as empty, posts the stock movements and then updates the order. Release and reversal need the movement rows saved on the order. This sequencing explains both the failed reversal and the partial stale reservation. [Reserve](../../src/orderStock.js#L105) · [Release and reverse](../../src/orderStock.js#L299) · [Stock ledger](../../src/stockLedger.js#L104)
- **Packing and Freight.** Packing owns scenario, carton and content documents and recovers missing print fields from the order and its lines. Freight owns quote and decision documents. Its decision rule requires an existing order, including for an explicit unmark. [Packing reader](../../src/pages/PackingListPrint.jsx#L12) · [Legacy unit and remark lookup](../../src/packingUnits.js#L3) · [Packing Excel](../../src/logisticsExcel.js#L47) · [Freight reader](../../src/logistics.js#L239) · [Freight rules](../../firestore.rules#L1242)
- **Invoices.** The PostgreSQL ledger retains invoice identity independently. App invoice print and Excel access depend on a live Firestore order and lines, and the internal app invoice list starts from current orders. The ERP invoice route has a separate data source. A follow-up claim also requires the current order to point at its allocation. [Invoice ledger](../../erp-sync/app_sales_invoice.sql#L21) · [Internal print](../../src/pages/SalesInvoicePrint.jsx#L40) · [Customer print](../../src/customer/CustomerInvoicePrint.jsx#L33) · [Sales Invoices](../../src/pages/SalesInvoices.jsx#L78) · [Queue](../../netlify/functions/lib/invoiceFollowupQueue.js#L41)

## Proposed implementation order

1. **Guard permanent deletion and close the stock race.** Limit permanent deletion to disposable drafts without inventory activity, document numbers, external source history, or linked Packing, Freight or financial records. Include legacy issue flags and snapshots, old issued-invoice references without allocation IDs, and work already in progress. Recheck eligibility and the order revision at commit time under the existing Shipping permission. The authoritative path must guard linked writes as well as deletion. A UI check or a read-before-delete alone leaves a race, since some child documents can be written independently. Move stock changes and their order state into an atomic operation where feasible. If a batch limit requires multiple transactions, use a durable, retryable stock operation that prevents deletion until it settles. Test both commit orders in two tabs, including legacy or interrupted stock operations.
2. **Keep real order history accessible.** For orders with downstream records, provide a close or archive action that retains the same order ID, lines and existing record permissions. Record who closed it, when and why. Release outstanding reservations explicitly. Reverse consumed stock only when the physical return is confirmed, through the existing audited stock workflow. Preserve scenario selection, stored freight pricing, order references, invoice/UC identities and every legitimate split or reissue. Show the reason permanent deletion is unavailable and make the closed order and existing document links searchable. Resolve or flag open invoice follow-ups for review before closure, preserving their audit record and the current no-late-write guard.
   [Completed closure review and proposed workflow](V8.20-SHIPPING-ORDER-CLOSURE-REVIEW.md).
3. **Review any already-detached records separately.** Run a read-only inventory and downstream reconciliation, using stable order and document IDs. Report detached movements, Packing scenarios, Freight decisions and invoice/UC records for owner review. Restore links or reconcile stock only from confirmed evidence. Keep saved manual and PI requests for missing orders in **Needs review** and keep intentional repeat orders available as independent requests.

## Implemented guard

Shipping staff delete eligible drafts through `/api/shipping-order-request`.
The transaction rechecks the operator's permission, the saved edit identity,
stock activity and linked Firestore records before removing the draft and its
lines. A bounded read of existing invoice and credit-note tables checks older
financial rows by order ID. Failed dependency reads stop deletion. Client-side
order deletion is denied by Firestore rules. A draft with any recorded SO,
PI, SI, UC or customer PO stays available for reference, including draft-status
orders that already received an SO during the normal creation workflow.

Stock reservation now marks the order before posting movements. The movement
transaction and Firestore rules also check the target order, including for a
stale browser using the older write path. The marker retains the order after
an interrupted attempt, a release or a reversal. A collection-group index on
`movements.order_id` covers legacy stock writes that never set the marker.
Packing and Freight creation require an existing order when a link is supplied.
This release adds the index and updates Firestore rules. There is no data backfill.
