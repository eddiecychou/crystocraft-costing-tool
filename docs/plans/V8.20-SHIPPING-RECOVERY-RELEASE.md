# Shipping recovery and PI upload limit

12 November 2026. The owner authorized correction, fictional testing, commit, push and deployment after both required GitHub checks. This publishes the previously local SH-07 request workflow together with its two readiness corrections. Publication and live verification results are recorded below when completed.

## Behavior

- Manual/PI entry, Duplicate Order and initial Direct Invoice retain one request identity through retries, lost acknowledgments, reloads and parallel tabs. Explicit separate orders/copies remain separate. Supplied invoice numbers and intentional split/reissued invoices keep their existing behavior.
- A first Direct Invoice with a saved SI but unfinished accounting updates reports `followups_pending`. The saved list offers Resume; the request offers Finish Direct Invoice. Retrying reuses its pinned first invoice operation and never allocates another SI. Changed references/customer/current-operation identity require review. Fully finished first operations remain independent from newer splits/reissues.
- New PI originals are limited to **20 MiB (20,971,520 bytes), labeled 20 MB in the UI**. Selection rejects larger files before reading/extracting them; server preparation and original verification enforce the same cap. Storage create rules enforce it independently. Oversized replacement leaves the previous original and entered lines intact. Existing originals remain readable; no saved file is resized, replaced, moved or deleted.

The fixes use the existing invoice follow-up guards, supplier/customer identities, precision and request/receipt ownership. There is no order-level or quote-level invoice uniqueness restriction and no automatic historical deduplication.

## Verification and lessons

The previously failing review probes are ordinary acceptance tests now, with no TODO suppression, and run in `customer-merge-emulator`. Six cases verify financial RPC failure, lost acknowledgment, parallel retry and four changed-reference/ownership refusals. Readbacks compare order, invoice, UC and receipt counts as well as exact financial values. The original split/reissue and repeat-sale/copy suites remain in place.

Nine manual/PI, eleven Duplicate Order, ten initial Direct Invoice and six readiness acceptance cases pass locally with real emulator transactions and disposable PostgreSQL 17. The PI suite uploads exactly the limit, downloads identical original bytes, denies a larger direct Storage upload even with a valid legacy descriptor, and retains read access to an existing larger original. Unit tests check the same boundary and prevent drift between shared JS policy and Storage rules. Full prebuild/build and touched-code no-undef pass. Chrome runs the actual editor, request list and recovery controls with fictional transports/records; browser and CI results are recorded in the release evidence table.

The initial boundary fixture omitted required request fields and returned a generic 503 before reaching size validation; it now prepares a valid receipt before simulating the legacy descriptor. A Chrome selector initially matched both existing error locations; it now targets the explicit form alert. The Direct Invoice browser fixture also omitted its fictional customer, so it correctly remained pending under the existing financial guard; the fixture now selects that customer. Resume checks the persisted operator/request identity because the saved invoice type is restored from the server without retaining the original URL hint. These corrections preserve application behavior.

An issued identifier is not a completed workflow: retain recoverability until required follow-ups are finished or explicitly reviewed. Resume the pinned operation, not the latest operation on the order. File limits must cover selection, backend descriptors and actual Storage bytes; a JSON request-size limit does not cap an independently uploaded original.
