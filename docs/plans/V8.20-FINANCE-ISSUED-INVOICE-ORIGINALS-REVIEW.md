## Matching a copy to an invoice

1. Start from the exact invoice in its source ledger. Use source, issuing legal entity or invoice series, and the complete SI as the identity. Preserve leading zeros. Order, UC, PO, filename and similar amounts can help locate candidates. Verify the invoice number on the document itself, including for splits and replacements that share the same order and UC. For legacy data, accept a documented exact SI reference and verify it against the issued record. A matching sales order number alone is insufficient.
2. Finance confirms provenance, such as the original sent attachment or a version retained at issuance. Match the issuer, bill-to identity, invoice date, currency and exact printed total to verified source evidence. For legacy display names, document the customer-to-account cross-reference. Compare the printed total, amount payable and outstanding balance as distinct values when present. Prefer documented evidence from issuance when dates or amounts were later edited. Blank values require review, and an explicit zero must be preserved.
3. Record the approved source and version privately with the SI, document type, original filename, byte length, SHA-256, reviewer and review time. Keep the original bytes and pin their version. Repeated intake of identical bytes can reuse the approved copy. Different bytes claiming the same SI and file type, unclear provenance, duplicate ledger identities, scans with unreadable fields and multi-invoice bundles go to **Needs review**. Finance resolves the conflict before the file is offered. Keep the reason and earlier evidence in the review history.

Each split or reissued SI has its own link and availability. A proven original of an explicitly void invoice can remain visible to staff with a **Void** label. Apply void and reissue status from the verified ledger, independently of what the historical PDF shows.

## Proposed access workflow

1. **Finance intake.** Finance identifies an approved source and supplies a small pilot set. A designated reviewer stages individual files privately, checks the matching evidence and approves the exact link. Reviewer assignment is a separate capability from reading invoices. An approved record references the stored version and digest. Record approval, replacement and withdrawal decisions. [Private file handling precedent](V8.20-CUSTOMER-FILES.md)
2. **Sales Invoices.** Invoice-only staff select **View original** on a verified OC row. The server checks their active Invoices permission on every request, resolves the exact SI and format, and returns the pinned private bytes. Use the same controls for viewing and downloading, with private, no-store responses. Customers use their existing scoped routes. JES copies stay subject to the ERP permission and can be considered in a separate slice.
3. **Availability.** Show **Original unavailable** for a known invoice without an approved copy. Show **Needs review** and send the case to Finance when the evidence conflicts. Show a retryable message for a temporary archive read failure. Under all three states, the summary remains available when the summary source is healthy. Staff CSV contains the availability label, with file locations and provenance kept private.
4. **Formats.** Pilot PDF viewing and downloading first. Treat workbooks as independently verified files. Offer original Excel only when Finance confirms the exact issued workbook and reviews its shareable contents. A PDF, recreated order export, or summary CSV cannot stand in for that workbook.

## Fictional verification

An isolated review harness passed 35 cases. It tested the proposed decision rules with fictional ledger rows and document metadata. One binary case used a PDF from the earlier fictional payable-export release and verified that a byte-for-byte copy keeps the SHA-256 and truncation changes it. Text readback of that fixture also confirmed that the printed total, amount payable and outstanding balance can differ. The existing summary and Shipping route suites passed all 20 tests. The harness log is in the ignored `qa/out/finance-issued-originals-review/` directory.

| Cases exercised | Result |
| --- | --- |
| First issue, split, replacement and void sharing an order, UC and financial values | Each exact SI resolved independently. A sibling or replacement filed against the wrong SI required review. Void status remained distinct. |
| Legacy SI, leading zeros, same SI in another source or legal entity, mere SO digits | Only the full SI in its verified source and issuer matched. An ambiguous or pending ledger record required review. |

| Regenerated copy with the same header, staging, multi-invoice bundle, missing file, duplicate and altered bytes | Unverified cases required review. ## Local fictional PDF pilot

The pilot adds a private PDF action to the invoice-only OC list. Sales Invoices opens an approved original in the existing local PDF viewer. **Download original** makes a fresh authorized request for the exact version that was previewed. The summary CSV carries document status only. An archive metadata outage has its own retry state while invoice summaries remain available. Missing approvals and withdrawn copies show **Original unavailable**. Metadata conflicts show **Needs review**. The server checks for the actual pinned object on each open and download.

The Node summary endpoint has a PDF read mode at `GET /api/oc-invoice-summaries?pdf=<exact-SI>`. It checks the signed-in user's current `admin` or `staff` with `invoices` profile before loading the ledger, and checks permission and approval again before returning the bytes. The exact ledger ID and order link, or the exact legacy order reference, bind the approval to one invoice. The approval also records the issuer, date, customer, currency, total and accounting payable. Temporary failures, missing bytes, corrupt bytes or a changed approval withhold the file. A valid void invoice keeps its void status on the summary row.

Approval documents use `oc_invoice_originals/{SI}`. The server derives the object path from the SI and approved digest, reads the pinned Storage generation and verifies size and SHA-256. Files use a private Storage bucket and carry no Firebase download token. Existing rules deny direct client reads and writes on both paths. The pilot buffers PDFs up to 4 MiB. [Netlify function payload limits](https://docs.netlify.com/build/functions/configuration/) · [Cloud Storage object generations](https://docs.cloud.google.com/storage/docs/objects)

The server feature flag `OC_INVOICE_PDF_PILOT` is off by default. Local tests seed their own approvals and files in Firebase emulators. Enabling the feature for a real archive is a separate release decision after Finance confirms the issued copies and an approved intake process. The pilot provides read access only. It has no intake or approval screen and requires no schema backfill.

The local emulator suite `qa/oc-invoice-pdfs-emulator.mjs` uses fictional current, split, reissued, void, staged and legacy records. It exercises the real Firestore and Storage SDKs, the existing rules and the endpoint handler with a fictional token boundary. The route test covers list actions and the CSV. Local Chrome checks cover multi-page preview, the original filename and bytes, and denial after revocation. Evidence is under `qa/out/oc-invoice-pdf-pilot/`. The tests join the existing release jobs. No deployment or production data operation was performed.
