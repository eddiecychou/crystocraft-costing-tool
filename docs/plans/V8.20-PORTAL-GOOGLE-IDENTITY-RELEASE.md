# Verified Google identity for portal applications and invitation claims

OC checks the Firebase ID token before processing either Google action. The token must identify Google as the provider for this session, contain an email address and mark that address as verified. The Google application uses that address. A Google invitation also requires a valid invitation link and a match with the invited email. A password session on an account linked to Google continues to use the password workflow.

Google self-applications still enter the approval queue. Existing admin invitations still apply the customer link and approval chosen by staff. The invitation page stays open across Google sign-in so the buyer sees the result and can retry with the invited account after an email mismatch. This application release requires no account migration, provider configuration change or Firebase rules deployment.

## Fictional verification

- The 12 portal access tests ran the application handler with Firestore in an emulator. Both Google actions rejected missing or invalid sessions, a password session with Google linked, a missing provider, a blank email and absent or false email verification. The rejected requests left profiles, the invitation, alert jobs and the captured mail count intact.
- Chrome used the portal’s normal sign-in form, the Firebase Auth emulator's Google popup and the actual invitation handler. A fictional Google applicant reached pending approval. A mismatched Google address left an invitation open. The invited buyer then claimed it, saw the confirmation and received access to the expected fictional company.
- The ordinary email application still entered the approval queue. A fictional password invitee claimed their link, set a password through the intercepted setup email and signed into the approved storefront. All test mail was intercepted locally.
- The route, access and enquiry isolation checks passed (38 tests). The repeatable browser rehearsal is in `qa/portal-google-browser.mjs`.
