## Operator workflow

- Choose **Sales Invoices → Direct Invoice**, enter the sale and click **Create Order**. The normal path saves the retail order, issues its first invoice and opens the saved order. It does not allocate an SO.
- After a lost confirmation or closed tab, reopen the request URL or find the entry under **My saved order requests** in Sales Invoices or Shipping. **Finish Direct Invoice** resumes the first invoice on that order. **Open saved order** is available even if issuance needs attention.
- A supplied invoice number is retained, including a legacy SI stored in the SO field. An issued first invoice shows its SI on the request. A later split or reissue remains a separate explicit action on the saved order.
- **Start a separate Direct Invoice** starts another sale. Two sales with the same customer, lines and amount may each have their own order and SI. Unsaved typing is local until the first valid Create.

## How a retry finds the same invoice

The Shipping request persists the intended order ID, header and lines. Its commit writes the order, lines and original invoice instruction together. The instruction records whether the operator supplied an SI or the first invoice is due. This permits a Shipping-only operator to save the order. Issuance requires both Shipping and UC permissions. [Shipping repository](../../netlify/functions/lib/orderCreateRequests.js)

The invoice endpoint’s `initial_direct` action checks the authenticated operator’s receipt, order ID, creation timestamp and Direct Invoice source. In the existing invoice-claim transaction, it finds or creates the **first** operation and binds its ID to the private request. If the saved-order workflow already started the first invoice, the Direct Invoice request adopts it. A split or reissue cannot become the target of an initial retry. SQL issuance, receipt verification, linking and follow-ups use the existing invoice workflow. Status reads can show the SI or pending work without issuing anything. Changed invoice details, an inconsistent operation or a replaced order lead to review on the saved order. ## Fictional verification

Tests read the committed order, lines, SO counter, SQL invoice rows, UC rows and allocation receipts. They cover lost responses before and after SQL issuance, a failed order link, parallel retries, a first invoice started independently from the saved order, supplied SIs, permission denial, replaced orders, intentional repeat sales and independent splits/reissues. Chrome exercises the actual Sales Invoices link and the saved-request controls after closing a tab, using Back, reloading and resuming from two tabs. Authentication, PI extraction and HTTP-to-SQL transport are fictional. Invoice allocation executes in local PostgreSQL 17.

The local build passed all 1,134 prebuild tests. The final emulator runs passed ten Direct Invoice cases, eight manual/PI cases, eleven Duplicate Order cases and 23 existing invoice recovery cases. Eleven Chrome scenarios passed, including three Direct Invoice scenarios. In the concurrent retry case, server readback found one retail order, one SI, one UC and an unchanged SO counter.
