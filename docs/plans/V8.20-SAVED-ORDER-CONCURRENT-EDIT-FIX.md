# Saved-order concurrent-edit protection

Owner authorized implementation, fictional tests, push and deployment on 9 November 2026, after both exact-SHA GitHub checks. This release concerns editing existing Shipping orders. Separate, uncommitted SH-07 creation recovery remains outside this release.

## Behavior and ownership

`shipping.getOrderEditSnapshot` reads server header / all lines / server header and retries when the version or invoice ownership changes. Legacy lines without `line_no` remain visible. `saveOrderWithLines` reconciles the complete line set and header in one versioned batch. Rules reject stale header edits and line writes, including an offline batch submitted before another operator's save. Reservations and unrelated stock fields keep their own ownership and merge behavior.

The form preserves the attempted header and exact line values before submitting. On conflict, it keeps the current editor visible, blocks another blind save and offers a latest-saved comparison. **Load latest and keep my draft** explicitly reloads the saved state while keeping the rejected draft available. **Restore draft for review** reopens the original edits for comparison. Reapply selected changes to a fresh version and save normally. Monetary values and line changes are never automatically merged. Rejected saves do not navigate away or update the financial registry.

Drafts live in device localStorage, scoped by authenticated UID, order and independent save-attempt ID. Two tabs retain separate drafts. They survive a refresh and can be explicitly discarded. They are not uploads or shared server records. If storage is unavailable, OC warns to keep the tab open and copy the edits. The server's acknowledged save remains authoritative even if local cleanup fails. Merely typing without attempting Save does not create a durable draft; this is conflict preservation, not a general autosave feature.

New line IDs are assigned before submitting and retained with the draft. A lost acknowledgement is accepted only when server `last_edit_id` matches the same attempt and its edit version is exactly the attempted next version. Another subsequent save requires review. Invoice allocation claims and reference links advance the edit revision in their existing Admin transactions. They preserve the last commercial attempt ID. The initiating form adopts returned invoice metadata only if the commercial attempt and creation identity still match its baseline; unsaved commercial fields are retained. First, split and reissued invoices remain independent.

## Migration and coordinated cutover

This plan is documented before applying production rules. No bulk migration or business-data repair is required. A historical order missing `edit_revision` is version zero. Its first accepted commercial save lazily writes:

- `edit_revision`: previous version plus one, independent of printed `pi_revision` and invoice-reference revision.
- `last_edit_id`: unique commercial save-attempt identity.
- `edit_origin_ms`: creation timestamp observed by the editor, or null on records without one. Rules compare it with the saved creation identity so a deleted/recreated record cannot accept the earlier draft.

Invoice Admin transactions increment `edit_revision` without changing `last_edit_id`. Existing attachments, line IDs, unknown fields and stock/reservation flags are preserved. New-order creation accepts absent/zero edit metadata, including its initial atomic lines; whole-order deletion remains atomic under existing ownership checks.

Publish only the approved Firestore rules after exact-SHA CI and candidate admin/customer verification, then promote the identical candidate app artifact. Old tabs' unversioned commercial/line saves are intentionally refused. Users must refresh the app before saving; they should copy unsaved edits before refreshing an older tab. No unrelated Storage rules or SQL migration belongs to this cutover.
