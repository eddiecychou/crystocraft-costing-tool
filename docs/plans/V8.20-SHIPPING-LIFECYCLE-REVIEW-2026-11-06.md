## Order loading findings

The actual ShipmentForm and shipping module were mounted in Chrome with real
React Router routes and fictional external I/O. Two ordinary navigation
controls passed. DOM-node identity also confirmed reuse of the form between
saved orders and between a completed saved order and a new form.

Six controlled scenarios reproduced incorrect editable state.

| Scenario | Observed result |
|---|---|
| A header response arrives after B has loaded | B's URL displays A's header, source file and lines |
| A line response arrives after B has loaded | B's header is combined with A's lines |
| A response arrives after navigation to New Order | The new form is repopulated with A's data |
| B does not exist after viewing A | B's URL retains A's editable form |
| B's order read rejects after viewing A | A remains editable and a promise rejection is unhandled |
| B's line read rejects after viewing A | B's header and A's lines remain editable with an unhandled rejection |

The submit button remained enabled in every reproduced defect state. One fictional Save
after the late A response at B's route captured A's header sent to `orders/B`,
A's item sent to `orders/B/lines/line-A`, deletion of B's existing line and
an invoice upsert linking `SI-A` to order B. This establishes the write-target
association in the application flow using mocked records.

The loader at `src/pages/ShipmentForm.jsx` has no response-identity or cleanup
guard. It resets the header and lines only for a new order, applies the saved
header before awaiting its lines and clears loading in an uncaught
`Promise.all(...).finally(...)`. A subsequent saved-order navigation also
does not set fetching back to true.

## Save outcome findings

Eight diagnostics exercised the actual frozen React form and Shipping helpers
with controlled timers and fictional operation acknowledgements. The financial
upsert and navigation boundaries recorded invocations.

| Scenario | Observed result |
|---|---|
| Immediate success | Header and lines complete before financial invocation and navigation |
| Header rejects quickly, lines succeed | Error is visible and navigation/upsert are blocked, but the lines have completed |
| Lines reject quickly, header succeeds | Error is visible and navigation/upsert are blocked, but the header has completed |
| Both finish before 6,000 ms | The form waits for both before proceeding |
| Writes remain pending at 6,000 ms, then succeed | Upsert and navigation occur at the timeout before completion |
| Header rejects after timeout, lines succeed | Prior navigation/upsert remain and no inline error appears |
| Header succeeds, lines reject after timeout | Prior navigation/upsert remain and no inline error appears |
| Existing-line query is pending at timeout, then rejects | The header completes, no line batch is constructed, and upsert/navigation still occur |

`raceWrite` deliberately allows progress after six seconds and catches later
rejections. Its boolean result is discarded by the caller. Header update and
line reconciliation are separate parallel operations. The latter first awaits
an existing-line query before constructing its batch. The timeout therefore
does not establish that both operations have entered the write queue.

These fixtures characterize application control flow and modeled completion
outcomes. Firestore offline-cache durability and actual Postgres receipt need
separate SDK/emulator verification before a save redesign is chosen.

## Repair order

1. Correct order-loading isolation first. Scope loaded state to the route,
   ignore abandoned responses, apply a matching header/line pair, and show
   missing/read-error states that block editing until a valid order loads.
   Include Retry and tests for saved-to-saved and saved-to-new navigation.
2. Review header/line write consistency and pending-save feedback together.
   Evaluate a single batch after the existing-line read, and define observable
   pending, committed and rejected outcomes while preserving the required
   offline workflow. Verify financial-index timing with those outcomes.
3. Run the relevant financial/stock regressions and normal exact-SHA CI,
   candidate and production role gates for any authorized runtime correction.
   Financial and number-allocation verification uses fictional records.
