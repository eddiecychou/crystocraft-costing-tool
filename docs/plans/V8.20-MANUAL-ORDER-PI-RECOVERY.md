## Operator workflow

- Open New Order or Import PI as usual. The editor URL identifies one request for the signed-in operator. The first valid Create saves the reviewed header, lines and original-file identity. Typing alone does not save a draft.
- If confirmation is lost, reopen the same URL or choose **Shipping → My saved order requests**. A prepared request shows its customer, PO, total, line items and original filename. **Resume saved request** completes it. **Open saved order** opens the order when creation has already succeeded.
- If the tab closed before the original PI finished uploading, select the same original when prompted. A completed upload is reused even after the tab closes. A different file cannot complete that request.
- **Start a separate order** creates a fresh request and keeps the customer from a customer-specific entry. Independent sales can have identical details. The ordinary URL for New Order always starts a fresh request.

## Data and permissions

The Shipping endpoint binds the request to the caller's Firebase UID and verifies the login and Shipping permission. Automatic SO issuance also rechecks Quotes permission inside the transaction. A supplied SO is retained. The request and its line documents are private to the service at `shipping_create_operators/{uid}/requests/{requestId}`. The operator can retrieve them only through the authorized endpoint. The completed order retains the usual customer-history access rules.

Preparation freezes the normalized payload, original hash and intended order ID. Lines are stored in separate documents. Commit writes the order, the lines, the optional SO counter and the receipt together. Both the order and receipt carry the same server timestamp. A replay returns that order, or shows a review error if the saved target was removed or replaced. The service derives totals and uses the existing Shipping validation, numeric precision and SO series. [Request repository](../../netlify/functions/lib/orderCreateRequests.js) · [Authenticated endpoint](../../netlify/functions/shipping-order-request.js)

The file key is `shipping_pi_originals/{uid}/{requestId}/{sha256}`. The Storage rule permits the owning Shipping operator to create the object for the matching prepared file. The server checks its size, actual SHA-256 and Storage generation before linking it. The saved order retains the original name and existing source-file URL shape. ## Verification and release boundary

The unit tests cover field preservation, validation, URL identity and endpoint access. The emulator suite uses the current Firestore and Storage rules with real transactions, server readback and denied customer access. Cases include a PI with 360 lines and over 1 MiB of line descriptions, two tabs submitting one request, PI byte-for-byte download and a removed order. The Chrome fixture runs the actual editor and authorized handler with an isolated local login and fictional extraction response.

The final local build passed all 1,133 prebuild tests. Eight Firebase emulator tests passed, including concurrent uploads and denial of overwrite, deletion and customer access. Five native Chrome scenarios passed. In the interrupted-upload case, closing the tab and resuming used the exact same stored generation, issued one order and downloaded the original bytes. The check for undefined identifiers also passed. Logs are in the local, git-ignored `qa/out/sh07-manual/` directory.

From a built checkout, run the following with Node 22, Java 21, Firebase CLI and the repo's local Chrome QA setup. Each emulator command uses its own fictional project.

```sh
npm run test:order-create
npm run build
firebase emulators:exec --only firestore,storage --project demo-sh07-manual 'node --test qa/order-create-emulator.mjs'
firebase emulators:exec --only firestore,storage --project demo-sh07-manual-browser 'node qa/order-create-browser.mjs'
```
