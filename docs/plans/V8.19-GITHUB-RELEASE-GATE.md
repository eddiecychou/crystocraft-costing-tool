# V8.19 GitHub checks before deployment

25 October 2026. Owner-requested release policy and build guard. This change
configures future releases; it does not publish a new application bundle.

## Before and after

Previously GitHub and Netlify ran independently after a push. The summary-status
release published while customer-merge-emulator later failed because its workspace
fixture replaced the new hook with null. Local prebuild and live role checks did
not cover that fixture. Both GitHub jobs are now required on the exact commit
before any candidate/production deployment; existing fresh admin/customer checks
remain after that CI gate.

scripts/check-release-ci.mjs verifies a clean committed checkout and matching
COMMIT_REF, then reads the latest run of Product search regressions for that SHA
from this repository and the current attempt's job list. Both product-search and
customer-merge-emulator must be completed/successful. An older success cannot
mask a newer failure/pending run. Missing, skipped, cancelled, malformed, wrong-SHA,
wrong-repository, inaccessible/rate-limited/network-error results fail closed.
--wait polls every 30 seconds for at most 15 minutes; known failures stop at once.

Netlify's build command is now npm run release:ci -- --wait && npm run build.
Normal Git/CLI builds cannot reach the build step if CI fails. A direct prebuilt
--no-build/API upload skips build commands, so the mandatory release workflow also
requires an immediate explicit check before those uploads. Release commands and
CI-first [skip netlify] pushes are in docs/skills/RELEASE-WORKFLOW.md and CLAUDE.md.
No security domains, credentials, rules, UI, cached summaries or task data change.

The GitHub workflow runs on every push/PR to avoid an exact release commit lacking
checks because only configuration or documentation changed. Its test:release-ci
step and prebuild test the checker with fictional GitHub responses; they do not
run the live preflight inside the unfinished workflow.
