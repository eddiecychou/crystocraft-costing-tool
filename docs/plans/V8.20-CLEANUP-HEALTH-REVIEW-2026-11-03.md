## Confirmed findings

### 1. New regression: saved invoices can reject matching edited amounts

Priority: fix before further extraction. Introduced by 159c4d8, the separate
Woo runtime repair, rather than a presentation move.

Fictional actual-form reproduction: start with a saved line total and Accounting
Total of 100. Change both to 200, leaving adjustment reason blank. The displayed
amounts agree and the reason input is absent. Before the Woo repair (43073fc),
Save produces one order write and one financial-index write. Current source
produces neither.

ShipmentForm loads the saved total_amount into header at line 180, then passes
that header to validateOrder at line 712. The stored-record accounting check in
shipping.js compares the edited accounting_total with the old saved total_amount,
not the current line-derived value. The later live-total guard never runs.
This can affect saved invoices across channels, not only Woo orders.

Repair direction: keep the recorded Woo checkout amount available for allocation,
but validate form saves against current computed amounts. Preserve stored-record
audit validation and genuine adjustment-reason requirements. Test edited line
quantity/price, discount, matching/differing accounting totals, reason/blank,
saved/unsaved, Woo/non-Woo and save/reopen; retain all payout/unknown-total guards.

### 2. Older defect: edit-form save errors are invisible

Priority: include in the same bounded save-path correction. Both the pre-repair
and current form reproduce a rejected fictional save without displaying its
error. extractError is rendered only inside the import-only card at
ShipmentForm.jsx:892–913; that card is absent during editing, direct invoicing
and quote-prefilled creation. Thus the new validation regression can look like
a silent Save Changes no-op.

Repair direction: expose validation/write errors beside submission controls in
every form mode, retaining unsaved input and existing write boundaries. Exercise
actual rejected saves and visible feedback, rather than allocation errors alone.

The two actual-page assertions have current results 0/2 and baseline results
1/2. These expected failures demonstrate defects; they are not green regression
results. All writes/providers are fictional and unexpected network is rejected.

### 3. Older defects: customer navigation can show stale data and collapse state

Priority: repair customer navigation isolation before another extraction.
An actual CustomerDetail/Router test starts a delayed read for customer A, then
navigates to B and completes B's read. The heading correctly shows B. Completing
the old A read replaces it with A while the route remains /customers/fictional-B.
The entire 37-line loader is byte-identical to pre-cleanup ee3e32c, so this is
pre-existing. The reproduction proves a read/render mismatch only; it invokes
no save handler and does not prove a cross-customer write.

CustomerCollapsible.jsx:20 initializes collapsed once from storageKey. When the
same component instance changes from customer A to B, B's stored preference is
not read. With A collapsed and B saved open, B remains collapsed. The extracted
original implementation before CRM cleanup reproduces the same behavior.
App.jsx reuses CustomerDetail for /customers/:id. Existing component coverage
remounts between customers, so it misses this transition.

Repair direction: guard delayed loader results by current customer identity and
reset/isolate page state on navigation. Test delayed A→B responses, reverse
completion, missing/error results and same-instance A→B→A navigation. Isolate
collapse state by customer/section, retaining saved/default preferences and
reload behavior. Existing remount-only coverage does not test this boundary.
