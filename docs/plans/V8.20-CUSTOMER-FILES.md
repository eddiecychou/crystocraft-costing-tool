## Contract before implementation

- Dedicated `customers/{customerId}/files/{fileId}` metadata and private
  `customer-files/{storageCustomerId}/{sha256}/` originals/derivatives. Never
  place cards in `assets`, product images or marketing collections.
- Admin or staff with the `customers` module only. Backend checks fresh Firebase
  identity/profile for every operation. Client Storage access is denied entirely;
  only the authenticated backend reads/writes this prefix. Metadata client reads
  are internal; all client writes are denied. Do not mint/store Firebase download
  tokens, signed read URLs or public links.
- Original bytes/filename, SHA256, MIME/size, company ownership, existing contact
  IDs, category, card front/back/set, title/notes/source/referrer and server upload
  time. Metadata edits use revision checks. Parent contacts/notes/IDs and marketing
  preferences are never written. No OCR, contact creation/merging or outreach.
- Multiple JPEG/PNG/WebP/GIF/PDF originals, up to 20 MiB each. Small authenticated
  binary chunks keep requests/downloads below Netlify buffered binary limits
  ([official limits](https://docs.netlify.com/build/functions/configuration/)).
  Hash-based identities make interrupted retries recover the same upload. Visible
  failures retain files for retry; thumbnail failure cannot discard an original.
- Separate image/PDF-first-page thumbnails, generated locally. PDF.js stays local
  ([Mozilla documentation](https://mozilla.github.io/pdf.js/getting_started/)); no
  Office Online/public viewer. Preview and original download authenticate every
  byte request; the browser validates the complete original hash before use.
- Existing customer merge must carry files and remap existing contact links,
  retain immutable storage provenance and preserve collisions. No live merge.

## Implementation ownership and lessons

- `CustomerFiles.jsx` owns listing, explicit selection/upload, category filter,
  metadata editing and visible outcomes. `CustomerFileMetadataForm` uses unique,
  explicitly associated labels. `CustomerFileDialog` uses native modal focus
  containment; `CustomerFilePreview` renders only local blobs/canvases.
- `customerFiles.js` reuses `authHeader`, sends explicitly typed binary chunks,
  checks original SHA256 before preview/download and creates temporary native
  download anchors/object URLs. Closing/changing company aborts outstanding work.
  Duplicate/resumed uploads preserve reserved metadata and visibly identify it;
  descriptor changes go through revision-checked Edit details.
- `customerFilesModel.js` owns enums, sizes, saved-contact-ID validation, immutable
  storage provenance and RFC 5987 filename headers. Do not use `normalizeCustomer`
  to generate new contact IDs during a file association.
- The Node handler/repository reuse Firebase Admin bootstrap, current-profile
  module checks, Firestore transactions and Cloud Storage. Body/type/checksum,
  fixed paths and immutable generation-zero object creates prevent replacement;
  server-only metadata mutation never writes the parent customer or contacts.
- Thumbnail originals stay distinct. PDF.js 6 cleanup belongs to the loading
  task; `openCustomerPdf` exposes a small stable lifecycle wrapper. A thumbnail
  error leaves the original saved and retryable. Never send cards to the public
  Office viewer or replace original images with resized JPEGs.
- The merge protocol carries `files`, remaps contact-ID sets and company linkage,
  retains immutable original storage ownership, preserves collisions/audit and
  reuses its existing lock/retry mechanism. No actual customer merge was run.
- Incomplete uploads remain private and resumable; completed uploads clean up
  their staging chunks. No automatic retention/deletion policy is introduced.
  OCR/extraction is not enabled. Any future extraction must be a review-only
  proposal with a separate explicit contact action, never an upload side effect.
