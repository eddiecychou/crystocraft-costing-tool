# Shipping order creation and retry recovery (SH-07)

**Review and proposed fix · 8 November 2026.** At checkout `cce005a8ec5e90171d9aca483a3c260e76bd7725`, OC can save an order and then offer Create again if the browser misses the confirmation. In fictional Chrome tests, accepting that offer created a second order and SO. Duplicate Order can also leave an issued UC without a copy attached to it. The frequency of either event in production is unknown.

**Give each intended new order a recoverable request before its first upload or allocation.** Reopening that request should offer **Resume** or **Open saved order**. Starting another sale or making another deliberate copy should still produce independent documents.

## What happens today

| Entry point | What one interrupted action produced in the fictional tests |
| --- | --- |
| New Order | Rejection before commit left zero orders and zero counter writes. Retry then created one order. Discarding the response **after** commit made the editor report failure. Clicking Create again saved two orders with two SOs. Repeated submits on the same busy form were already guarded. |
| Back, reload and two tabs | Chrome Back after success and reload after a lost confirmation both opened a blank entry form. Re-entering the details created another order. Two tabs on the same generic New Order URL each saved the identical details, with fictional SO260101 and SO260102. Leaving an in-flight manual Create did respect the user's new page. |
| Import PI / customer’s New PI | The current handler uploads before validating the order. An excessive deposit uploaded the PDF with zero orders. Correction and submission uploaded it a second time. A real Storage upload followed by a rules-rejected Firestore transaction also left an object. After a successful retry, both objects contained the original bytes and the order linked only the second. A lost *successful* confirmation followed by Retry produced two orders with separate file references in the page fixture. |
| Direct Invoice | Losing the order confirmation before the invoice call left the first order without an SI. Retry created a second order and requested an invoice for that second ID only. Neither consumed an SO. If the order was acknowledged and the invoice service alone failed, the form navigated to the existing saved order. Deliberately starting another Direct Invoice raised a separate request against its own order. |
| Duplicate Order | Losing the UC confirmation, or rejecting the order transaction after a successful UC allocation, left one fictional UC unattached to a new order. Retry requested another UC. Losing the *order* confirmation after a successful copy and clicking Duplicate again created two copies with separate UCs and SOs. Two deliberate copies preserved the source and line precision. |
| Leave the list during Duplicate | If the user navigated elsewhere while allocation was pending, its completion navigated them to the copy. The Shipping list handler lacks the mounted-owner check already used by the manual form. |

The manual and Direct form call `createOrderWithLinesAllocatingSo`. It commits header, lines and optional SO counter together but generates a new order reference for each new submission. A true transaction rollback is safe. The form's in-flight flag lasts only for that mount. Duplicate reads the source, requests a UC through the registry, then calls the same order allocator. These are independent writes to PostgreSQL and Firestore. [Shipment form](../../src/pages/ShipmentForm.jsx) · [Shipping list](../../src/pages/Shipping.jsx) · [Order allocator](../../src/shipping.js) · [UC client](../../src/ucRegistry.js) · [UC endpoint](../../netlify/edge-functions/uc.js)

The PI object key uses the current millisecond and original filename. The emulator also confirmed that two uploads to an identical timestamp/name key can replace each other's bytes. This is a conditional collision test. Existing released PI selection and line-matching protections address a different stage of import. ## Proposed implementation order

1. **Manual Create and PI.** Assign a random request ID to the draft and put it in the editor URL before submission. Preserve the customer-prefilled entry. On the first valid submission, persist the reviewed header, normalized lines, file identity and intended order ID in a staff-only request. Store enough information to resume from the list as well as the URL. Retrying the same ID with changed content should show what was already prepared and allow an explicit review or restart. Two independently started drafts may contain identical details.

   Validate the draft before transferring the PI. Use a file ID scoped to the request, keep the original filename, and verify the bytes, object generation and selected file against the saved draft. After a lost upload response, check for the matching object before transferring bytes again. A newly selected replacement gets its own file ID. If the upload never finished and the tab closed, prompt for the same original file. A finished upload should survive navigation and reload. Retain the existing source-file link format on saved orders.

   Have the server commit the order, its lines, any required SO counter and the request result in one Firestore transaction. Replay returns the stored result. A changed request or inconsistent link needs review. Preserve original line precision, current validation, imported JES SO numbers and supported order sizes. Check request-document and transaction size limits with large valid orders before choosing how to store snapshots. After an uncertain response, check status before enabling another submission.

2. **Duplicate Order.** Prioritize this path once the shared request exists because it can issue a financial registry number even when no order is created. Persist the source order, reviewed line snapshot, intended order ID and request ID before allocating a UC. Use a private SQL receipt keyed by that request. Creating the UC and its receipt must be one PostgreSQL transaction. A retry reads the same receipt, then finishes the Firestore order/SO transaction with that UC. A changed or missing source before preparation, a mismatched receipt, or an issued UC with an unfinished order should have a visible recovery state. Never recycle an issued number. Preserve the separate registry Create action used elsewhere.

   In the list, show a pending or completed copy with **Resume** or **Open**. Keep **Make another copy** available for genuine repeat sales, including multiple copies of one source. Completion should respect navigation if the user already left the list.

3. **Initial Direct Invoice.** Use the same recoverable order request with SO allocation disabled. If an invoice still needs issuing, reopen that order and use the existing invoice status, Raise or Resume operation. Persist that follow-up is due so it is discoverable after a closed tab. A supplied SI should keep its existing behavior. Additional, split and reissued invoices continue to use explicit separate invoice operations. [Released invoice recovery](V8.20-INVOICE-RETRY-RECOVERY.md)

The defining distinction is the request ID. PO number, customer, amount, source order and file contents can all legitimately recur. Use the content fingerprint only to detect changes within one request. Give requests a durable lookup that works after the browser loses its local state. Keep draft details and recovery receipts staff-only, and bind access to the authorized operator or an explicit staff recovery permission.

## Compatibility and rollout

- **Permissions.** Retain Shipping access for order creation, the Quotes permission currently required for automatic SO counter access, and UC permission for Duplicate allocation and invoice issuance. A shipping-only staff member can currently save a supplied SO or a Direct order without allocating an SO. Invoice status has a Shipping read gate. Enforce each existing check again server-side when a privileged service performs the write. Customer order history may continue to read eligible saved records. Keep the private draft and operation history outside that readable surface. [Firestore rules](../../firestore.rules) · [Storage rules](../../storage.rules) · [Invoice handler](../../netlify/functions/lib/invoiceRecovery.js)
- **Other writers.** Preserve the released per-quote conversion protocol and its explicit additional-order action. Woo uses its own deterministic order ID. Its real concurrent-import control yielded one order and one line. Inventory operational importers, administrative writers and older client bundles before tightening general-create rules. [Quote conversion contract](V8.20-QUOTE-ORDER-CONVERSION-RECOVERY.md) · [Woo import](../../src/wooImport.js)
- **Migration.** Introduce receipts for new requests only. Keep existing order IDs, lines, invoice history and file URLs readable as stored. Historical duplicate-looking documents and unlinked files require separate evidence and review. Refresh old clients during cutover. An old tab can still submit an unmarked manual-looking order wherever direct client creation remains allowed. Plan and test the final old-client rejection or refresh experience with the identified writers before claiming full protection.
- **Future release.** Each implementation slice needs fictional failure and concurrency tests, including access denial and ordinary new sales. Both required GitHub jobs must pass on the exact candidate commit before deployment. Verify fresh admin and approved-customer access on candidate and production. A UC receipt migration also needs a permissions check and a rollback plan that retains committed receipts and issued numbers. [Repository release workflow](../skills/RELEASE-WORKFLOW.md)

To reproduce the manual case in an isolated demo, enter a line for 1,000 pieces at 1.222. Drop the first Create confirmation *after* the transaction commits, click Create again, and read the orders, lines and SO counter from the server. For PI, select a fictional PDF, enter a deposit above the total, submit, correct the deposit and compare the stored objects with the saved order's source file. For Duplicate, discard the UC response after the registry insert, then retry from the same source and read back both registry rows and the copy. Local harnesses, counts and logs from this review are under the git-ignored `qa/out/general-create-review/`.

**Acceptance for the fix.** One intended submission must yield one order, one set of lines, at most one new SO, one PI object per selected version, and for Duplicate one UC for the copy. Retry after any committed step, Back, reload, a shared draft URL in two tabs, and loss of the invoice hand-off must all converge on that same order. Independent new sales, intentional repeat copies, additional quote orders and split/reissued invoices must continue to produce distinct records. Concurrent edits of an already saved order and financial updates after browser closure remain the following two review topics.

The tests used fictional records only. This review changed repository documentation. It did not audit production records or publish an app, rules or SQL change.
