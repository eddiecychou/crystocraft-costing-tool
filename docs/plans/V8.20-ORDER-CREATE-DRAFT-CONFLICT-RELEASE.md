# Shipping two-tab order draft recovery

When a second tab submits different details for an immutable saved request,
the server returns a draft-conflict code. The tab retains the submitted
header, lines and original PI identity and shows the saved request beside
**Use my draft for a separate order**. This action opens an editable draft
and allocates a new request ID in the browser. Order and number allocation
still require Create. Revisiting the original conflict opens the same
separate request.

The separate draft preserves commercial edits and clears SO, PI, UC, SI
and invoice accounting references for review. The same open tab retains
the original PI. After reload, the draft can be restored from that tab's
session storage and the original file must match its filename, size and hash.
If session storage is unavailable, the open page keeps the draft in memory.

Fictional Chrome and emulator tests verified one order, one request and one
SO after the conflict, no allocation on opening the separate draft, and
exactly two orders and two SOs after explicit Create. Reopening the request
and losing the final acknowledgement caused no additional order or number.
The tests also compared the saved PI bytes and exact saved unit price.
