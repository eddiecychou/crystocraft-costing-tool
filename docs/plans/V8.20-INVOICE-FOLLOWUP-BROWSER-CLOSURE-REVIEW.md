# Invoice follow-up after browser closure

12 November 2026. Review baseline `33f3c64`. The review uses isolated Chrome,
Firestore emulator and disposable loopback PostgreSQL fixtures.

## Current workflow

`invoice-allocation` records one request per intended invoice. PostgreSQL
allocates against that request and saves its receipt. After the order links to
the issued SI and UC, the same server request runs the financial copy and
applicable WooCommerce UC update. Each stage records its result on the invoice
operation. [Existing recovery contract](V8.20-INVOICE-RETRY-RECOVERY.md).

The saved request and order provide Resume. That path can continue the original
operation, and an initial Direct Invoice retry stays pinned to its first
invoice. Source inspection found no scheduled consumer of pending invoice
follow-ups. The other invoice paths remain relevant boundaries. Saving an
already-invoiced order still sends a separate best-effort registry update,
and Sales Invoices Re-sync is an explicit reconciliation workflow.

## Findings from full Chrome shutdown

Each scenario paused the first financial SQL call after the invoice was issued
and linked. The fixture closed the whole Chrome process, then let the real
handler continue through its loopback SQL adapter. The browser and local
stores are real. Authentication, transport faults and timing are controlled
by the fixture. This measures the persisted recovery behavior and does not
model how a hosted function handles a client disconnect or runtime termination.

| Scenario | Persisted result |
| --- | --- |
| In-flight request succeeds after Chrome closes | The local handler finished the financial stage. The original ledger row received its total, and the operation was marked done. |
| Failure before the financial write | The ledger total remained blank and the linked invoice stayed pending after the request ended. Reading status left it pending. A fresh Chrome process reopened the saved request and two tabs retried it. The same invoice was updated once, with one additional audit entry and no additional invoice, UC, order or receipt. |
| Financial write commits and its response is lost | The ledger already held the correct total while the operation remained pending. Two tabs in a new Chrome process completed the same operation. The invoice, UC, order, receipt and audit counts stayed fixed. |
| Write is delayed until after manual review and an intentional split | Starting the split while the first stage was pending returned 409. After an authorized fictional actor marked the first invoice reviewed, the split issued independently. Releasing the delayed financial request wrote the original invoice's previously blank total while its status stayed `manual_review`. The newer split's record and order pointer stayed intact, and the split reused the UC. |

**Pending work needs an operator after a failed request.** A close by itself
did not interrupt the successful local request. Once the server attempt
ended in failure, status and reload only exposed the pending operation. The
financial stage had no independent consumer to retry it. The existing manual
Resume remains safe for the tested same-operation retries.

**Manual review can race a write that already passed its checks.** The handler
checks the order before dispatching SQL. Manual review updates Firestore, and
the SQL update guards the receipt and target row independently of that review.
The later outcome write correctly preserves `manual_review`, but that cannot
undo the ledger write. Close this gap before adding automatic retries.

The 14 existing Chrome scenarios and four new closure scenarios passed.
Another 50 integration cases passed with local Firestore and PostgreSQL:
23 invoice recovery, 10 Direct Invoice, 11 Duplicate Order and six
Shipping follow-up acceptance cases. They confirm that repeat orders and
additional copies remain distinct, split/reissued invoices retain independent
receipts, and a retry does not issue again. They also cover preserving manual
finance edits and WooCommerce zero versus unknown amounts. The four new Chrome
cases characterize current behavior, including the reproduced late write.
Ignored evidence and test harness are in `qa/out/invoice-followup-review/`
(`browser.log`, `closure-evidence.json`, `browser-review.mjs`,
`emulator.log`).

## Proposed first fix

1. **Coordinate in-flight work with finance decisions.** Use a claim to
   avoid overlapping attempts and validate it at the SQL write boundary.
   Fence manual review and supersession at the same receipt/stage boundary
   as the write before enabling background retries. A Firestore lease alone
   cannot prevent a delayed SQL
   request from committing after another actor takes over. A candidate
   design is to serialize the guarded write and stage closure on the same
   SQL receipt row, with a generation checked at mutation time. Manual
   review should acknowledge any write that already committed before closure.
   Persist the closure and its outcome in SQL. If Firestore confirmation is
   interrupted, reconcile that exact outcome before allowing the next invoice
   operation.
   Recheck changes to order references, customer/currency and financial values
   at execution. Preserve the receipt's row ownership and compare-before-write
   safeguards. The implementation plan should account for any previous writer
   that could bypass the new write guard during rollout.
2. **Schedule only work for an issued and linked invoice.** In the server
   transaction that links the operation, record discoverable pending work keyed
   by the operation ID and stage. Carry the exact order, SI, UC and SQL receipt
   identity. Use the existing synchronous attempt for the normal screen flow
   and let a bounded server worker retry outstanding work. Share the same
   stage claim and completion rules between both paths. The worker should
   have a dedicated follow-up entry point. The general Resume endpoint can
   follow the order's current operation and can allocate while a request
   lacks a result, so it is unsuitable as a worker entry point.
3. **Retry only safe failures.** Use backoff and a finite attempt budget for
   transient failures and uncertain acknowledgments. Confirm an already
   applied result against the exact receipt and preserve its audit history.
   Changed ownership, current references, independently edited financial
   rows, unresolved WooCommerce totals and incompatible reused UC records
   require a visible review state. Preserve zero and unknown as distinct
   values. Record initiating and executing identities separately.
4. **Preserve explicit new work.** Each repeat order, split and reissue keeps
   its own existing request and receipt rules. Deduplicate only the same
   operation and stage. Keep manual Resume and reviewed outcomes usable.
   Keep already-issued history and use separately approved handling for
   existing pending records, pre-link recovery and ordinary order-save
   financial synchronization.

Use the existing server-side scheduled retry pattern as a starting point.
Size the batch and retry intervals after testing realistic concurrency. Add
tests for two workers, a user retry racing the worker, a killed worker,
completion acknowledgment loss, source edits and manual review during a
delayed write. Assert the exact SQL row, receipt, reference and audit counts
for each operation. Review the queue/index, grants and recovery policy before
implementing or releasing it.
