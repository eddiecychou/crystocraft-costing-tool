# V8.19 Crystal Components Implementation Plan

19 October 2026. Phases 1–2 are released as V8.19; the Firebase swatch migration and OC uploader
are complete and verified on production.
See [migration and release evidence](V8.19-SWATCH-MIGRATION-RELEASE.md) for the
current backup, rules, import and application deployment states. Phases 3–4
remain planned; the full third catalogue is not part of this first delivery.

## Business outcome and agreed scope

Create **Crystocraft Crystal Components**, a third customer catalogue alongside
Crystocraft Range and Corporate Gifts. Use **Crystal Components** in navigation.
The first release is **enquiry first**, as confirmed by the owner on 19 October:
show specifications, photographs, samples and availability; add approved selling
prices later where appropriate. Crystal fabric remains project-quoted from real
drawings and application details. An absent price must never appear as zero or free.

The range covers the owner's producible cut-crystal components, crystal fabrics
and surfaces, and clearly identified original Swarovski/Strass stock for clearance.
Existing tooling and confirmed production capabilities determine what is offered.
The Swarovski brochures are reference material; their full assortment, images,
specifications and claimed capabilities are not an import list for Crystocraft.

**Firebase Storage will hold swatch images. Firestore will hold their records.**
OC will manage uploads and descriptions without stone-pitch calibration. The
catalogue and sample workflow will operate without Fly. The existing renderer
remains a separate parked prototype, with its assets preserved.

This replaces the historical requirement in `Crystal_Fabric_Studio_Spec.md` that
the Fly registry be the catalogue's sole photo store. It does not restart the
unfinished renderer or authorize deleting its volume.

## Catalogue organisation

| Customer view | Initial content | Supply treatment |
| --- | --- | --- |
| Cut Crystal Components | Confirmed octagon, heart and pear products, then other confirmed tooled shapes | Existing stock and/or made to order |
| Crystal Fabrics and Surfaces | Crystal Fabric, Fine Rock and Rock; real colour/backing samples and confirmed customization options | Enquire for the required material, application and quantity |
| Original Swarovski Stock | Owner-identified original Swarovski/Strass articles | Stock only, no replenishment; sold-out state retained |

Original Swarovski Stock is a clearance view across product families. Brand,
product family, publication and replenishment policy are separate attributes.
An original Swarovski item is never merged with its Crystocraft alternative,
even when size, colour or reference number resembles it. A stock-only item does
not imply that Swarovski has discontinued that article worldwide.

Every listing has its own Crystocraft catalogue identity and may carry a clearly
labelled comparison/reference number. Record only confirmed dimensions, holes,
colours, material, backing, application method, unit, MOQ and lead time. Crystal
colour and backing colour are separate choices. Show only valid combinations.

### Crystal fabric quoting: keep the customer flow simple

Owner clarification, 19 October 2026: area, adhesive/no adhesive and added effects
inform an estimate, but the final crystal fabric quote should be based on the
actual drawing and intended application. Keep these as internal estimating
considerations; no customer area-price calculator or automatic effects pricing
is planned. Later approved catalogue prices do not replace this project review.

The customer selects a reference swatch and sends a drawing/reference file,
intended application and quantity. Let them add dimensions, adhesive preference
and effects in brief optional notes, with "not sure" acceptable. Early enquiries
can proceed without a finished drawing; staff obtain the required drawing and
application details before confirming the project quote. Do not create a variant
for every custom outline, area or effect.

Reuse the existing enquiry/CRM attachment handling where suitable. Drawings and
project notes belong to the private customer enquiry, not the published sample
library. Retain the reviewed drawing revision and agreed specification with the
quote so a later drawing change does not silently change what was priced.

## Implementation sequence

### Phase 1 Preserve assets and prepare the transfer

1. Refresh upstream and preserve unrelated work. Bump `APP_VERSION` to **V8.19**
   in the first implementation commit; this planning change leaves the app alone.
2. Confirm the existing Firebase project, default database edition and Storage
   bucket before implementing the new records/rules. Use the existing project;
   no new database, account or bucket is proposed. The database metadata read
   timed out during planning, so this remains an implementation preflight check.
3. Export the live registry and all files under its data directories, including
   templates, outlines, graphics and zones, to a private backup outside Git.
   Record SHA256, byte size, image dimensions, original path and source registry
   hash. Compare the source inventory again at export completion.
4. Export existing swatch-reference notes and identify saved sample/customizer
   references that depend on colour names or filenames. Preserve original IDs.
5. Produce a dry-run manifest: registered sample mappings, extra unregistered
   files, missing/invalid files, destination paths and any identity collisions.

**Completion:** a verified backup and reviewable manifest cover the current live
library. No migration writes or publication changes occur in this phase.

### Phase 2 Put swatches in Firebase and simplify management

Build the records, access rules, uploader and migration review before switching
the existing pages. Reuse the existing `swatch` staff capability and retain the
Swatch Library entry for this first delivery. Relabel it Crystal Components when
the third catalogue is added; do not rewrite users' module lists. Supply access
continues to govern stock and supplier records separately.

Use these proposed stores:

| Store | Responsibility |
| --- | --- |
| `crystal_swatches/{sampleId}` | Customer-safe photographed sample identity, colour, actual/legacy material style, backing label, publication, media paths and revision |
| `crystal_swatch_notes/{colourName}` | Existing colour-level legacy references, retained through a compatibility link so notes are not duplicated or silently orphaned |
| `crystal_migration_runs/{runId}` | Private manifest, source/destination hashes, mappings, progress, verification and conflict results |
| Storage `crystal-swatches/{sampleId}/{contentHash}/original.jpg` | Exact migrated source bytes, immutable per revision |
| Storage under the same sample/revision | Derived display images and thumbnails; originals remain intact |

Derive each imported sample ID deterministically from its exact legacy colour,
style and backing tuple; use a collision-resistant hash rather than a lossy slug.
Changing a label later does not change identity. Keep renderer calibration and
source provenance in the private migration record for possible future reuse.
New uploads do not require renderer calibration.

The OC editor supports upload, real-photo preview, colour, material style,
backing, display order, reference notes and publication/archive controls. Preserve
aspect ratio, permit intentional manual crop, and keep original bytes. Uploads
are drafts until published. Do not generate missing swatches or recolour one
photo to represent an unphotographed material/backing combination.

Use an admin-reviewed migration screen: inspect the manifest, apply the reviewed
batch, and read back results. Preserve all 165 observed source image files in the
backup; import only current registered samples into the customer library. Extra
files remain private until reviewed. Migration defaults to dry run. A live apply
requires the exact reviewed manifest; if a one-off script is necessary, follow
`ARCHITECTURE-RULES.md` section 0's file-review requirement.

Uploads use atomic create-only checks and immutable destination
paths. A retry verifies existing bytes and metadata before marking a file done.
An unexpected existing object or changed source/target record is a conflict,
not permission to overwrite. Register each sample only after its image verifies;
keep progress resumable across partial failures. Storage and Firestore are not
one transaction, so expose pending, verified and failed states explicitly.

**Completion:** current registered samples have matching source/destination
hashes and metadata, repeat runs create no duplicates, notes remain linked, and
both OC and customer swatch pages read Firebase only. Keep colour grouping for
browsing; 156 photographs do not become 156 sellable products.

### Phase 3 Build the component catalogue and inventory links

Proposed catalogue stores:

| Store | Responsibility |
| --- | --- |
| `crystal_products/{productId}` | Customer-safe family, name/code, description, brand/origin, replenishment policy, publication, safe specifications and hero reference |
| `crystal_products/{productId}/variants/{variantId}` | Stable identity for each real orderable combination: size, colour/effect, holes, unit and confirmed options |
| `crystal_products/{productId}/images/{imageId}` | Real product/media references, ordering, alt text and publication |
| `crystal_product_private/{productId}` | Internal supply notes and approved per-variant inventory mappings; no customer read access |
| Storage `crystal-products/{productId}/...` | Product photographs and revisions, with publication-aware access |

A material product may reference several reusable swatches. Preserve the
difference between a photographed example and an orderable variant. Avoid
creating the full size/colour/backing cross product automatically. Start with
the real existing octagon, heart and pear range and reviewed original stock.
Do not import a generic website Customized Product placeholder as a real SKU.

Loose crystals already used in figurines link to the existing `crystals/{id}`
inventory and movement ledger. Other products link to their verified existing
inventory record where one exists. New inventory items are created through the
normal supply workflow only when no matching physical item exists; unresolved
matches remain unlinked with availability unconfirmed. No name-based auto-merge.

Do not copy balances into a second editable catalogue stock field. The same
physical crystal sold externally and consumed in figurines must use one ledger.
Map catalogue units to stock units explicitly: pieces, sheets, lengths and
areas cannot be interchanged without an approved conversion. Never count a
photographed swatch as a unit of sellable stock.

For original stock, review article, colour/effect, size, holes, quantity, condition
and provenance. Link or establish its canonical stock item and opening count
through a reviewed stocktake movement. No guessed quantity or duplicate opening
balance. Availability is on-hand less reservations. Enquiries do not reserve
stock; check availability again when an operator confirms/reserves an order.

Provide a customer-safe server projection for availability, following the
existing `customer-availability` pattern. It resolves private stock mappings and
returns only approved availability/lead information. Customers never read
`crystals`, movements, supplier costs or private mapping documents directly.

Stock-only confirmation must reject insufficient availability atomically.
The shared ledger already supports transactions/idempotency but its generic
`postMovement` is not an oversell guard. Review all reservation paths touching
linked items, including figurine use; the direct-sale check alone cannot protect
a shared balance if another writer can over-reserve it. Reuse safe movement
semantics with stable per-order event IDs, and test retry, release, cancellation
and reversal. Do not deduct once for a component sale and again as figurine BOM
consumption. Until this path passes, keep stock handling operator-reviewed and
do not claim automated fulfilment.

**Completion:** reviewed products/variants have real media and valid supply
links, genuine stock and alternatives remain distinct, and both usage routes
share the canonical inventory without duplicate consumption.

### Phase 4 Add the customer catalogue and enquiry flow

Add `/crystal-components` in OC and `/shop/crystal-components` in the portal,
with product details and a swatch/material view. Preserve old `/swatch-library`
and `/shop/swatches` links through compatible redirects/aliases. Reuse the
existing design language and image-carousel behaviour; do not clone supplier
or costing screens into the portal.

Customer functions:

- Browse Cut Crystal Components, Crystal Fabrics and Surfaces, and Original
  Swarovski Stock; filter by relevant shape, size, colour and supply status.
- Read confirmed specifications and safe availability; view original product
  photographs and sample/backing combinations at useful magnification.
- Add a component enquiry or physical sample request with exact variant/sample,
  backing, quantity, unit, intended application and notes.
- For crystal fabric, provide a simple drawing/reference attachment and project
  brief following the quoting approach above; staff review the final quote.
- Keep favourites and download a catalogue PDF for the selected published range.
  PDFs contain photographs, identifiers and specifications; selling prices are
  omitted at launch. Do not reproduce the Swarovski reference PDFs as our offer.

Extend the existing enquiry cart and serializer together. `EnquiryPage.jsx`
currently explicitly selects fields, so merely attaching a new field to a cart
item would lose it on submission. Cart identity must distinguish size, material
and backing. Preserve old `swatch_sample` cart entries; resolve legacy names
through the migration map or ask the customer to reselect, never substitute a
different sample. Enquiry lines snapshot their descriptions and chosen options
so later catalogue changes cannot rewrite submitted requests.

Launch with **Request a quote**, not a zero price, checkout or automatic sales
order. Reuse CRM enquiry handling and existing reviewed custom quote lines.
Where a quote/order adapter is added, preserve unit, source collection, variant,
cost and description snapshots correctly and update `shipping.js`'s `normLine`
allowlist. A new source must not fall through a corporate/range default and be
mislabelled. Preserve the existing corp-gift margin and per-customer pricing
contract; do not add a typed universal price as a shortcut.

Place Crystal Components beside the other two catalogues. Keep the existing
mobile navigation within its five-slot layout rather than squeezing in another
bottom-bar item. Generic browse content remains within the current approved
customer portal boundary. Existing public WordPress SEO pages/URLs stay intact
and can link to the new catalogue after release; public SEO/content work and
automatic WordPress publishing are outside this implementation.

**Completion:** an actual product enquiry and exact physical sample request can
be reviewed end to end, PDFs contain only published customer-safe data, and old
links/carts retain a clear path forward.

### Phase 5 Verify and switch over

Test each phase before broadening it. Use emulator/fictional data for mutations;
no live catalogue edits or stock movements as QA fixtures.

| Area | Required proof |
| --- | --- |
| Migration | Fresh inventory; hashes for every registered image; all extra files preserved; retry/conflict/partial-failure coverage; source changes detected |
| Access | Anonymous/pending denied; approved customers read published samples/products only; cannot read drafts, archives, supplier data, stock mappings or another customer's work |
| Staff | `swatch` manages catalogue/sample content; `supply` manages inventory; no implicit pricing or customer-data grant |
| Images | Uploaded bytes, type/size validation, original retention, replacement revision, authenticated reads, refresh, failed-image state and caching |
| Catalogue | Only actual variant combinations; precise sample/backing identity; enquiry-first prices never shown as zero/free |
| Crystal fabric quotes | Simple drawing/application brief; adhesive/effects can be unspecified; private attachments remain scoped to the enquiry; reviewed drawing revision retained with quote; no automatic area price |
| Stock | Shared crystal used by figurine and direct sale; insufficient-stock/concurrency/retry/release/reversal cases; no double issue |
| Documents | Enquiry and quote/order snapshots retain source/options/units; PDF render and image inspection at realistic product counts |
| UI | Actual OC/portal pages at 320, 375, 414 and 1280 px; loading, empty, error, archived and missing-record states |
| Release | Full relevant checks, rules emulator, candidate and production fresh admin plus approved-customer sign-ins and evidence per `RELEASE-WORKFLOW.md` |

Rollout order: deploy additive reviewed rules; stage and verify the Firebase
copy; verify the exact candidate against the staged catalogue; switch catalogue
reads only after verification; repeat both role checks on production. Record
rules, app, data migration and source commit as separate release states.

Do not leave Fly and Firebase as two active catalogue editors. During the final
export/cutover use a brief agreed pause on Fly edits, compare source hashes, then
make OC the catalogue editor. Retain the source archive and old renderer files;
new OC uploads do not silently sync back to the renderer. After cutover, a
temporary Fly read fallback is no longer the main data path. If needed during
transition it must be explicitly shown, never mask a failed migration.

Turning Fly off is a later reviewed action after auditing remaining customizer,
template, saved-design and image dependencies. This plan's migration does not
require deleting the Fly service or its volume.

## Access and image delivery details

Published catalogue metadata must be customer-safe at document level; Firestore
does not redact selected fields. Store internal costs, stock mappings and
migration metadata separately, with explicit rules on each new top-level path.
Queries must constrain publication as required by the rules; hiding a draft in
the UI is not access control.

Storage rules must mirror metadata publication and role checks. Fetch protected
images through authenticated Storage reads or a narrowly authenticated image
endpoint, with appropriate browser CORS and object-URL caching/revocation.
Do not use permanent download-token URLs as a substitute for access control.
Use immutable revision paths and private browser caching, extending the existing
catalogue image policy deliberately. A visibility change must affect subsequent
reads. Sample migration retains the current approved-customer audience; archive
and unreviewed content are not newly exposed to customers or anonymous visitors.

## First implementation deliverable

Start with **Phases 1 and 2: a verified export, Firebase swatch storage, an OC
uploader and compatible existing swatch pages**. Complete that smaller migration
before adding the full components catalogue. This makes the owner's existing
photography useful immediately and removes the Fly upload/calibration dependency
without waiting for inventory and new catalogue screens.

release evidence linked above. Fly remains intact; there is no renderer restart
