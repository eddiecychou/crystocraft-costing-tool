# Invoice follow-up review guard and retries

The [fictional review](V8.20-INVOICE-FOLLOWUP-BROWSER-CLOSURE-REVIEW.md)
reproduced both stranded follow-ups and a delayed write after manual review
and a split. Implementation tested the database guard before adding the
scheduled worker.

## Behavior and cutover

- The [migration](../../erp-sync/migrations/20261112011943_guard_invoice_followup_review.sql)
  preserves the existing financial/UC write function and moves it behind
  service-only wrappers. Review and writes lock the same SQL receipt. If review
  commits first, a delayed write returns the saved review. If a write commits
  first, review records the stage that already applied. SQL persists the review
  actor, reason and timestamp before Firestore records completion.
- Linking an issued invoice and creating its pending stage jobs use one
  Firestore transaction. The foreground endpoint and scheduled function share
  claims. The SQL write checks the claim deadline after locking the receipt.
  A worker that stops leaves a claim that can expire. The queue is server-only
  under the current Firestore rules and uses a standard collection index.
- The [scheduled function](../../netlify/functions/invoice-followup-retry.js)
  runs each minute and considers up to three due stages per invocation.
  Automatic attempts are limited to four with backoff. Changed references or
  order revisions, separately edited ledger rows and unknown Woo amounts
  pause automatic work for review. Manual Resume remains available. The worker
  follows the exact linked operation and stage and has no allocation action.
  SQL continues to check row identity and compare before writing. Firestore
  order saves and manual Re-sync remain their separate workflows.
- Only newly linked receipts enter the queue. Older pending operations retain
  foreground Resume. Repeat orders, splits and reissues retain separate
  operations. A deliberately reused UC is still subject to the existing
  compare-before-write and review rules.

The migration validates the current function body and owner, uses an additive
receipt change, and refreshes PostgREST. Deploy the approved candidate after
the migration. The existing four-argument RPC stays available to old server
invocations and obeys any SQL-recorded review. The production OC URL must use
the new backend for manual review to record a SQL closure. Refresh old open
tabs after deployment. Avoid using archived deploy URLs for financial work.

## Fictional verification

The guard passed 18 isolated Chrome scenarios before the worker was added.
The same 18 passed afterward, including a complete Chrome shutdown, lost SQL
acknowledgment, and the delayed write after manual review and a split. The old
invoice remained untouched after review, and the split kept its own record.
Local PostgreSQL tests covered both commit orderings and expired claims.

The combined unit and PostgreSQL suite passed 26 cases. Another 55 integration
cases passed against Firestore emulator and disposable PostgreSQL. Worker
tests covered competing worker/foreground attempts, expiry, lost write or
review acknowledgment, changed references and the retry limit. The tests
asserted invoice, UC, receipt and audit counts, and checked that admin, staff
and customer clients cannot read or alter the private queue.
