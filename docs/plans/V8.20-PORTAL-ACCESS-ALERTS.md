# Portal account access alerts

**Released 9 November 2026.** The email and Google self-application handlers saved a pending profile and invitation, then returned without notifying the owner. Portal opened on approved customers. Production had five pending customer accounts at the time of the review. Its Netlify Functions configuration included both `RESEND_API_KEY` and `MAIL_FROM`.

## What the owner sees

A new access application triggers a transactional Resend email to **eddie@uart.com.hk** with the applicant’s company, contact, email address and a direct link to review their OC account. The server fixes the recipient. Both the email and Google application forms use this flow, including an application submitted against an existing invitation that still needs approval.

Admins see the pending count on the Portal navigation item and a notice at the top of Portal. **Review requests** opens Accounts on the Pending tab. The count updates when a request is added, approved or removed from pending. Staff with read-only Portal access retain their login activity view. Existing pending applications appear in the count. Only new applications enqueue an email.

## Delivery and recovery

The application transaction saves the pending profile, invitation and a private mail job together. It attempts delivery immediately after commit. The scheduled Netlify function checks due jobs every five minutes. Concurrent attempts are leased, and retries after uncertain responses reuse the same exact payload and Resend idempotency key. Acceptance requires a provider message ID. The applicant’s access stays pending independently of delivery.

Portal → Invitations shows the admin alert’s status separately from applicant invitation and setup emails. If a response stays uncertain beyond the safe replay window, OC shows **Check Resend**. An admin who confirms the message was never accepted can retry the alert there. Normal retries need no manual action. [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys)

The mail job is private to the server at `portal_access_alerts/{invitationId}`. The invitation holds only its alert status. Normal sign-ins, duplicate applications, honeypots and historical pending records do not send new alerts. The existing follow-up draft, customer linking, pricing and approval actions remain separate. ## Verification and release

Local verification uses fictional applicants, actual Firestore transactions and access rules, simulated Firebase Auth identities, and intercepted Resend responses. It covers both registration methods, pending applications against existing invitations, simultaneous submissions, retry after a lost response, configuration recovery, admin review and denial of client access to jobs. UI tests render the actual sidebar, Portal and Accounts views, including the staff-only login activity case.

```sh
npm run test:portal-followup
firebase emulators:exec --only firestore --project demo-portal-access-alert 'node --test qa/portal-access-alert-emulator.mjs && node --test qa/portal-followup-emulator.mjs'
```

The portal-only checkout passed its production build and all 1,131 prebuild tests. The Firestore emulator passed nine signup alert cases and 22 existing follow-up cases. In Chrome, a fictional email signup generated one intercepted Resend request addressed to the owner. The desktop and mobile counts updated, **Review requests** opened the applicant’s entry, and approving it cleared the count. Local Netlify packaging recognized the five-minute schedule for the retry worker.

No retrospective mail is sent. There is no data migration or Firebase rules change. The two required GitHub jobs must pass for the exact release commit before publishing the app and scheduled worker. A future production check should distinguish a Resend acceptance from delivery to the owner’s inbox. [Repository release workflow](../skills/RELEASE-WORKFLOW.md)
