Status: implemented and locally verified. Not pushed or deployed; no real email,
applicant, approval, CRM record, pricing or security rule has been changed.
Release remains subject to explicit publishing authorization and the existing

## Owner-approved flow

Portal → a pending customer account now has an Application follow-up card directly
below its identity. Request more information opens a short editable template,
addressed to the registered applicant, with sender/reply inbox visible. Save draft
persists without sending; Continue draft reopens it. Send email is an explicit
reviewed action. The card shows Waiting for reply and the sent date/time in Hong
Kong time, plus expandable email history (latest 20 attempts).

Replies arrive in the configured normal inbox. Mark information received is
manual and does not approve access. Link/create the customer and set pricing/
approve separately through the existing account controls. History remains keyed
to this same application UID after customer linking/approval, without copying it
or creating a provisional customer record. The first version does not ingest
replies into this card or automatically detect whether information was received.

## Implementation and boundaries

- `PortalAccountFollowup.jsx`, mounted by the existing admin-only `AccountEdit`,
  owns the compact inline composer/status/history. `portalFollowup.js` supplies
  editable wording in Eddie's style. Empty contact names use Hello rather than
  inventing a person. Draft loading does not call AI or send mail.
- Existing `/api/portal-invite` gains five admin-authenticated actions:
  `get_account_followup`, `save_account_followup_draft`, `send_account_followup`,
  `mark_account_information_received`, `resolve_account_followup`. Its existing
  invitation/setup/approval actions remain separate. The helper rechecks admin
  identity from the database; the actor UID comes from the verified token.
- Server-owned `portal_account_followups/{uid}` stores revision, draft, review
  state, active message and server timestamps/actor. Its `messages/{uuid}` stores
  the frozen provider payload, acceptance state/key, attempt times and audit.
  Existing Firestore rules default-deny browser access, including for the
  applicant and admin client SDK; all access is through the admin API. No rules
  change/deployment is needed. Nothing is added to the self-readable users doc.
- The server derives the recipient from the current users record, checks the
  reviewed address still matches, and permits new drafts/sends only for pending
  non-internal customers. Role/status/customer links and prices are never written.
  Other admins' draft changes reject stale revision saves/sends.
- Mail uses existing Resend credentials and `MAIL_PERSONAL_FROM` (falling back
  to `MAIL_FROM`), with `MAIL_REPLY_TO`/`MAIL_ADMIN` as the reply inbox. Missing
  sender/key/reply configuration disables sending but still permits draft saves.
  Sends are plain text, bounded to a 200-character subject/6,000-character body;
  no arbitrary recipient, CC/BCC, HTML, attachments or password/setup links.

## Interrupted-send recovery

A transaction reserves a UUID and immutable message/key before the provider call;
concurrent clicks/new UUIDs cannot bypass an active attempt or stale revision.
The provider call has a 20-second timeout; a 30-second lease prevents simultaneous
retries. Its final transaction records acceptance without replacing a newer
attempt/result. Sent replay returns the saved history without sending again.

Unconfirmed provider/network results retain the active message and block new
mail. Refresh status reads history; Retry same email reuses the stored payload/
key within 23 hours, shorter than the provider's documented 24-hour retention.
It never creates a fresh key for an uncertain send. After checking provider
acceptance externally, an admin can explicitly record Confirmed sent/not sent
with a separate confirmation and audited resolution; this action sends no mail.
Sent means provider acceptance, not proof of final delivery/opening.

Provider reference: [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys).
The send payload is retained exactly across retries even if sender configuration
changes. No credentials are stored in the follow-up documents or returned to UI.
