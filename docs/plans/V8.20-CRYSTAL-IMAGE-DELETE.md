## Existing methods inspected

- Corporate Gifts: `ProductDetail.jsx` mounts `ImageGallery.jsx`. Its shared
  `ConfirmDialog` asks “Delete this image? This cannot be undone.” The gallery
  removes the Firestore image record, updates the hero when applicable, then
  attempts Storage cleanup. The image operation saves immediately.
- Crystocraft Range: `RangeForm.jsx` removes an entry from `form.gallery` and
  persists it with Save changes. Its separate colour-preview removal also uses
  confirmation. The normal gallery removal does not purge its underlying file.

Crystal photograph operations already save immediately, so use the Corporate
confirmation/record-first/file-cleanup pattern. Keep the existing protected
Firebase media model and require changing/saving a cover before deletion;
Crystal publication requires a valid cover/primary variant and must not be
silently changed by this action.

## Implemented

- `CrystalProductImages.jsx`: Delete image button on each photograph, shared
  Corporate confirmation, cancellation and busy locking. Archive/Restore actions
  and their guidance are removed. Existing archived images remain visible in OC
  and can be published or deleted; no existing record is automatically changed.
- `crystalProducts.js`: revision-checked transaction reads the current parent and
  image; refuses a saved cover, changed image or foreign file path; deletes only
  the selected image record. Cleans up its exact original/display/thumbnail
  paths afterward. Missing files count as already cleaned. Storage failures are
  reported with Retry file cleanup in the current screen, preserving failed
  paths while it remains open. Historical orphan revisions are not bulk purged.
- Image refresh preserves pending catalogue edits and parent revision guards.
  Both selected and saved covers are protected in the UI. The cover selector and
  component save are blocked while image deletion is in progress.
- Existing `ConfirmDialog` gains optional busy handling (default false) and
  dialog semantics. Other callers keep their existing confirmation behaviour.
- Firestore image deletion allows only `swatch` staff/admin and refuses the
  saved cover. Product/variant deletion remains denied. Storage deletion allows
  the same capability only for exact raster paths after that image document has
  been removed. Profile + image lookup stays within Storage's two-document
  cross-service limit. Overwrites/listing, supplier files, swatches and customer
  access boundaries are unchanged.

No data migration, new collection, endpoint or service credential is needed.
No real customer/product/quote record or photograph was deleted during testing.
The app and the two rule files must be released together for Delete to work on
production; a Git/Netlify release alone does not publish Firebase permissions.
Follow the normal exact-SHA two-job gate, authorized rules release and fresh
candidate/production admin/customer verification before publishing.
