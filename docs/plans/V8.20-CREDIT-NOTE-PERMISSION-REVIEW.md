# Credit-note permission review

12 November 2026. Review of the posted credit-note boundary on source `059add1`.
Production evidence comes from read-only catalog and advisor queries. The
proposed grants passed a disposable PostgreSQL test with fictional records.
The initial review preceded implementation. See the implementation section for
the migration, regression coverage and release status.

## Finding

**P1 — credit-note posting and voiding grant execution to `PUBLIC`.** The setup
SQL revokes the named `anon` and `authenticated` grants, but both roles still
inherit execution from `PUBLIC`. The live database has one signature for each
function. Both run as their owner (`postgres`, `SECURITY DEFINER`,
`search_path=public, pg_temp`), and their bodies match the repository. The
functions rely on the gateway for caller authorization and have no role check
of their own. The grants therefore allow the financial operations outside the
gateway's module check, request validation and actor attribution. This review
establishes the exposure through metadata. Historical use is unverified.

| Function | Effective `anon` / `authenticated` | Effective `service_role` | Proposed access |
| --- | --- | --- | --- |
| `allocate_credit_note` (19 arguments) | Execute | Execute | Owner and `service_role` |
| `void_credit_note(bigint,text)` | Execute | Execute | Owner and `service_role` |
| `credit_note_audit_fn()` | Execute | Execute | Owner, with the existing audit trigger still firing |

The third function returns `trigger` and is invoked by `trg_credit_note_audit`.
Its broad grant is unnecessary for OC and separate from the two financial
operations. Both client roles lack direct read/write privileges on the posted
and audit tables and have no privileges on the three credit-note sequences.
Supabase Security Advisor flagged all three functions, and catalog inspection
confirmed the effective grants. [Supabase database function privileges](https://supabase.com/docs/guides/database/functions#function-privileges).

## Caller and workflow inventory

- The credit-note form saves a Firestore draft, posts via `src/creditNotes.js`
  and stores the returned CN number and row ID on the working document. Void
  sends that row ID to the same gateway and then updates the working document.
  The form lists posted credits by original invoice for the over-credit check.
  The register, CSV and print view use Firestore working records.
- `/api/credit-note` is the only tracked caller of the two database functions.
  It verifies Firebase identity and uses `requireModule('credit_notes')`, which
  permits admins and staff assigned that module. Both customer accounts and
  staff without the module are denied. The gateway uses its existing Supabase
  server credential for posting, voiding and filtered reads. It takes the actor
  from the verified identity and requires a reason for accounting adjustments.
- WooCommerce refund staging creates a Firestore draft, then links to the same
  credit-note form for review and posting. It adds no alternate SQL caller.
  The inventory covers tracked code and the live database catalog. Confirm any
  out-of-repository direct SQL integrations before applying the change.

## Proposed fix

1. Apply a single transaction scoped to the three exact function signatures.
   Check that there are no unexpected overloads and that the definitions,
   ownership and security configuration match the reviewed baseline. Revoke
   execution from `PUBLIC`, `anon` and `authenticated`. Retain the explicit
   `service_role` grant on post and void. Keep the audit function's execute
   privilege with the owner and verify trigger-driven audit writes. Check the
   effective privileges before committing so any inherited access or missing
   service access stops the whole change.
2. Update the canonical setup script so function creation and final grants
   commit together. Apply the narrow grant migration to an existing database.
   Preserve function bodies, signatures, trigger, table and sequence grants,
   numbering, financial values and Firebase permissions. Keep draft, post,
   void, filtered reads, CSV, print and WooCommerce draft staging on their
   existing paths. Treat posting recovery after a lost response as a separate
   question from execution permissions.
3. Follow the repository release workflow for the SQL-only change. Refresh
   the PostgREST schema cache after application, then read back definitions,
   effective grants and advisors. Use harmless input validation and a
   nonmatching list filter for any live gateway checks. Exercise posting and
   voiding with fictional records in a disposable database.

## Fictional verification plan

Check the baseline and proposed grants in PostgreSQL. Compare function and
trigger definitions, posted rows, audit rows, sequences and relation ACLs
immediately before and after applying the proposed grants. Exercise the real
credit-note client and gateway with fictional identities and local SQL. Cover
administrator and Credit Notes staff access, customer and other-staff denial,
posting and sequential CN numbers, UC lookup and legacy references, filtered
reads, a rejected adjustment, and void with a repeat request and preserved
audit history.

## Review results

Six verification groups passed on PGlite PostgreSQL 17.5. The fixture loaded
the checked-in SQL, bundled the real browser client and gateway, and used
fictional Firebase identities plus a local PostgREST adapter. Production
PostgreSQL 17.6 supplied only definitions and privilege metadata. The review
did not test production posting or voiding.

| Check | Result |
| --- | --- |
| Effective privileges | Baseline `PUBLIC` access reproduced in the catalog. The proposed grants retain service execution on post and void, with direct execution denied to `anon`, `authenticated` and an unrelated role. |
| Preservation | Existing fictional note, audit history, UC row, sequence state, relation grants, function identities/definitions and trigger definition compare equal before and after the grant change. |
| Gateway access | Twelve anonymous, invalid-session, customer and unassigned-staff requests returned 401/403 across post, void and list. The adjustment without a reason returned a validation error. None reached the database. |
| Authorized workflows | Admin and assigned staff posted distinct sequential CNs against the same fictional SI. SI/order filters, exact accounting amounts, verified actor, existing UC lookup and unresolved legacy UC text passed. |
| Void and audit | Assigned staff voided a pre-existing note. Its original row remained, with one audit update containing before/after status. Repeating void added no audit event and advanced no sequence. |
| Inheritance guard | A fictional inherited service grant remained effective after the direct revokes. Checking effective privileges caught it before commit, and the test rolled back. |

Evidence is in ignored `qa/out/credit-note-permission-review/results.log`.
Draft editing, CSV, print and WooCommerce draft staging were traced in source.
The compatibility run exercised the client/gateway and SQL boundary, with
Firebase authentication and HTTP transport simulated. The future release
should validate its exact migration and run the repository's live role checks.

## Approved implementation

The [migration](../../erp-sync/migrations/20261111172028_harden_credit_note_execute.sql)
checks the three function definitions against the reviewed catalog and verifies
the audit trigger before changing grants. It checks effective access and the
resulting ACLs before commit, then requests a PostgREST schema refresh. The
canonical [setup SQL](../../erp-sync/app_credit_note.sql) now commits definitions
and grants in the same transaction.

The [fictional regression](../../qa/credit-note-permissions.test.mjs) loads the
canonical setup, recreates the legacy grants and applies the exact migration.
It repeats the review scenarios, re-applies the migration, and checks failure
and rollback with inherited service access or drift in the function or trigger.
It runs in `test:invoice-reconciliation` and the `product-search` GitHub job.
