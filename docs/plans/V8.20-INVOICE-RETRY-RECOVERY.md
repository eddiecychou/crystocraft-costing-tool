# SH-05B — durable invoice retry and reference recovery

8 November 2026, Australia/Sydney. Owner authorized implementation, fictional
tests, push and deployment after both exact-SHA GitHub checks. Baseline
`122a21875eb35dd800dc84886164b7cf9fc93db0`; SH-05A permission hardening is live.
This records the design/migration before applying any production change.

## Contract

- One durable request UUID per intentional invoice operation, saved in Firestore
  before any SQL allocation. Retrying the same saved order resumes its active
  operation across navigation, reload, timeouts and simultaneous editors.
- A new split/reissued invoice is an explicit action with purpose/reason and a
  compare against the currently reviewed operation/references. It creates a new
  UUID. Never constrain invoice `order_id` to uniqueness, guess an invoice from
  order/customer/year, overwrite another invoice or backfill legacy operations.
- A private SQL receipt table makes allocation atomic/idempotent by UUID plus
  exact request JSON. A reused UUID with changed facts fails. Same-operation
  calls serialize before the existing per-year allocator lock; different UUIDs
  remain separate legitimate invoices.
- Server derives/fixes request facts from the saved order and authenticated
  initiating identity. Clients cannot choose an arbitrary UUID/customer/order
  association. Unsaved customer/currency/UC changes require saving first.
- Allocation and linking have separate durable states. A committed SQL result
  survives a lost response or Firestore failure. Resume recovers that result,
  then retries only the unresolved stages. Conflict means Review required,
  with the issued number visible; never allocate another number as recovery.
- Root reference revisions and Firestore rules reject stale/legacy saves that
  could overwrite recovered references. Normal commercial saving remains atomic
  across header/lines. Non-allocation legacy orders retain their existing path.
- Financial-copy and Woo registry follow-up failures have their own persisted
  outcomes and retry paths; none can issue another SI. Use saved raw source,
  existing projections/validation and compare-before-write checks. Preserve
  known Accounting Total, unknown versus zero and manual financial edits.
- Existing parent/order/ledger records and historical invoices remain intact.
  No historical duplicate repair, automatic voiding, number reset or bulk backfill.

## Ownership and compatibility

The protected Node invoice-allocation endpoint owns Firestore request claims,
SQL receipt calls, reference linking and follow-up outcomes. It reuses existing
Firebase Admin bootstrap/current profiles and server-side Supabase identity.
Read requires internal Shipping access; mutation also requires UC access (the
existing order screen plus invoicing permissions). Customers are refused before
order/SQL access. No server key or private request is sent to the portal.

Operation documents live in an internal-only order subcollection. Its existing
recursive rules must exclude this collection, including the zero-segment parent
overlap, so broad legacy grants cannot bypass new protections. Client operation
writes and allocation-pointer writes are denied. A reference-changing client
save must carry the next loaded reference revision and can only occur after the
operation is linked; stale saves fail atomically without a financial follow-up.
Pending operation deletion is blocked. Source attachments/lines stay intact.

The existing seven-argument allocation logic is moved intact to a new private
schema as the internal core. Its body/owner/date/sequence/UC semantics remain
unchanged. New service-only RPCs allocate once or look up a receipt. The old
public seven-argument signature remains as a fail-closed refresh message and
cannot issue a number. Thus old open tabs, old deployments and an app rollback
cannot silently bypass request identity. Do not roll back by restoring an unsafe
legacy allocator, removing issued receipts or deleting numbers.

Canonical historical setup is guarded against replay after the recovery layer
exists. The SH-05A historical migration cannot reactivate unsafe legacy calls:
even if its server grant is reapplied, the legacy signature only raises the
refresh error. Private schema/table/core have no client/service direct grants;
new RPCs retain explicit service-only execution and pinned search paths.

## UI and create flow

- Existing Raise/Allocate actions resume the saved request. Immediate repeat
  clicks are guarded; the server claim handles concurrent tabs/late responses.
- Pending/issued-but-not-linked/review/follow-up states are visible on the saved
  order after reopening, with issued SI/UC and a safe Resume action.
- New split/reissued invoice is a separate reviewed action; earlier invoices
  remain in operation history and the ledger. No invoice is automatically voided.
- Conflicting current references require explicit review before linking a
  recovered result. Changed customer/currency cannot be silently adopted.
- Direct Create commits the order first and invokes the same recovery workflow.
  The landed saved order carries any pending outcome. Repeated create clicks
  are guarded; quote conversion policy and general abandoned-create recovery are
  separate SH-06/07/08 work, not blanket one-order-per-quote behavior.
- Follow-up review can be explicitly recorded as handled manually, without
  altering financial facts, so a deliberate later invoice is not trapped behind
  an unresolved optional auto-fill. No background outreach or stock action.

## Implementation and migration review — before production application

Implemented server ownership in `netlify/functions/lib/invoiceRecovery*.js`,
with thin `/api/invoice-allocation` wrapper/client and the controlled
`ShipmentInvoiceRecovery` panel. ShipmentForm retains commercial editing,
atomic header/line saving, PDF/Excel totals and ordinary financial Re-sync.
Pure existing invoice/Woo projections and edge write normalization are shared,
rather than reimplemented. Standalone SO/UC allocation remains unchanged.

The reviewed DDL file is
`erp-sync/migrations/20261108013402_invoice_retry_recovery.sql`. It creates the
private schema/receipt table, moves the exact existing allocator to
`oc_invoice_private.allocate_core` (retaining its OID/body), installs a public
legacy refresh-only shim, and adds three service-only, owner-definer RPCs:
`allocate_sales_invoice_once`, `lookup_invoice_allocation`, and
`apply_invoice_allocation_followup`. Complete initial invoice/UC snapshots are
captured inside the allocation transaction. The follow-up RPC locks the exact
receipt's row and compares its typed full row, including nulls and timestamp
precision. A subsequent manual edit is preserved even if recovery reads it
fresh; an already-applied identical patch is a no-op. Unknown source amounts
stay pending for manual review. No order-level uniqueness, historical backfill,
number reset, invoice voiding or financial-row update is part of migration.

New functions explicitly revoke PUBLIC/anon/authenticated execution. The
private schema, core and receipt table also deny direct service-role access;
RLS is enabled without client policies. Postchecks fail the whole transaction
if effective execution boundaries differ. The transaction limits lock wait to
5 seconds and statements to 30 seconds, then reloads the PostgREST schema cache.
The historical bootstrap refuses replay over the private schema. SH-05A's DCL
can only regrant the new legacy shim, which cannot allocate.

Use connected JES `apply_migration` for this DDL after exact-SHA CI and candidate
role gates. Unlike SH-05A's DCL-only operation, this may register migration
metadata; inspect and record the actual history state afterward. Verify live
baseline allocator body MD5 `d39f6973c728db0db9c2de3d1f0a7328`, OID 26477,
owner/SECURITY DEFINER/pinned search path, no unexpected overload/private schema
and current table columns before applying. Read back every new ACL/RLS/function
and compare core identity/body plus business row counts afterward. Do not replay
the entire historical SQL file or bootstrap unrelated schemas/grants.

Firestore migration is additive server-only metadata, with no backfill:
`orders/{id}.invoice_allocation_id`, `.invoice_reference_revision` and private
`orders/{id}/invoice_allocations/{UUID}` documents, created only on a deliberate
invoice action. All client operation writes and pointer changes are denied.
Reference edits on tracked linked orders require the next loaded version;
commercial edits with unchanged references retain it. Root pending deletion is
denied. The previous recursive rule also matched zero segments and could bypass
root protections; its replacement requires a child collection/document and
excludes invoice_allocations from both broad Shipping writes and own-customer
reads. Existing ordinary child permissions remain. New-order/duplicate writers
strip allocation metadata rather than copy the old intent.

The old app/API/RPC entry point fails closed during cutover. Refresh old tabs
before invoicing. A number issued before this migration has no durable request
receipt; it is never inferred from an order/customer/year. Review historical
unlinked numbers separately rather than guessing or silently deduplicating them.
An app rollback must retain these rules, receipt records and legacy refusal;
fix forward on recovery instead of restoring unsafe allocation.

## Verification implementation and lessons

- Native PostgreSQL **17.6**, verified official source/checksum, runs only as an
  owned temporary loopback process. Each suite refuses a remote/non-QA URL and
  creates/drops its own fictional child database. Six independent connections
  are observed waiting on real locks; PGlite is not substituted for concurrency.
- Permanent CI uses a disposable `postgres:17.6` service in both required jobs,
  with clearly fictional credentials and an explicit loopback QA database. The
  product-search job runs native SQL plus model/client/panel tests; the emulator
  job runs actual Firebase Admin/client SDK transactions/rules, controller and
  SQL transport against native PostgreSQL. Missing local services fail rather
  than skip. Existing save/source/RBAC tests remain required.
- The local PostgREST adapter preserves PostgreSQL JSON timestamp precision.
  A pg driver Date conversion truncates microseconds and falsely fails full-row
  comparison; timestamp-only CAS would miss manual edits and is not used.
- Existing real-form reference/Woo regressions now mock the new service boundary,
  keeping their exact source/amount/notes/save/reload assertions. Service-side
  allocation/link/follow-up semantics have separate actual-store tests.
- A missing parent's protected update now returns permission-denied before the
  SDK's NOT_FOUND precondition. The existing save test accepts either refusal,
  while continuing to prove that no header or orphan lines are created.
- Direct Create has an immediate in-flight guard, commits first, then uses the
  same durable request. On failure it lands on the saved order for Resume.
  General abandoned-Create/re-entry and quote-conversion policy remain SH-06/07/08.
- History shows the latest 20 requests and labels older retained history. The
  ledger and private receipts retain all invoices; no deletion or uniqueness is
  inferred from this display limit.

Local commands: `npm run test:invoice-recovery`,
`QA_INVOICE_DATABASE_URL=<explicit loopback QA URL> npm run test:invoice-recovery-postgres`,
and the required workflow's Firestore emulator command. No production number,
order, financial row or outreach is used by these tests. Production verification
uses fresh sign-ins, invalid-input/legacy-refusal checks and `action:ready`, which
only looks up the all-zero UUID (the allocator requires UUIDv4).
