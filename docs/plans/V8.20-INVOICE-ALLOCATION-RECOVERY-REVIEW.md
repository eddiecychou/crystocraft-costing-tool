# Invoice allocation recovery — SH-05 read-only contract review

7 November 2026, Australia/Sydney. The owner authorized releasing SH-03, then
read-only inspection of the deployed SI allocator and a recovery plan. This
record is that review. No allocator, grant, schema, order or financial record
has been changed; no invoice/UC number has been requested or issued by this
review. Implementation and database publication remain a separate batch.

## Confirmed contract

Source baseline: `96ba538ad074b16f305bc8ac351c04eadd61159e`. Trace
`ShipmentForm.jsx` → `ucRegistry.allocateInvoice` → `/api/uc` →
`public.allocate_sales_invoice(text,text,text,text,bigint,text,text)`.

Connected Supabase SELECTs inspected function definition/configuration,
effective privileges, table columns and indexes. They did not query business
rows, invoke the allocator or run DDL. Ignored raw evidence is retained at
`qa/out/invoice-allocation-review/live-metadata.json`; it contains metadata,
not tokens. `pg_get_functiondef` and effective privilege checks are documented
in the [PostgreSQL system-information reference](https://www.postgresql.org/docs/current/functions-info.html).

| Finding | Verified state and consequence |
|---|---|
| Allocation transaction | The live function locks the year, chooses the next SI after app/mirror maxima, reuses or creates a UC, and inserts the invoice in one transaction. That protects the database allocation, not the later Firestore reference patch. |
| Retry identity | Seven parameters; no operation identifier, request fingerprint or prior-result lookup. Every successful invocation allocates another SI. Existing columns/indexes have no operation identity; only invoice ID and SI number are unique. |
| Saved-order Raise | An acknowledged result updates local state before `updateOrder`. A failed reference write produces an error, but no durable recovery intent/result is retained for reload. |
| Direct Create | The order commits first, then allocation and reference patch share one catch. A reference failure can be reported as allocation failure. Navigation loses that form warning; a later ordinary Raise calls the allocator again. |
| Private table access | Metadata reports no anon SELECT/INSERT or authenticated INSERT on either financial table. RLS is disabled. This is not proof of complete table ACL safety; the function privilege finding below is independently sufficient. |
| App gateway | `/api/uc` verifies Firebase role/module access and calls PostgREST with the server key. Browser clients do not need SQL function execution rights. |

The review confirms a mechanism that can issue a second number on retry. It
does **not** establish that historical duplicate invoices exist. No historical
repair or duplicate deletion is proposed from this metadata-only evidence.

## First priority: narrow allocator execution privileges

Live effective EXECUTE is **true for anon, authenticated and service_role**.
The explicit ACL is `{=X/postgres,postgres=X/postgres,service_role=X/postgres}`:
the `PUBLIC` entry remains. The checked-in SQL revokes named anon/authenticated
grants, but never revokes the default PUBLIC grant. The deployed function is
`SECURITY DEFINER`, with `search_path=public, pg_temp`, and can write the
private invoice/UC tables with its owner's rights.

This is a confirmed database privilege gap. No anonymous HTTP allocation was
attempted, because success would issue a real financial number. Transport-level
exploitability and historical misuse have not been tested or claimed.

Prepare a small, separately reviewed, transaction-wrapped grant migration before
the larger recovery work. Its proposed operation is:

```sql
-- DESIGN ONLY: not applied by this review.
REVOKE ALL ON FUNCTION public.allocate_sales_invoice(text,text,text,text,bigint,text,text)
  FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.allocate_sales_invoice(text,text,text,text,bigint,text,text)
  TO service_role;
```

Also correct the canonical SQL so a later full replay cannot restore PUBLIC
execution, and inspect existing overloads before migration. Do not replay the
whole historical setup file against production. Confirm actual callers and
test the existing service-only gateway in a disposable fictional database.
Post-migration catalog readback must show anon/authenticated EXECUTE false and
service_role true, with the function body/owner/search path otherwise unchanged.
Do not broaden table/raw-schema grants or run the real allocator as a smoke test.
Audit other financial SECURITY DEFINER grants read-only as a separately bounded
follow-up; this review does not imply that every function has been assessed.

## Second priority: durable allocation intent and reference recovery

Preserve intentional multiple/split/reissued invoices. Do **not** add unique
`order_id`, assume the newest invoice belongs to the current attempt, or silently
reuse any invoice merely because its order/customer/year matches.

1. Persist a unique allocation intent on the saved order **before** requesting a
   number. Direct Create must save the order and its intent first. Resume the
   same intent after navigation/reload, ambiguous network failure or retry.
   Prevent simultaneous editors from replacing an active intent using an atomic
   compare/write. Keep any acknowledged result recoverable outside component state.
2. Add an additive, private database operation identity with a unique constraint
   and normalized request fingerprint. The allocator must atomically return the
   existing result for the same intent, reject conflicting reuse, or allocate
   exactly one new SI/UC. Use transaction/lock ordering that is safe for concurrent
   same-intent and different-intent requests. Preserve current sequence, UC reuse,
   invoice date, audit and historical record semantics.
3. Carry the intent through the existing Firebase-authorized API. Validate its
   identity and ownership/server authority; do not trust an arbitrary client
   intent/order association. Maintain service-only SQL execution. Plan compatibility
   for older open browser tabs explicitly: missing-intent calls must not silently
   retain unsafe automatic retry behavior or break halfway through rollout.
4. Separate allocation from linking. After allocation succeeds, retry only the
   order-reference patch, with readback and conflict detection. A lost response
   retries the same intent to recover the same SI/UC. Existing different SI/UC
   references require review rather than overwrite. Any later financial-copy or
   Woo registry failure must identify its own stage and cannot reallocate.
5. Show durable pending/allocated-but-unlinked/linked/review-required outcomes on
   the landed saved order. Busy guards cover immediate repeated calls. New invoice
   intent must be a deliberate action consistent with the agreed split/reissue
   policy; it must not be an automatic escape from an uncertain previous attempt.

The exact persistence fields/table and reissue UI are design decisions to review
with the implementation diff. Existing invoices without an intent stay intact.
Ambiguous legacy records require read-only matching and human review; no bulk
backfill, inferred relinking, number deletion or voiding is authorized here.

## Verification and rollout gates for that batch

Use fictional records in a disposable PostgreSQL test database and actual
client/edge/page tests. Cover: failure before dispatch; allocation rollback;
commit with lost response; acknowledged allocation plus rejected/timeout reference
patch; reload/navigation; two tabs; concurrent same-intent calls; conflicting
fingerprint; intentional distinct intents; existing UC and missing UC; existing
conflicting order references; old-client compatibility; permission denials; and
failed financial-copy/Woo follow-up. Assert SI/UC row counts, identical recovered
IDs and preserved source data. A mock-only test cannot prove SQL concurrency or
transaction behavior.

Document additive migration, compatibility/deploy order, dry-run metadata checks,
roll-forward/rollback limits and recovery UI before applying anything. Never
roll back by deleting issued invoices or resetting a numbering sequence. Keep
permission hardening in effect if application code is rolled back.

Both exact-SHA GitHub jobs and fresh admin/approved-customer candidate and
production checks remain mandatory. Publish SQL separately under explicit scope,
read back grants/function/schema, and prove app behavior with fictional records
without issuing production numbers or sending customer emails. Access checks
must confirm customer/staff-without-module refusal as well as permitted admin
access. No database change or SH-05 implementation is included in SH-03's release.

## Lessons and next scope

- A database allocation transaction cannot atomically acknowledge the later
  Firestore patch. Recovery needs persistent operation identity across systems.
- Revoking named roles does not establish service-only execution when PUBLIC
  retains an effective grant. Verify effective rights, not only migration text.
- Allocation failure and linking failure need different messages and retry paths.
- Keep a financial-number review read-only; proving the unsafe path by invoking
  the live allocator would itself create a consequential financial record.

Recommended next batch: review and test the narrow grant hardening first, then
implement the intent/recovery contract with the split/reissue policy preserved.
