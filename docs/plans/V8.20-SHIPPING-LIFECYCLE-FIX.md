## Resulting behavior

Each saved order has its own mounted editor. New-order entry contexts are keyed
by customer, quote and direct-entry intent; saved-order invoice-focus query
changes retain that order's unsaved edits. Abandoned reads cannot update a newer
editor. The saved header, source file and lines appear together only after both
order reads succeed. Missing or rejected reads show an error and Retry, with no
editable order or Save action.

`shipping.saveOrderWithLines` reads existing lines before staging any mutation.
It submits one batch containing the header update and the normalized replacement
line sets/deletions. A read/staging/batch failure cannot independently persist
one half of this save. Header update semantics preserve unrelated metadata and
refuse to recreate a deleted order. The existing lines-only API remains for
other callers. Creation and SO/UC/SI allocation algorithms remain unchanged.

An existing-order Save awaits the batch acknowledgement. After six seconds it
continues to show Saving and an explicit pending-confirmation message; a timeout
never means success. Form controls, stock actions, delete, tabs and invoice
allocation are disabled while saving. Repeat submits are guarded synchronously.
Save also waits for an in-flight extraction/allocation to finish before starting.
A late failure retains the edited fields, shows the error and permits explicit
retry. The financial-index upsert and return to the list happen only after a
successful Firestore acknowledgement. An old editor's save can still synchronize
its original financial entry after completion, but cannot navigate away from a
newer order or display errors on it.

## Limits retained

This is atomic header/line persistence, not a lock against concurrent editors.
The line query and batch do not constitute a transaction across other users'
changes. An offline query can know only cached lines, so an unseen line added
elsewhere cannot be reconciled until it is read. Offline batch queuing stays
supported, with pending feedback until server acknowledgement. Browser closure
can interrupt the frontend financial-index follow-up; the existing Sales Invoices
reconciliation remains the recovery mechanism. No durable cross-system outbox,
automatic historical repair or permission change is introduced.
