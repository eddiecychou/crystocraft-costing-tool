# Issued invoices awaiting an order link

17 November 2026 AEDT · Read-only review of `e58bd8e9`. An invoice can have a durable SQL receipt and an issued SI even while its Shipping order still shows the previous invoice or a blank invoice field. The order status check can look up the saved operation and confirm the SI. The cross-order **Invoice follow-ups** view starts after linking, so it omits this earlier recovery stage. ## When to Resume and when to send it to Finance

| Situation | Staff action |
| --- | --- |
| Exact SQL receipt confirmed, saved request is current, order still open, customer identity, currency and saved references match | Reopen the order and use **Resume saved request** for that exact operation. Check the SI and UC before confirming. A completed link may already be visible after refresh. |
| Exact receipt already linked | Use the existing **Invoice follow-ups** flow if financial or UC work remains. A fully complete request needs no further action. |
| Saved references changed, with the same customer and currency | Send the exact SI, UC and order reference to Finance. After Finance confirms that the issued copy belongs to the order and approves the replacement references, an authorised operator can use **Review references** against the freshly reopened order. |
| Customer ID or name changed, currency differs, current request changed, order is closed or missing, or receipt identity conflicts | Send the case to Finance. Preserve the issued SI, its UC, earlier invoices and saved request. Include the operation ID, the exact references that are verified, and the reason for the handoff. A same-name customer change still requires ownership verification. |
| Receipt source temporarily unavailable, or no issued receipt found | Refresh and verify the original request and receipt evidence. Escalate persistent uncertainty or any contradictory evidence to Finance. A successful lookup with no receipt remains an unconfirmed issuance and follows the existing saved-request workflow. |

Shipping staff can read the order status. Admins and staff with Shipping and UC can take the existing recovery actions. Invoice-only staff and approved customers received HTTP 403 on the recovery status endpoint in the fixture. ## Proposed implementation order

1. **Protect ownership and the review snapshot first.** Capture and validate the stable customer ID on new allocations. Verify the saved operation, customer, currency and reference revision inside the link transaction. Use the full saved reference snapshot when confirming a reviewed link. Keep issued operation IDs and frozen SQL requests intact. Older unresolved receipts that lack a verifiable customer identity go to Finance.
2. **Distinguish receipt outcomes on read.** Report a matched issued receipt, a successful check with no receipt, an unavailable source, and conflicting evidence as separate outcomes. Keep the read path bounded and attach each outcome to the exact operation ID. An unavailable or contradictory result should never be presented as a verified issued invoice ready to link.
3. **Surface verified unlinked invoices under Production → Orders.** Add an **Awaiting order link** section with the exact issued SI, UC and order, plus the appropriate Resume or Finance-review guidance. Link through to the exact saved request and reload its status when opened. Show detached or conflicting records for review without a recovery action. Keep issuance and recovery controls in the existing order panel and keep post-link financial work in **Invoice follow-ups**.

## First fix · invoice link ownership and reference review

New requests keep the saved `customer_id` beside their frozen order facts in Firestore. A newly created request for a walk-in order records an explicit empty selection. Resume and Review references check the saved customer identity, name and currency before linking. A customer mismatch or an older unresolved receipt with an unknown original customer stays with Finance. Existing SI, UC, SQL receipt and history records remain available. The saved request sent to SQL keeps its existing shape.

The explicit Review references confirmation binds the operation, issued result, customer, full saved references and reference revision at the time the form opens. A change in those facts requires reopening the review. The server repeats this check inside the linking transaction. Older tabs must refresh before confirming a reviewed link. A link review can only confirm an already recorded issued result.

This patch covers the first implementation item. It uses the existing data permissions and needs no SQL, Firebase rules or record migration.

## Second fix · read-only receipt status

Opening or refreshing an unlinked invoice request checks the SQL receipt for its exact operation ID. The response distinguishes four states.

| Order status | Evidence and next step |
| --- | --- |
| **Issued receipt verified** | The receipt matches the saved operation, order and frozen request. If the operation already recorded an issued result, both results agree. An authorized operator can use the existing recovery controls when ownership and saved references allow it. |
| **No issued receipt found** | The lookup succeeded with an empty result and the request has no recorded SI or UC result. Staff can use the existing saved-request workflow. |
| **Receipt source unavailable** | The read failed or the source response was incomplete. Refresh the status before using recovery controls. |
| **Conflicting receipt evidence** | A receipt disagrees with the saved request or its issued result, more than one row was returned, an invalid row was returned, or a recorded result had no SQL receipt. Send the exact saved request to Finance. |

The order retains recorded SI and UC as saved references during an outage or conflict. The status check neither writes the SQL result back to Firestore nor changes the order link. Each status request performs at most one receipt lookup, and the order avoids overlapping status reads during a polling cycle. Linked invoices continue through **Invoice follow-ups**. The release needs no rules, SQL or record migration.
