## Findings

1. **Preserve the losing draft in a two-tab conflict.** Two Chrome tabs opened
   the same new-order request. The first saved a line at 1.222. The second
   submitted a different description and a price of 7.87. The server refused
   the different payload, and readback found exactly one request and one
   order with the original price. The second tab switched to the saved request
   screen and lost access to its edits. Start a separate order opened a blank
   form. [Request editor](../../src/pages/NewShipmentEntry.jsx#L87) ·
   [Immutable request check](../../netlify/functions/lib/orderCreateRequests.js#L248).
2. **Show removed manual or PI orders as requiring review.** A fictional
   manual order was saved and then removed from the emulator. The request list
   still said Open. Opening it showed the removed-or-replaced error and
   offered Check saved status, which repeated the error. The saved request
   remained and no order was recreated. Direct Invoice and copy detail already
   have a structured review state. [Request status and list](../../netlify/functions/lib/orderCreateRequests.js#L154) ·
   [Saved requests panel](../../src/components/shipping/SavedOrderRequests.jsx).

## What passed

- Eight Chrome cases exercised the actual form, API handler, Firestore and
  Storage emulators. Controls covered a lost order confirmation, reload, Back,
  deliberate new order, same-request concurrency, lost PI preparation response,
  wrong-file rejection, reuse of the original object after browser closure,
  saved-request discovery and status Retry. The two cases above confirmed
  the current conflict and removed-order behavior.
- Thirteen quote conversion Chrome cases passed, including source drift,
  lost acknowledgements, recovery, and an explicit additional order.
- The exact-SHA CI suites verified that Direct Invoice retries reuse the same
  order, SI and UC after lost replies, including first-invoice follow-up.
  Duplicate Order replay reused its receipt and explicit copies received
  separate receipts. Split and reissued invoices kept separate operations
  and ledger rows. These financial checks ran in GitHub's fictional
  Firestore and PostgreSQL environment. [GitHub run](https://github.com/eddiecychou/crystocraft-costing-tool/actions/runs/43407039825).

## Proposed order

1. Keep the losing draft available on an immutable-request conflict. Show
   both the saved request and the operator's draft, and let the operator
   explicitly open a separate request with those edits. Keep a selected PI
   in the open tab, with re-selection and byte verification if needed after
   reload. Verify concurrent submissions, lost acknowledgements and exact
   persisted order/SO counts before any broader extraction.
2. Give removed or replaced manual/PI requests a structured review outcome
   and align the list and detail labels. Verify missing and replaced targets,
   pagination, no order recreation and no additional number allocation.
3. Then extract the client-side order request orchestration from
   `NewShipmentEntry`. Keep validation and draft editing in `ShipmentForm`.
   Keep immutable request ownership and persistence in the existing server
   repositories. Quote conversion and invoice issuance retain their separate
   intent IDs, so explicit repeats, splits and reissues remain independent.
