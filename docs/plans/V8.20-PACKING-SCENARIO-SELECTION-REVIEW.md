# Packing scenario selection review

15 November 2026 AEDT · Repository baseline `6d16c6d5` · Fictional orders in a local Firestore emulator

The Packing star sets the working plan. Opening a different plan in the editor
lets staff inspect it and export it by its own scenario ID. The separate Freight
decision selects a saved carrier quote. Changing the working plan should affect
the default for a new Freight quote while preserving existing Freight decisions
and their commercial snapshots.

## Reproduced behavior

| Two-tab case | Result |
| --- | --- |
| Star different saved plans with unchanged membership | Exactly one stored star after each commit. The last commit won. The other open tab still displayed its previous star until reload. Reopening Freight defaulted to the winning plan's saved cargo. |
| Both tabs save their first Packing plan | Both distinct plans and drafts were saved successfully. Both documents had `selected: true`, and the editor showed two stars after reload. |
| Star while the other tab creates and stars a new plan | Tab A read the list before Tab B saved and starred Scenario 3. After Tab A's older batch committed, both its target and Scenario 3 were starred. A fresh Freight form defaulted to the older of the two starred plans in this fixture. |
| Delete the starred unused plan | The scenario and its carton were removed. No surviving plan had a stored or visible star after reopening. The editor and new Freight form fell back to the remaining plan. |
| Star a plan already deleted by the other tab | When the delete committed before the star query, the click appeared to succeed. Tab B drew a star on the deleted row and cleared the real star on the surviving rows. When the delete committed after the star query, Firestore rejected the whole batch and preserved the real star. The editor surfaced a raw permission error in that ordering. |
| Star another plan when the original plan has only a legacy timestamp | The star action advanced the original scenario's `updatedAt` without changing the measured cargo or carton. A fresh Freight comparison labelled the chosen quote **Packing changed**, and an already-open new quote on that legacy scenario failed as stale. Its draft price stayed in the form. The chosen quote's stored cargo, price, link and decision stayed identical. |
| Open the working plan and then explicitly open another plan | After reopening, the Packing editor's PDF preview and downloaded Excel opened the starred plan. Opening Gamma directly exported Gamma while Beta stayed starred. The preview date of a plan without an explicit Packing date advanced after the star batch, because the preview falls back to `updatedAt`. Excel left the explicit date cell blank. |

The primary cases compared every saved Freight quote and the full decision
document before and after the Packing actions. Readback preserved USD 145.25,
its stored HKD 1,162 equivalent, the source Packing scenario and revision where
linked, charge breakdown and notes, and the chosen quote ID. The saved quote's
cargo override stayed at seven cartons, 0.8754 CBM and 31 kg chargeable.
The stale legacy badge was a display consequence of the timestamp change.
The quote was still chosen on reopening.

## Why it happens

First-save selection comes from the editor's local list, and an individual
Packing save transaction reads its own scenario. Star writes batch together the
scenario documents returned by a prior query. That update never checks that
the requested target still exists in the result or coordinates with a scenario
created after the query. The delete handler checks the exact scenario revision,
prevents deleting linked plans and removes descendants, with no write to
choose a surviving working plan.

The read path recognizes older records where the selection flag is absent.
When all surviving flags are explicitly false or several are true, consumers
fall back to a scenario without repairing the ambiguity. Star also changes
each scenario's generic update timestamp. Freight uses that timestamp as a
revision fallback for legacy Packing, and print uses it as a date fallback.

## Proposed fix

1. **Give each order one working Packing selection.** Use one authoritative
   selection record per order, following the existing Freight decision pattern.
   First save, explicit star changes and guarded deletion should coordinate on
   that same record. Initialize it in the same commit as the first saved
   scenario and its contents. A second first-save attempt should keep its
   independent plan and cargo while preserving the winning selection. Star
   should verify the target exists on that order and is writable at commit.
   A stale target should return a clear reload message while retaining the
   currently confirmed choice and any unsaved edits.
2. **Resolve deletion as part of the same transaction.** If the selected plan
   can be deleted under the existing Freight link and revision guard, choose
   the oldest surviving saved plan, with scenario ID as a stable tie-breaker.
   Clear the selection when the final plan is removed. Check the same selection
   record during concurrent star, create and delete operations so the selected
   ID always resolves to a saved plan on its order. Keep the existing atomic
   limits for cartons and contents and include the selection write in that
   limit.
3. **Keep one selection read for Packing and Freight.** Use the confirmed choice
   for the editor's initial plan, the closed-order list and the default in new
   Freight forms. Keep explicit print and Excel links tied to their own plan
   ID. Refresh the star independently of the open draft. A retry after an
   uncertain response should recover or show the confirmed choice without
   silently overwriting a later choice. An explicit Freight draft already
   tied to a valid plan and revision can keep that cargo if the default star
   changes.
4. **Preserve historic cargo and dates.** Write only Packing selection metadata
   for a star change. Leave scenario revisions, content timestamps, quote
   snapshots and Freight decisions intact. For orders with old flags, use the
   sole valid legacy star where possible. For zero or multiple stars show a
   deterministic working default and prompt for confirmation, with no write on
   read. Backfill of old flags or quote revisions would require a separate
   decision. Protect the authoritative record with existing Shipping access
   and closed-order checks. Verify that stale clients cannot override it.
5. **Keep the role issue separate.** Review whether standard-carton lookup can
   fail independently of loading, starring and exporting saved plans. Preserve
   existing Range permissions.

A later implementation should replay both commit orders for star versus
create and delete, two first saves, retry after a lost response, empty/legacy/
closed orders, and direct stale browser writes. Assert exactly one valid
working selection when saved plans exist and verify Packing preview, Excel
and the default Freight cargo. Compare the full Freight quote and decision
documents again, including legacy timestamps, original prices and manual cargo.

## Verification scope

The harness used the live React Packing editor, Freight Comparison and print
page from the repository, the Firestore Web SDK and deployed-source rules in
a loopback-only emulator, and the Shipping request handler backed by the
Admin SDK on the same emulator. The harness paused real reads or transactions
before commit to control ordering. Eight cases used fictional admin and
Shipping-plus-Figurine staff sessions. A separate Shipping-only check read the
saved scenarios successfully but the Range lookup failed and the editor
showed an error before rendering them. All 25 existing Packing and Freight
emulator regression tests passed. Print verification covered the browser
preview content and a downloaded workbook parsed for its scenario-specific
item code. The native Print dialog was outside this check.

The diagnostic runner, logs, evidence and duplicate-star screenshot are in the
Git-ignored `qa/out/packing-selection-review/` directory. Application code,
Firestore rules and production records were unchanged.

## Implementation

The working selection is stored in `packing_selections/{orderId}`. A new
plan and the first selection commit together. Explicit stars update only the
selection document and the editor can receive the confirmed selection from
another tab without replacing its open draft. When the other tab selects a
plan missing from the local list, **Reload working plan** updates the list
while retaining local drafts. If a deleted choice is stale, the editor
refreshes the saved selection and reports the unavailable plan.

Guarded deletion keeps the existing revision and Freight-link checks. If it
removes the working plan, the same transaction chooses the oldest survivor or
clears the selection after the last plan. Deleting an unused order draft also
removes its former Packing selection. New Freight forms reload the saved
working plan before filling their defaults. Existing forms stay attached to
the scenario and revision they already loaded. Direct writes to the old star
flag are blocked. Legacy records get a working default on read and can be
confirmed explicitly without a bulk migration.

The Shipping-only catalogue lookup issue remains a separate follow-up.
Rollout publishes the Firestore rules with the application. Existing browser
tabs should refresh before using the Packing star or saving a new plan.
