# Saved-order concurrent editing review

**Reviewed 9 November 2026. Implementation is proposed.** Two fictional Shipping
operators exercised the actual save helper, Web SDK and current access rules in
a loopback Firestore Standard emulator. The tests confirmed that an older editor
can overwrite a newer commercial save. They also reproduced mixed versions
during initial loading and during the gap between reading lines and committing.

## Findings and priority

| Priority | Reproduction | Observed result |
|---|---|---|
| P1 | Both operators open the same order. A records a deposit, then B saves only a notes edit using the original screen. | The deposit of USD 155 becomes blank and the original payment terms return. |
| P1 | A adds a line and changes a unit price. B saves the earlier line set. | A's added line is deleted and the unit price returns from 1.333 to 1.222. |
| P1 | A removes a line. B saves the earlier line set. | The deleted line is recreated at its old document ID. |
| P1 | B goes offline. A adds a line. B saves its cached copy and reconnects. | The new line survives, while the header total becomes USD 1,226. The saved lines total USD 1,232.25. |
| P1 | A's line read is held while B saves a new line, then A's batch commits. | A's header and B's new line coexist, producing the same total mismatch. |
| P1 | Both screens retain the same linked invoice references and reference revision. A changes price/deposit, then B saves an old notes edit. | Existing invoice-reference protection permits the stale commercial overwrite. |
| P2, part of the same repair | B reads the header. A saves a deposit and new line. B then reads lines. | The editor can start with the old deposit and the new line set. |

Three controls succeeded. Reloading before the second save preserved the first
operator's changes and exact prices. A stale invoice-reference revision was
rejected atomically. The assigned customer could read its order but its save
was denied. Stock flags, original-file pointers and unrelated line fields were
preserved by the tested save path.

These are confirmed fictional reproductions. The review did not inspect or
repair historical business records.

## Why the current boundary permits this

`shipping.saveOrderWithLines` reads the existing line collection, builds one
batch and reconciles that collection to the editor's submitted line set. The
batch has no expected commercial version. It can therefore commit successfully
after another save. A fresh query at Save also cannot establish that the form
was based on that version, and another write can land after the query.

`ShipmentForm` reads the header and lines sequentially. `getOrder` normalizes
the header, and that normalization drops `updatedAt`. The editor keeps a
separate invoice-reference baseline, which protects invoice identities through
`invoice_reference_revision`. That counter covers a different responsibility
from commercial editing. `pi_revision` is the manually selected printed revision.

The reviewed `src/shipping.js`, current `firestore.rules`, and the saved-order
submit handler match committed source at `c3a4236`. The preceding local SH-07
creation-recovery work has its own release boundary. This finding concerns
editing an existing order.

## Proposed repair

1. **Capture one coherent baseline.** Add an explicit edit snapshot carrying the
   editable header, complete line identities and a system edit revision. Read
   the root around the line read and retry if its commercial version changes.
   Confirm online initialization reads with the server and retain that verified
   baseline with an offline draft.
   Keep the existing loading/error/Retry behavior. Legacy lines missing
   `line_no` need explicit handling so they cannot disappear from the edit
   snapshot and be deleted on Save.
2. **Compare at commit.** Introduce an internal `edit_revision`, independent of
   the printed PI revision and invoice-reference revision. A save based on
   revision N must write N+1 with the header and full line reconciliation in
   one batch. Firestore rules must compare against the stored revision and
   require line changes to accompany that root transition. A UI precheck can
   improve feedback, while rules enforce the actual commit condition.
3. **Keep the draft on conflict.** Retain the submitted edits and show that the
   saved order has changed. Offer a comparison with the latest header and lines
   and an explicit way to reopen/reapply edits. Avoid automatically replacing
   typed fields or merging monetary values and line changes. A rejected save
   must not navigate away or update the financial index.
4. **Preserve offline pending saves.** An already loaded, coherent draft can
   retain the existing locally queued batch behavior. It stays Pending until
   server acknowledgement. If its base revision is stale on reconnect, the
   whole batch is rejected and the draft remains available for review. An
   offline opening without a verified baseline needs a visible draft state
   until that baseline can be confirmed.
5. **Account for other writers.** Audit the callers below before enforcing the
   rule. Every writer that changes guarded commercial fields, invoice ownership
   or order lines must participate. Reservation and production flags have
   their own ownership. Preserve those fields and avoid making ordinary stock
   activity consume a commercial edit revision. Server/Admin writes require
   explicit participation because they bypass Firestore rules.

A stable save-attempt ID can accompany the root transition. On an uncertain
acknowledgement, a matching saved attempt can confirm success without generating
another line set. If another edit has already followed it, retain the draft and
require review rather than guessing that the retry should overwrite that edit.
Document this acceptance rule before implementing the retry UI.

| Print, customer and reconciliation readers | Preserve the commercial projections and customer access rules. System concurrency metadata must not become a document label. |

The current acknowledged financial upsert is a separate cross-system step.
This repair must prevent it after a rejected edit. Ordering or recovery of
financial follow-ups after later successful saves remains the separately
planned durable synchronization review.

## Migration and release proposal

Treat a historical order without an edit revision as revision zero. Its first
accepted guarded save writes revision one. This allows lazy adoption without
bulk rewriting commercial records or attachments. Review legacy missing-line
metadata before choosing how the editor exposes it.

Rules must reject an older client's unversioned commercial or line write after
enforcement. Otherwise old tabs retain the overwrite path. Plan a coordinated
rules/app cutover and a visible refresh requirement. Candidate fixtures must
cover both versioned orders and historical orders. A deployment requires the
owner's release authorization, both exact-SHA GitHub jobs, separate rules
verification and fresh admin/customer candidate and production checks.

Firestore rules. Seven cases reproduce defects and three establish existing
controls. The manual runner checks that every named scenario executes and
produces evidence, with a 30-second independent process deadline per case.

assertions completed. Isolating client lifetimes resolved the runner cleanup
issue while retaining all assertions. This is a review runner, outside the
normal application regression commands.
