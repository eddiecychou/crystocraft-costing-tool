## Findings and priority

### SH07-R1 — P1: initial Direct Invoice reports completion before accounting recovery finishes

**Confirmed with two fictional fault cases. Fix before deploying this recovery workflow.**

`readInitialDirectInvoice` treats any linked first invoice with an SI as `issued`, without examining its financial follow-up state. The `initial_direct` claim then returns no operation and the handler responds `initial_complete: true`. The saved-request UI consequently offers Open instead of Finish Direct Invoice. This shortcut bypasses the existing follow-up retry code.

References: [first-invoice status](../../netlify/functions/lib/initialDirectInvoice.js), [claim selection](../../netlify/functions/lib/invoiceRecoveryRepository.js), [completion shortcut and follow-ups](../../netlify/functions/lib/invoiceRecovery.js), [request completion predicate](../../src/orderCreateRequestModel.js).

Reproduction using one fictional sale:

1. Prepare and commit a Direct Invoice order: line total GBP 1,222, approved accounting total GBP 1,200, deposit GBP 100 and a fictional PO reference/remarks.
2. Issue the first invoice but fail the financial follow-up RPC before its SQL write. The SI/UC/order link exists; follow-up is `pending`.
3. Read or retry the original saved request. Status says `issued`, Finish is absent, and retry returns `initial_complete: true`. The invoice registry still has null total, accounting total, PO and remarks.
4. Use the existing saved-order **Resume** action. It fills those fields correctly using the same operation and SI. Readback confirms one order, one new SI, one new UC and one allocation receipt; the original deposit remains unchanged.
5. Repeat with the follow-up SQL write succeeding but its response lost. Amounts are already correct, but the original request still cannot clear the pending follow-up. Saved-order Resume acknowledges that same operation without a second issue.

This is a new-entry completion/recovery defect, not evidence of duplicate issuance. The existing saved-order recovery remains a verified workaround. The broader problem of automatically completing work after all browser tabs close is a separate future design task.

**Proposed bounded fix:** distinguish linked-but-unfinished first invoices from fully completed first invoices; expose their outstanding follow-up in the request/status UI and resume that exact pinned first operation. Reuse the existing guarded follow-up mechanism. Never route an initial retry to whichever newer split/reissue happens to be current. If current references/ownership have changed, require review rather than replacing them. Keep supplied SIs, explicit separate sales, intentional copies, splits and reissues independent. Turn both reproduced failures into normal acceptance tests and add a real-page request-list/Finish scenario before release.

### SH07-R2 — P3: PI original uploads have no explicit maximum byte size

**Confirmed validation gap; recommended hardening before publishing the new Storage path.** `originalFile` validates a positive safe-integer size, and Storage compares actual size with that descriptor, but neither sets an upper bound. A fictional 2 GiB PDF descriptor was accepted. No large file was allocated or uploaded. The endpoint's 6 MiB JSON-body limit does not limit uploaded file bytes. Server commit streams the original again to verify SHA-256, so an oversized file can consume storage/bandwidth and keep verification timing out on retry.

This requires a permitted Shipping operator and their own prepared request; it is not an anonymous upload or cross-customer access bypass. Set a documented practical limit consistently in selection feedback, server descriptor validation and Storage rules. Test boundary values and direct oversized requests, preserve original bytes for accepted files, and keep already saved files readable. [Descriptor validator](../../netlify/functions/lib/orderCreateRequests.js) · [Storage path](../../storage.rules) · [Original verifier](../../netlify/functions/shipping-order-request.js).

The scoped Firebase assessment is [recorded as JSON](V8.20-SHIPPING-RECOVERY-RULES-AUDIT.json). Direct rule-denial tests do not establish secrecy for anyone holding a Firebase download-token URL: existing source-file bearer-link behavior is preserved and is outside a new private-download redesign.
