# Packing List scenario isolation and atomic save

The Shipping Packing List tab keeps each scenario's draft in memory while
the tab is open. Switching waits for a coherent header and carton snapshot,
and late reads cannot replace the active scenario. A failed switch retains
the prior draft and offers Retry. Editing and switching pause while a save
is pending. New and duplicated scenarios first become printable and available
to Freight when their first complete save succeeds.

One Firestore transaction updates the header, pallets, totals, cartons and
contents. Existing scenario, carton and item IDs are reused. The transaction
rejects a stale saved identity, and retrying the same draft after a lost
acknowledgement adopts the previous commit. The editor uses the transaction
result directly, so a failed refresh cannot turn an acknowledged save into
a failure. The print and Excel screen uses the same coherent reader. Existing
scenarios need no migration.

The transaction writes only changed child documents and deletes only removed
ones. The SDK's atomic write limits still apply. A plan that exceeds them
keeps its open draft and the last complete saved plan. Saves require a
connection. Drafts are scoped to the open Packing List tab.
