# Shipping Duplicate Order recovery

**Implemented locally.** The existing Duplicate action used to issue a UC in PostgreSQL before creating the copy in Firestore. Losing either confirmation allowed a retry to request another UC. This slice extends the [manual order request](V8.20-MANUAL-ORDER-PI-RECOVERY.md) and covers that gap. [Fictional review](V8.20-GENERAL-ORDER-CREATE-RECOVERY-REVIEW.md)

## Using Duplicate

- Select **Duplicate order** on the source row. The first click prepares the copy, issues its UC, saves the order with a fresh SO and opens it.
- Clicking Duplicate again on the same source opens that operator’s latest copy request. **Finish order copy** resumes a pending copy. **Open saved order** opens a completed one. **Shipping → My saved order requests** also lists earlier copies.
- **Make another copy** explicitly prepares a separate order from the source as it exists now. Review the saved items and select **Finish order copy** to issue its own UC and SO. An earlier pending request stays available in the operator’s list. Two tabs requesting the same successor converge on one request.
- Leaving Shipping during a pending save respects the new page. An issued UC can be recovered even if the original order later changes or is deleted. Missing or replaced finished orders show a review message. Registry conflicts show a review message and retain the issued receipt.

Copies carry the customer, currency, incoterm, destination, notes and normalized lines. The copy starts in draft with fresh references and empty totals. Numbered lines retain their order and unit-price precision. Legacy lines without a line number are included after the numbered items. The source record retains its original UC, references and financial fields.

## Where recovery is stored

1. The service checks the operator’s Shipping, Quotes and UC permissions. It reads the source and lines in a Firestore transaction and freezes the copy, the intended order ID and the UC request. The operator’s private `copies/{sourceId}` pointer and request are saved together. A new request with a stale displayed source header prompts a review. An exact retry of an earlier request ID can still find that original request. [Copy preparation](../../netlify/functions/lib/duplicateOrderCopy.js)
2. The service records that issuance has started before calling PostgreSQL. A service-only function serializes requests for one operation ID and writes one registry row and its immutable receipt in one SQL transaction. The receipt includes the actor, source, destination order and original issuance terms, including the Hong Kong year. Read-only recovery checks the actual receipt. A changed registry identity, reassigned row, closed or voided UC requires review. [UC adapter](../../netlify/functions/lib/duplicateOrderUc.js)
3. The Firestore commit rechecks permissions and the receipt’s subject, then creates the copy and its lines, allocates the SO and marks the request complete in one transaction. A repeated commit returns the same order. Other operators can intentionally start their own independent copies. [Order commit](../../netlify/functions/lib/orderCreateRequests.js)

## Migration and future release

The [migration](../../erp-sync/migrations/20261108122444_duplicate_order_uc_receipts.sql) adds `oc_shipping_private.duplicate_order_ucs` and `public.duplicate_order_uc(uuid,jsonb,boolean)`. It uses the registry’s existing UC default. It adds no invoice, historical backfill, sequence change or uniqueness constraint on a source order. The private receipt has row-level security. The RPC fixes its search path and grants execution to the service role. Anonymous and authenticated database roles cannot execute it or select receipts. [Supabase function privileges](https://supabase.com/docs/guides/database/functions)

Only disposable local PostgreSQL 17 databases received the migration during verification. For a future release, confirm the target table/default and roles, verify that the new schema and RPC names are free, then apply the reviewed migration under the repo’s exact-commit release workflow. Confirm the signature, privileges and migration readback before enabling the new app path. Refresh older tabs, which can still call the former Duplicate flow. Keep the receipt table and issued numbers through an app rollback. [Release workflow](../skills/RELEASE-WORKFLOW.md)

## Fictional verification

- The integration suite runs the actual Node handler, Firestore transactions and PostgreSQL migration. The fixture supplies fictional identities and bridges the RPC’s HTTP payload to SQL as `service_role`. Cases cover concurrent submissions, lost UC responses, rejected Firestore saves, receipt conflicts, missing sources, permissions, repeat copies, legacy lines and rollback.
- The native Chrome suite exercises the actual Shipping row button, pending recovery after reload, **Make another copy**, lost preparation and final-save confirmations, and navigation while the UC call is pending. SQL, Firestore and the browser run locally.
- The existing manual/PI and invoice recovery suites are separate compatibility checks. Initial Direct Invoice creation remains the next cleanup slice.

The final build passed 1,133 prebuild tests. Eleven copy integration cases, eight manual/PI emulator cases, eight Chrome scenarios and 23 existing invoice recovery cases passed. With both SQL migrations installed, the copied order’s UC supported three distinct invoices for first issue, split and reissue. Retrying each invoice returned its original result. Local verification logs are in the git-ignored `qa/out/sh07-duplicate/` directory.

The combined tests use the repository’s loopback PostgreSQL 17 fixture (`QA_INVOICE_DATABASE_URL` pointing to `oc_invoice_recovery_qa`). Use Node 22, Java 21 and the local Chrome setup for the browser run.
