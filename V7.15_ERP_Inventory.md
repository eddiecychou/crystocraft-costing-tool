# V7.15 — ERP Data Inventory (step 1 of the JES retirement)

**Status:** first pass complete, 2026-07-18. Read-only survey of the Supabase
mirror; nothing in JES or the app was touched.

Goal of this step: work out **what the ERP is actually for**, so we know what a
replacement has to cover. Reproduce with `erp-sync/inventory.py`
(`schemas` / `tables` / `recency`); raw results in `erp-sync/inventory/*.json`.

| | Tables | Rows |
|---|---:|---:|
| Mirrored from JES | 494 | 18,726,306 |
| Non-empty | 208 | — |
| **Active in the last 3 months** | **52** | **18,448,255 (98.5%)** |
| Active in the last year | +9 | 57,507 |
| Stale (1–3 yr) | 10 | 57,387 |
| Dormant (3 yr+) | 93 | 18,913 |
| Reference/lookup (no date column) | 41 | 140,734 |

**286 of 494 tables are completely empty.** JES is a *jewellery-industry* ERP
package (alloys, gold casting, diamonds/Rapaport price feeds, stone
clarity/cut/setting, hallmarking, POS/retail, consignment, customs declarations,
Tradelink EDI, fixed-asset depreciation). Crystocraft uses a fraction of it.

> We are not replacing an ERP. We are replacing **the slice of one that this
> business actually uses** — and that slice is six modules wide.

## 2. Accounting is out of scope — confirmed twice over

JES's general ledger **was never used**. Every transactional accounting table is
empty: `acjournal` (the GL itself), `acsettle`, `acperiodended`,
`acperiodbalance`, `acbudget`, `acallocation`, `acve` — all **0 rows**. The only
accounting rows that exist are configuration (chart of accounts 119, period
codes 26, report settings 34), last touched **2004–2006**, and `acyearearn` has
one row stamped by user `demo` — vendor sample data.

**Owner confirms: accounting runs in a separate system, PBIS, on Cindy's
machine.** So retirement never has to close books, run periods, or produce
statutory output. This removes the risk most likely to have killed the project.

### The one real dependency: the invoice export to PBIS

Invoices are **exported from JES and imported into PBIS**. JES's *built-in*
accounting interface is not what does this — `accinterfacesetting` and
`acinterfacelog` are empty, and `accinterfacecodemap` is a stub (681 rows, one
customer mapped to `AR-A01`, every other account code null). So the export is
almost certainly a **report/list export to Excel/CSV**, whose column layout
lives in JES's report definition, not in any table we can read.

**Needed before designing anything:** one real export file exactly as Cindy
sends it, plus the JES menu path that produces it. That converts the finance
handoff from an unknown into a fixed contract the app can reproduce — after
which her PBIS import is unchanged and she need not notice the cutover.

**Sequencing implication:** invoicing is the function most tightly coupled to a
downstream consumer, so it is probably *not* the right first migration. Prove
the pattern on something whose output nobody else consumes.

**Sales.** `salesorder` (5,630) + detail/ana/surcharge/hallmark;

**Purchasing.** `purchase` (4,255), `purchasedetail`, `purchasedetailitem`,

### Notable: the quotation module is already abandoned

`quotation` / `quotationdetail` stop at **2024-12-20**. Quoting has already

Also effectively dead: `employee` (2025-02), `warehouse` (2016), `shipmethod`
(2020), `customeraddress` (2 rows, 2005), all 93 dormant tables.

## 4. Data-quality notes (carry into any migration)

- **Every one of the 7,510 columns in the mirror is `text`.** Deliberate — the
  sync lands raw so a bad value can never fail the load, and `api_views.sql`
  casts on the way out (62 × `nullif(col,'')::numeric|timestamp|int`).
  **Rule: every new curated view must cast.** Uncast text comparisons produce
  wrong numbers that look like right ones.
- **Junk dates exist.** `itembatchheader` max = `4131-02-20` (typo),
  `currencytx` = `2099-12-31` (sentinel). Validate ranges; don't trust MAX.
- **Don't infer meaning from column names.** `lastupdate**by**` contains the
  substring "date" but holds usernames — an early version of this survey
  reported a confident ranked table of "recent activity" that was entirely
  usernames. On a 494-table all-`text` mirror, wrong answers look like right
  ones. Validate values, not names.
- Sales dates run slightly into the future (shipment/delivery dates) — expected,
  not corruption.
- **`itemwhbal` is a stale snapshot — do not use it for stock.** It is the
  obvious "item warehouse balance" table, but of its 8,599 non-zero rows
  **8,368 have a null `lastupdate`** and only 25 were touched in 2026. Stock
  must be computed from the movement ledger `itemtransaction` (signed
  `itqtycal`, live to the last sync). The two agree on 93.75% of a 400-row
  sample; the disagreements are all in the fast-moving warehouses (FWIP/FSTK) —
  items that kept moving after the snapshot froze. In aggregate they match
  (ledger 8,604 non-zero pairs vs 8,599). Built this way in `erp_stock`.
  *Generalise: prefer JES's ledgers over its balance tables until each balance
  table is proven maintained.*

## 4a. There is no bank master in the ERP

Checked while scoping default bank accounts for customer receipts and supplier
payments. JES has the *shape* of a bank master and none of the substance:

| Table / column | Reality |
|---|---|
| `raw.bank` | **2 rows** — `HKB` "HONG KONG BANK" (name column is null), `HSB` "HENG SANG BANK". Last touched 2003 / 2005. `baaccode` = `11-1`, a GL code — these rows exist to feed the never-used GL interface. |
| `raw.accountno` | **empty** |
| `customer.ctbank` | populated on **10 of 458**, only ever `HKB`/`HSB` |
| `supplier.subank` | populated on **8 of 463**, same two codes |
| `ct/su accountnn`, `…nnar`, `…nnap` | **0 of 458 / 0 of 463** — never used |
| `acbankrec` / `acbankrecdetail` | the dead GL module; 2004–05 only |

There are no account numbers, SWIFT/IBAN, beneficiary names or intermediary-bank
fields anywhere in the schema. The app has none either — the only trace is a
placeholder in the quote-terms textarea (`QuoteDetail.jsx`) hinting the user
type "Beneficiary Bank: …" as free text.

**So remittance details today are retyped by hand per document, and/or live in
PBIS.** Consequence for V7.15: bank accounts are **new app data, not a
migration** — nothing to extract, no legacy shape to honour. That is the easy
version of this problem.

Two things to get right when it is built:

- **Supplier bank details are a fraud target.** Invoice-redirection (BEC) fraud
  works precisely by changing a supplier's account number. Whatever stores them
  needs an audit trail of changes (who/when/old→new) and ideally a confirmation
  step, not a plain edit field.
- What is usable from JES here is `paymentmethod` (12 rows) and `paymentterms`
  (39 rows, live to 2023) — genuinely used, referenced by 93% / 95% of
  customers. Those are worth carrying over; the bank tables are not.

## 4b. The document model (owner, 2026-07-18) — and a duplication to remove

Naming matters here because the team's words and JES's words differ:

| Team says | JES document | Generated in | In the app |
|---|---|---|---|
| **PI** | **SO** (sales order) | JES | PDF uploaded, AI-parsed into `orders` + lines in Firestore |
| **Invoice** | **SI** (sales invoice) | JES | referenced by number only (`erp_si`, UC registry) |

- An **SI is often copied from an SO in JES — but not always.** Simple sales are
  invoiced directly with no SO behind them. Any future invoice module must
  support both creation paths; it cannot assume SI derives from SO.
- Neither document is generated by the app. `QuoteExport` (the quotation) is
  the only real document generator, plus the packing-list and PO print pages.

### The app re-parses data it already has

The PI/SO import runs AI extraction over a PDF to recover header and line
items. Those exact lines already exist as clean structured rows in the mirror:

```
public.erp_sales_order       code, date, customer, currency, amount, status
public.erp_sales_order_line  order_no, seq, item_code, description,
                             item_type, qty, unit_price, amount, ship_date
```

188,386 order lines, current to the last sync (SO260026, 2026-07-16). The
parsing was built before the ERP archive existed; now that it does, **importing
an SO by number is strictly better than OCR-ing a picture of it** — no
extraction errors, no Gemini call, instant, and the item codes are the ERP's own
rather than whatever the parser read.

More importantly it removes a **second source of truth**: today the same order
lines live in JES *and* in a re-parsed Firestore copy that can silently diverge.

**The blocker is freshness, not capability.** The mirror is a manual
full-replace, so an SO raised this morning isn't there yet. That makes the
incremental-sync work (§"Known gaps" in PROJECT-PLAN V7.14) a prerequisite
rather than an optimisation — or, cheaply, keep PDF parsing as the fallback
when the SO number isn't found in the mirror yet.

Suggested order: incremental sync → SO import by number (parser as fallback) →
then invoicing, which is the PBIS-coupled piece and wants the export sample
first.

## 4c. Item master / BOM vs the app's components — complementary, not rival

Owner's observation: the app tracks *critical components*, while the ERP item
master carries the **full BOM — metal, crystals, packaging**. Both true. But the
two systems hold different halves of the problem, and neither is a subset of the
other.

### The ERP has the complete structure

`explode_bom('D0175-001-GPI')` — a real finished good from SO260026 — returns 16
lines over 2 levels: the stone (`ST` BDC-8232-0014-005 ×2), alloy sheet (`AY`),
semi-finished metal (`FM-*`), and **all the packaging** (`P-*`: gift box,
certificate, hang tag, tissue paper, silica gel, screw, silver string, EPE foam).
Nothing is missing.

### The ERP has almost no costs

| column | non-zero, of 44,460 items |
|---|---|
| `a_cost` | **0** |
| `b_cost` | **82** (0.18%) |
| `c_cost` | **0** |
| `labour_cost` / `metal_cost` / `stone_cost` | **0** |
| `srp` | 34,281 (77%) |

**Costing was never done in JES.** It holds structure and selling prices; the
cost side of the item master is empty. So the app is not a partial copy of the
ERP's costing — **the app IS the costing system**, and the ERP has none.

### What each side actually owns

| | ERP | App |
|---|---|---|
| Complete physical BOM | ✅ | partial by design |
| Component costs | ❌ empty | ✅ `range_components` |
| Crystal prices | ❌ | ✅ `crystal_unit_costs` (size × brand) |
| Plating / extras / markup | ❌ | ✅ `costing` |
| SRP | ✅ 77% | ✅ computed |
| Products not yet in JES | ❌ | ✅ |

The app's exclusions are deliberate and documented: `range_components` covers
only parts that drive the production promise (lead time, tooling, MOQ, supply
risk); packaging is stocked with "no per-product BOM"; crystals are costed as a
size×brand BOM because a stone's brand does not follow the SKU's brand.

**They already share a key space** — a component's `code` IS the ERP item code,
and packaging items are ERP codes too. So they can be reconciled without a
mapping table.

### The opportunity (reconcile, don't replace)

Same pattern as the SO cross-check: the ERP knows *what is in the product*, the
app knows *what it costs*. Use the first to check the second.

1. **Completeness check on costing.** For a range product whose code has an ERP
   BOM, list what the ERP says it contains and flag anything the costing has no
   line for — "the ERP says this also has a gift box, hang tag, tissue paper and
   silica gel; your costing has no packaging line."
2. **Seed `crystal_bom` from the ERP.** The ERP already knows
   `BDC-8232-0014-005 ×2` = Bohemia 8232/14; today someone types "2 × 14mm
   Octagon, Bohemia" by hand. Suggest the line, let a human confirm the
   size/brand mapping.
3. **Packaging per product.** The ERP knows exactly which box/tag/insert each
   design consumes. That would improve packing and MRP, where the app currently
   has only pooled packaging stock.

**Do not replace the app's model with the ERP BOM.** Two reasons: the ERP has no
costs to replace them with, and the app must cost products that do not exist in
JES yet — new designs are quoted before an ERP item is ever created. That
capability has no ERP equivalent.

### PBIS carries the app's UC number

```
SALES INVOICE SI250040 / UC4743/
```

Every sales voucher references both the JES invoice (`SI250040`) and the UC
number. **That is the join across all three systems** — JES, `uc_registry`, and
the books — and it already exists, with no work from us.

**Cross-check result: 152 of 152 UC numbers in the books exist in
`uc_registry`. Zero orphans.** Nothing has been posted to the books that the
registry doesn't know about, which independently validates the V7.14 migration.

One disagreement: **UC4836** — books say `SI250137`, the registry says
`SI250128/137`. Probably one UC covering two invoices, but the registry's
free-text `SI250128/137` isn't a parseable reference. Worth a decision on how
multi-invoice UCs should be recorded.

### The books are ~5 months behind

Median lag from transaction date to posting is **153 days**, worst case over a
year. FY2025 sales were posted in March 2026. This matters for anything that
would read "what's paid" from PBIS: it is not a live source.

### What this does NOT tell us

reading the UC registry as well as the JES invoice, meaning the app is already
upstream of the books. If so, the app generating the posting file directly is a
smaller step than it looks.

## 8. The 31 March stock take is already in JES — as IA documents

The open question "which 31 March, and what cost basis" has a partial answer
that no one had to supply: **the stock take is performed in JES every year, as
Item Balance Adjustment documents**, and it has been since 2007.

**2026 is done.** Four documents, issued 31/3/2026, entered 8–13 May:

| doc | remarks | lines | net qty | warehouses |
|---|---|---:|---:|---|
| `IA260033` | 31/3/26 STK TAKE ADJ CRYSTAL | 3 | −3,508 | FREV, FSTK |
| `IA260034` | 31/3/26 STK TAKE ADJ POS | 7 | −8,045 | FSTK |
| `IA260035` | 31/3/26 STK TAKE ADJ PURPART | 92 | −273,147 | FSTK |
| `IA260036` | 31/3/26 STK TAKE ADJ PACKING | 162 | −1,086,744 | FSTK |

**The trap.** `IA260039`, issued 16/6/2026 with the remark *"This amount offsets
order IA260033"*, is a **line-for-line exact reversal** of the crystal document
— all three lines, same warehouses, same codes, opposite signs:

```
IA260033  FREV BDC-8232-0014-002  -3598   IA260039  FREV BDC-8232-0014-002  +3598
IA260033  FSTK BDC-8232-0014-002   +240   IA260039  FSTK BDC-8232-0014-002   -240
IA260033  FSTK C01-1028-09-021     -150   IA260039  FSTK C01-1028-09-021     +150
```

So **the 2026 crystal stock-take adjustment has net zero effect.** Any valuation
that reads `IA260033` without `IA260039` will be wrong, and the same pattern
appears in earlier years (`IA260031` "AJD IA260030", `IA181721` reversing
`IA171570`). Reversals are normal practice here, not an anomaly — the
adjustment ledger must always be read net.

**Two more things the remarks give away:**

- **Metal is absent from the 2026 take.** 2025 had `IA250025` "STK TAKE ADJ.
  METAL", 2024 had "POS&METAL"; 2026 has crystal, POS, purchased parts and
  packing only. Consistent with metals not being maintained in JES.
- **Adjustments are routinely tied to invoices after the fact** — "ADJ JAN26
  SI260002/40/56", "ADJ MAR26 SI260029/30/52/53/54", "adj rework order SI260039
  Widdop". Stock is corrected in batches against invoices already issued, which
  is a further reason the balance tables lag the ledger.

**Backdating is the norm.** Issue dates are the effective date, entered weeks
later — the 31/3 documents were keyed on 8–13 May. Anything the app builds
against these must use the issue date, never `LastUpdate`.

## 9. Other structure confirmed from the screens

- **Job orders are compound-numbered**: `JO260022-012-001` — one job order per
  product per line, not per order. Status `CLOSED`, SBU `FR`.
- **Sales Return references a credit note**: `SR260004` carries `CN581/26` in
  its Reference field, tying the ledger to the DN/CN register found in V7.16.
  That is the join Cindy's DN/CN mapping will need.
- **Purchase orders carry zero-price lines** — `PU260044` line 3
  (`P-WB051000002-WD`, 500 pcs at 0.00). Free/bundled items are normal; a PO
  importer must not treat 0.00 as missing data.
- **GRN links to a PO line, not just a PO** — `Goods Receive Note Detail` binds
  `P.O. No.` + `P.D. Seq`. Receipts are matched at line level.
- **JES rejects empty item codes** at GRN entry ("Empty item code is not
  supported") — one of the workflow constraints the app made optional.
