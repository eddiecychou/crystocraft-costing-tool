# Reusable Crystocraft Range MCP — V1, read/preview deployed

Built from upstream `f2742198`, branch `codex/reusable-range-mcp`. This is a **separate** stdio server and `/api/mcp-range` Node endpoint. It does not reinterpret, register over, or grant privileges to the existing B0016 or Corporate Gifts writer. The initial implementation did not create production state. The separately approved release now has a scoped read/preview identity and endpoint; live commits remain disabled and no catalogue test record was created. See [release evidence](../../docs/plans/RANGE-MCP-RELEASE-2026-10-16.md).

## Tools and example

`manifest.json` is the complete generated tool schema (regenerate with `node mcp/range/export-manifest.mjs`). Runtime validation uses the strict schemas in `server.mjs` and the independent server-side planner.

| Tool | Boundary |
| --- | --- |
| `search_range_families` | At least one bounded name/exact identity filter; 1–50 results, default 20; canonical expanded codes and stored base SKU both searchable. |
| `get_range_family` | One stable ID; version, update timestamp, finishes/chips, exact links, size/dimensions/media, price state; no supplier quotes/costs. |
| `search_range_components` | Exact code first or bounded name; returns canonical ID/code/category/plating, version and linked flag. Punctuation candidate requires selecting the returned ID **and exact code**. |
| `prepare_range_upload` | Read-only, no approval/audit/reservation writes; structured existing/proposed/diff, missing facts, conflicts, warnings, signed token/hash/expiry. |
| `commit_range_upload` | Exact token, private owner approval ID and caller UUID; no payload override. Atomic commit, persisted readback and durable receipt. |

Example payload in `examples/hidden-family.json` is **emulator-only**, uses synthetic component IDs, and must never be submitted to production. Family facts are not defaults. First search exact design/format and intended full code. If found, read the existing ID/version and prepare `mode:update` with that `range_id` and `expected_version`. Never create another coach as a live test.

A finish row contains `crystal_colors` chips. Additional price-distinct configurations may have their own rows. Codes use `buildRangeSku` / `enumerateRangeSkus`, not a new formula. New rows get stable `id`; older rows are addressed as `legacy_<index>`, valid only against the exact family version. Do not cache legacy index identities across another read/version.

For each critical link, explicitly select the exact existing `component_id` + `code`, or supply a full `create` definition including approved library category and plating. Include `qty_per_unit`, applicability (`auto`, `always`, or an offered plating), and `critical_reason`. `ref_index` corrects an existing link against its exact version. Unmentioned links/variants remain; no removal/replacement API. This is selected supply-critical stock, not a full BOM. New taxonomy requires exact `field:value` confirmation only where the OC datalist permits it. Crystal chips and component categories must be in current settings.

Overall dimensions require positive confirmed length/width/height and `mm`/`cm`; partial/ambiguous measurements return `needs_input`. Defaults: hidden Concept, null wholesale prices. No stock, MOQ, lead, quotes, supplier identity/cost, formula or publication writes. Existing visible-family corrections additionally require explicit owner public-update consent; the tool still cannot change visibility/status/prices.

Media V1 accepts only an exact existing Range gallery/variant/colour-image reference read back from its source family, on the configured OC Storage buckets and Range paths, with caption. Append only. No file path, base64, arbitrary URL, download, upload, deletion or implicit media change. Upload through approved OC UI first. The server validates reference provenance, not image bytes. Storage object replacement under the same URL is outside this V1 transaction.

## Authorization and live-use gates — owner approval required

Nothing here authorizes the following deployment/provisioning actions. Review the code/rules first, then separately authorize a candidate and production release under `docs/skills/RELEASE-WORKFLOW.md`, including fresh real-page admin **and approved customer** sign-in on each. The emulator mock admin is not hosted login proof.

1. Review and deploy the prototype Firestore **and** Storage rules as separate security releases. New service UID is permanently excluded from general admin/staff/customer/storage paths, even if misprofiled. It must not receive ordinary modules or direct Range writes. Do not deploy old rules after enabling this capability.
2. Ship the new app/endpoint plus shared normal-UI persistence contract. Rules now require `range_family_claims` for family creation/identity changes, and `range_component_claims` for component creation/code changes. Existing same-identity edits remain valid. Old cached forms/import scripts that omit reservations fail closed and must reload/update. Schedule a maintenance window for rules/app cutover; keep the new capability disabled until both are verified. Other Admin SDK writers must use the same reservation contract or be paused. Do not enable generic writes while a legacy B0016 release window is active.
3. On a trusted operator machine, provision **only** Firebase UID `mcp-range-upload-service`, custom claim `range_upload:true`, profile `{role:'service',status:'approved',service_scope:'range-upload-v1',modules:[]}`. This special role intentionally grants no UI role. Never reuse the corporate writer, grant full admin/figurine/supply, or copy an Admin SDK key to an MCP client. Bootstrap the scoped refresh credential through Firebase Auth using trusted operator tooling. No automatic provisioning script is shipped/run.
4. Configure a separate server-only random signing secret of at least 32 characters in `RANGE_UPLOAD_PREVIEW_SECRET`; retain existing server Admin credentials only on Netlify, with runtime scope including Functions. The endpoint uses the esbuild bundler and externalizes firebase-admin. `RANGE_UPLOAD_WRITES_ENABLED` defaults off. The Admin SDK bypasses rules, so handler field/collection validation, authenticated roles, review checks and server secrets are part of the security boundary.
5. Trusted operator creates private `range_upload_controls/service`: `enabled:true`, `principal_uid:'mcp-range-upload-service'`, `writes_enabled:false`. Reads/prepare need this explicit enabled control. For an approved write window only, set `writes_enabled:true`, `write_expires_at` to a Firestore Timestamp no more than one hour ahead, and enable the server write flag. Disable both afterward. Expiry is rechecked inside the commit transaction.
6. Install dependencies with `npm ci --prefix mcp/range`. Register a **new** server entry, command `node`, args `[absolute/path/mcp/range/server.mjs]`; env `OC_BASE_URL` approved candidate/production origin, `OC_FIREBASE_API_KEY` public app key, `OC_RANGE_REFRESH_TOKEN_FILE` absolute private owner-only 0600 scoped refresh-token file. The client refreshes scoped access tokens and persists rotated refresh credentials; no service-account/custom-token minting. Do not register over B0016. Verify actual `tools/list` and a harmless read/dry-run after restart.
7. Obtain a dry-run JSON. A human OC admin reviews all proposed facts, new parts, exact diff/hash and warnings. `node mcp/range/operator.mjs preview.json` defaults to review only and prints the proposed new component definitions too. Approval uses a separate current admin ID token, `OC_REVIEWED_PREVIEW_HASH` and `OC_APPROVAL_PURPOSE`, then explicit `--approve`. `--allow-public-update` is a separate affirmative consent for an existing visible product. This operator action is **not** an MCP tool and accepts no service/admin key. No self-approval. Protect tokens from shell history/logs; never paste them into an agent prompt.
8. Commit the exact token + returned approval ID + caller-generated UUID. Save them securely until outcome resolved. Owner approval is single-use and 15-minute preview-bound. Never mint a new key to retry a timeout: retry the same token/approval/key. Receipt replay survives token expiry but still requires the scoped account/control to remain enabled. `readback_verified:false` means the receipt exists but readback needs reconciling; it is not permission to create again. Fetch the family and inspect audit/receipt as admin. After a concurrent update or a 409, get a fresh readback and obtain fresh approval.

Preview tokens bind full target/reference versions, current settings, catalogue/component identities, proposal/diff, caller scope and 15-minute expiry. Full target hashes include unrecognized fields and `colour_images`. Replanning and claim reads occur inside the transaction; family, missing components, claims, approval consumption, receipt and sanitized field-level audit commit together. A failed transaction leaves no family/part orphans. Failure events contain only actor, operation, UUID, code, time and outcome uncertainty in server logs, never request/token/private document bodies. Committed audits/receipts are private admin-readable, client-immutable. A lost server log is not a durable failed-write receipt; investigate with the UUID and retry protocol.

Claims are immutable tombstones, intentionally retained after record deletion; never delete them to force a duplicate. Normal seed reset reuses the reserved family ID. Legacy exact/punctuation duplicates must be reconciled by an operator before proceeding. Do not backfill or repair live data automatically.

V1 bounds: reads/plans scan at most 2,000 families and 2,000 components server-side to catch unindexed legacy collisions; output is filtered/bounded. Above that, fail closed pending an index migration. Commit transactions are intentionally conservative (unrelated identity changes may invalidate a preview). Limit 40 supplied variants, 20 critical links and 200 family codes; 128 KiB HTTP request, bounded text/media/token sizes. This is a single-family tool, not a bulk publishing API. Only this endpoint, the updated normal UI/import writers and the existing controlled B0016 writer participate; privileged external writes outside this contract cannot be protected by client rules.

## Simple owner/agent workflow

Use [RANGE-PRODUCT-ENTRY.md](../../docs/skills/RANGE-PRODUCT-ENTRY.md). The owner can use Quick Add in OC or send one natural-language brief to the agent. The agent resolves library identities and prepares one complete preview; the owner does not need to handle JSON/token/CLI details. Keep optional fields optional, consolidate genuine missing-fact questions, review once and correct the same product. Existing exact-preview approval and live-write locks remain unchanged.
